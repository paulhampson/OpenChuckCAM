# UI message inventory (prefix U): apps/openchuck-ui/src and the openchuck-app presentation helpers it calls

Read-only survey of `main` at e869d932 (7 Nov 2026). Test code and doc comments excluded. Paths are relative to the repository root.
Message texts that are made in other crates (path warnings, setup-warning words, model findings) are listed here by family with how the UI shows and links them; their exact wording and per-warning class belong to the path / types inventories.

## 1. How the UI renders messages today (facts)

**Messages panel** (`apps/openchuck-ui/src/shell/dock.rs:173` `messages_tab`, row layout `row_with_links` dock.rs:440):
- Filter chips "Errors n", "Warnings n", "Information n" (`Severity::name`, crates/openchuck-app/src/overview.rs:308), coloured by severity when on. Tab label "Messages (n)" counts errors + warnings only (dock.rs:96).
- Each row: severity icon (`marks::severity`, shell/marks.rs:103: Error = red filled triangle, Warning = amber triangle outline, Info = blue ring with "i"; tooltip is the plural chip name, e.g. "Warnings"), the text (wrapping; `Message::new` capitalises and adds a full stop, overview.rs:405 / `sentence` 1367), then up to two links: the source item's name (selects it in tree and view) and the action link (`MessageAction::label`, overview.rs:365). A second line holds "Show in view N" links for unreachable-area warnings (dock.rs:231).
- Action link words (overview.rs:365-379): ReviewExport "Show result"; Show "Show"; Reselect "Reselect"; ReviewSetup "Review setup"; EditWorkholding "Edit workholding"; Generate "Generate"; ShowSetting "Show setting"; OpenRecovery "Open project"; LocateRecovery "Locate folder"; ShowInView{area} "Show in view 1".."Show in view 5".
- Order: errors, warnings, information (stable sort, overview.rs:2368); shell-added messages inserted by severity (`Overview::push`, overview.rs:677).
- The disabled primary action highlights the blocking error message (dock.rs:204, frame.rs:1136).

**Operation row / chip / inspector**: tree mark tooltip = `ItemStatus.cause` ("Warning: <text>") (shell/tree.rs:118, marks.rs:93); inspector header chip = mark + state name (`status_chip`, frame.rs:117). An operation in Warning shows only its FIRST path warning in the cause (overview.rs:1830). Error state gets the inspector error banner "This operation can't be generated" + cause (shell/inspector.rs:971-1004).

**ShowSetting marking**: `Application::operation_warning_settings(op)` (overview.rs:1640) returns the distinct `PathWarning.parameter` names of the op's current path. The inspector (shell/inspector.rs:1061) passes them as `Marks.warned` to `form_panel::show`; each named field gets an amber border and the sentence `WARNED_SETTING` (form_panel.rs:129) under it; the "Show setting" link sets `setting_jump` to the FIRST name only (shell.rs:1429-1435), which opens its section and scrolls to it once.

**Results tab** (`run_panel.rs:77` `result_lines`, tab at run_panel.rs:938): levels Info / Warning / Problem, chips "Errors / Warnings / Information" (run_panel.rs:1141). Copied text prefixes "Warning: " / "Problem: " (run_panel.rs:256). Every path note is a Warning line (run_panel.rs:152-163); feed-limit notes are replaced by one Info line per operation (run_panel.rs:113-121, decision 0430). No line has a link.

**Export dialog checks** (export_panel.rs:1104): "Blocks writing:" (red) or "Warning:" (amber) before each `Check.text` from crates/openchuck-app/src/export.rs:357. No links.

**Setup checks tab** (dock.rs:325): tick or amber triangle, the text, and one action link (no source link). Errors (stored workholding cannot be built) are not rows here.

**Status line**: `Shell.status` is assigned in many places (shell.rs:554, 597, 820, 964, 1691, 1740, 1748, 2047, 2067; shell/pending.rs:44) but nothing draws it: the footer (frame.rs:1119) shows the job or "Ready", "Verify G-code before running it", "Workholding changes not applied" and the step note / blocked reason only. Only tests read it (shell/model_copy_tests.rs:103). Those texts are never seen.

## 3. Mechanism gaps: how a message links to a setting today

**Variants** (`MessageAction`, crates/openchuck-app/src/overview.rs:319; handled in apps/openchuck-ui/src/shell.rs:1394-1437):

| Variant | Link words | What it opens |
|---|---|---|
| `ReviewExport(i)` | Show result | the export result modal for report i |
| `Show(item)` | Show | selects the item in tree and view (`show_item`); no field |
| `Reselect(set)` | Reselect | starts picking again on that set |
| `ReviewSetup(setup)` | Review setup | opens the Setup step on the setup, NO section and NO field (`choose_setup(setup, None)`) |
| `EditWorkholding(setup)` | Edit workholding | the setup's Workholding section; no tab row or field is marked |
| `Generate` | Generate | starts generating stale operations |
| `ShowSetting(op)` | Show setting | selects the operation; marks every field named by its warnings (`operation_warning_settings`) and scrolls to the FIRST one |
| `OpenRecovery(i)` / `LocateRecovery(i)` | Open project / Locate folder | another project's recovery |
| `ShowInView{op, area}` | Show in view N | goes to Operations/Simulate, selects the op, turns the view to the unreachable area |

The only variant that reaches a specific field is `ShowSetting`, and only for operation parameters drawn as number or text boxes.

**Gaps**

1. `ShowSetting` carries only the operation id, not the parameter. All "Show setting" links of one operation jump to the same, first named setting (shell.rs:1431-1435), whichever warning was clicked. The parameter should travel in the action (for example `ShowSetting { operation, parameter }`).
2. Flags and choices cannot be marked or scrolled to. `form_panel::row` passes `warned` and `scroll` only to number/integer/text rows (form_panel.rs:298-330); a Flag (`face_free_ends`, named by four finishing warnings, crates/openchuck-path/src/finishing.rs:244-437) or Choice row gets neither the amber mark, the WARNED_SETTING sentence nor the scroll. Only its section is forced open. So "Show setting" for those warnings lands on an open section with nothing marked.
3. Only operation parameters can be named. `PathWarning.parameter` is a form-field name; nothing can point at:
   - the tool (flute length, diameter, holder) in the Tool section or tool library: the flute warning (U2) links to `stepdown` when a layered strategy gives it, else only `Show`;
   - the operation's Geometry roles and selection sets (U8, U9);
   - setup fields: safe Z, clearance, Clearance from stock, work offset, stock size, part (U16-U26); `ReviewSetup` opens the setup at no section, and the setup inspector has no `warned` marks at all (shell/inspector.rs:1668 passes `warned: None`);
   - machine profile fields (U16, U18, U54 open the machine section at best, no field);
   - workholding tabs and held regions (U3, U27, U28): `EditWorkholding` opens the section but marks no tab row;
   - export choices (short-block settings U73, file name templates U78).
4. Warnings with `parameter: None` link only `Show(op)`: the tab-length path warning (built with `parameter: None`, crates/openchuck-app/src/operation.rs:934), the flute warning without layers, and the swarf, region, rest, face-flow and simultaneous warnings without a parameter (crates/openchuck-path/src/{swarf,region,rest,face_flow,simultaneous}.rs). `Show` selects the operation; it does not open anything.
5. Refusals that name a parameter in words ("operation 'X' cannot be generated: parameter stepdown: …", decision 0522 item 4) get `Show`, not `ShowSetting`: the error has no typed parameter.
6. Results-tab lines (U103-U111) and export checks (U68-U75) have no links at all; Setup checks have an action but no source link; several Messages rows have no source (U10, U11, U13, U38-U41, U43-U46).
7. The reach warning (U9) in Messages offers only "Edit workholding"; spec 11.7 gives it "Show in view" too, as the inspector line has.
8. The operation's Warning state names only its first warning (overview.rs:1828-1831). With levels split into warning and information, the state should follow the most serious remaining level, and the count.
9. Messages have no kind or id: the inspector finds reach warnings by `action == EditWorkholding` with an operation source (shell/inspector.rs:1009-1018, 1206-1218) and matches them to sets by the substring `'<set name>'` (inspector.rs:1603). A typed kind (and the parameter) on `Message` would remove this.
10. The `WARNED_SETTING` sentence is the same for every warning and says "see Messages"; it cannot say which warning or its level.
11. `Severity` has no way to show the same item's message in two places at different levels: refusals are Error in Messages but an amber Warning line in the inspector (U7, U8).

Kinds of message that cannot link to a specific field today: tool-property warnings (flute length, tool diameter vs tab), selection/role problems, every setup and machine check, workholding findings, simulation findings (overcut, rapid cut, enclosed material), G-code check and short-block findings, export file naming, model unit/mesh questions (link selects the model, not its Units field), and any path warning or refusal without a typed parameter or whose parameter is a flag or choice.

## 4. Specification comparison (docs/ui-design/ui-specification.md)

- **Section 9, Messages** defines the row (severity icon: red triangle, amber triangle, blue "i"; one or two sentences; the source as a link; an action link, examples "Reselect", "Review setup", "Generate"), the order (errors, warnings, information; fixed order of sources), filter chips with counts, and "Where messages come from". Code matches the row, icons, order and chips. Differences:
