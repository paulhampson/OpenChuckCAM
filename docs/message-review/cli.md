# Message inventory: command line, build/log/About diagnostics, setup sheet (prefix C)

Scope: `apps/openchuck-cli/src/main.rs` (2402 lines, everything a user can see, tests left out), the helpers it prints from `openchuck-app`, `crates/openchuck-buildinfo`, the About window, the start-up, log and panic texts of `apps/openchuck-ui`, and the setup sheet (`crates/openchuck-app/src/setup_sheet.rs` and how `lib.rs` builds it). Branch `main`, read only.

## How the command line labels levels (summary)

The CLI has no severity type. It writes a free-text prefix, and the same message gets different prefixes in different commands:

| CLI prefix (stream) | Where it is used | Nearest GUI level |
| --- | --- | --- |
| `error: ` (stderr), from `main` (main.rs:453) for every `Err` that ends the command, plus `copy-model` per-model refusals (main.rs:943) | refusals, validation, I/O | Error / Blocking |
| no prefix (stderr) | `validate` model problems (main.rs:531, 536, 540): they fail the command, so they act as errors | Error |
| no prefix (stdout), lines indented under a file or setup | `regenerate` replay mismatch and `check:` findings (main.rs:686, 692), `simulate` rapid cuts and `OVERCUT` (main.rs:1355, 1397). They make the command fail at the end | Blocking / Problem |
| `warning: ` (stderr) | every pipeline note in `validate`, `regenerate`, `simulate` (main.rs:584, 616, 724), setup warnings **and setup notes** in `validate` (main.rs:568, 575), tool warnings in `validate`, unreadable library files, the "no project.toml" lead-in, the long order keys | Warning **and** the GUI's Info (feed-limit summary, linked model note are not "warning" in the GUI) |
| `warning:    ` (stdout, aligned label) | tool warnings in `report`, `tools`, `tool` (main.rs:1599) | Warning |
| `  - ` (stdout, no word) | setup warnings in `setup`/`report` (main.rs:2028), mesh problems in `inspect`/`import`/`units`/`transform` (main.rs:2200) | Warning |
| `note: ` / `note:       ` / `note:      ` (stderr or stdout) | linked model (main.rs:547), setup notes in `setup`/`report` (main.rs:2031), model inspection notes (main.rs:2226) | Info |
| `unit?      ` (stdout) | unit question in `inspect`-style output (main.rs:2162); the same question is `warning:` in `validate` and `import` | Warning |
| upper-case words `UNCONFIRMED`, `OVERCUT` | `machine` fields (main.rs:1865, 1869), `simulate` (main.rs:1397) | Warning / Problem |

Main points:
- **Every regeneration note is printed as `warning:`**, whatever it is: path warnings (copied into the notes), ordinary path notes, one line *per move* for feed limits (the GUI groups them into one Info line per operation, decision 0430), "feed(s) were lowered to the post's maximum feed", short-block reports in Slow down mode. Under the owner's rule several of these are INFORMATION.
- **The same text changes level between commands**: setup notes are `note:` in `setup`/`report` but `warning: setup '…':` in `validate`; mesh problems and the unit question are `  - ` / `unit?` in `inspect` but `warning:` in `validate`; "has changed since it was added (PRJ-02)" is a `note:` in `inspect` (model.rs:377) but a failing problem in `validate` (main.rs:536); tool warnings go to stdout with an aligned label in `tool`/`tools` and to stderr in `validate`.
- **The operation is named by the pipeline prefix `operation '<name>': `** (pipeline.rs:364). The CLI never calls `operation::warning_text`, so the flute-length and tab-length warnings do not get the decision 0522 form `Flute length (operation 'X', tool 'Y'): …` here, and no CLI line names the tool. Post notes use other forms: `Operation '<name>': short blocks …` (capital O, posting.rs:629), `setup '<name>': N feed(s) were lowered …` (setup only, posting.rs:923), `Setup '<name>': …% of the part's surface …` (simulation.rs:191).
- **GC-16 / partial path**: handled. `regenerate --out` refuses to write when any enabled operation has a warning with `requires_acknowledgement` unless `--acknowledge-partial-path` is passed (main.rs:634-653; decision 0239 item 10). Without `--out` nothing is refused: the partial-path warning is one more `warning:` line, not marked as needing acknowledgement. The general GC-16 export confirmation is not asked, as GC-16 says for the command line; the NFR-12 notice is printed at every `regenerate` (main.rs:699).
- **GUI export checks that the CLI does not print at all**: "Operation '…' has not been simulated…", "These machine values are not confirmed on the machine: …", the stock-simulation-skipped warning and its acknowledgement (decision 0168; export.rs:459, 509, 527), and the "Operation '…' was made with a warning: …" form. GC-15 says to "warn when an operation has not been simulated, listing the checks before writing". This needs a flag, not a level choice.
- **Behaviour found while reading (flag only, not a level question)**: `regenerate --out` writes the G-code files (main.rs:654-662) *before* it prints the replay/`check:` results and fails with "N G-code file(s) failed the checks above" (main.rs:701). In the GUI a failed file check is Blocking and nothing is written (export.rs:427). GC-15 says to refuse to write. The files stay in the folder after the error.

## Five most important findings

1. **The CLI prints every regeneration note as `warning:`** (main.rs:584, 616, 724). Feed-limit notes come out one line per move, where the GUI shows one Info summary per operation (decision 0430). "feed(s) were lowered to the post's maximum feed" and Slow-down short-block reports are warnings too. Under the owner's rule these are information (C21, C25, C26).
2. **Levels change from command to command** for the same text: setup notes (`note:` in `setup`/`report`, `warning:` in `validate`), mesh problems and the unit question (`  - ` / `unit?` vs `warning:`), "model has changed (PRJ-02)" (a `note:` in `inspect`, a failing error in `validate`), tool warnings (stdout aligned label vs stderr prefix). Failing problems in `regenerate`/`simulate`/`validate` have no `error:` word at all (C8-C10, C38, C39, C55, C57).
3. **The operation and tool naming of decision 0522 is not applied on the CLI.** Notes carry `operation '<name>': ` (pipeline.rs:364), but `operation::warning_text` is never called, so flute-length and tab-length lines lack `(operation 'X', tool 'Y')`. Post notes use three other forms ("Operation '…'", "setup '…'", "Setup '…'"). No line names a tool or the parameter to change (C19, C24-C26).
