# Message inventory: crates/openchuck-path/src (issue #567), id prefix P

This is a read-only inventory of `main`. Paths are relative to `crates/openchuck-path/src/` unless they start with `crates/` or `apps/`. Test modules, `tests/` folders and doc comments are left out. Parameter labels and descriptions in the schemas are also left out, because they are setting help, not messages.

## How these messages reach the user (path-specific facts checked for this inventory)

- **PathWarning** (`assemble.rs:71`): the Messages panel shows it as Warning with the operation as its source. The action is ShowSetting(op) when `parameter` is Some, otherwise Show(op) (`crates/openchuck-app/src/overview.rs:1844-1856`). The operation chip shows the first warning as the operation's state (`overview.rs:1825-1830`). `operation::warning_text` adds the operation and tool only for the `flutes::WARNING_LEAD` ("Flute length: ") prefix. The "Show in view N" links are offered only when `unreached::lists_areas` matches "simultaneous finishing cannot reach " or "rest machining cannot reach " (`crates/openchuck-app/src/unreached.rs:40-52`). **face-flow's unreached warning (P8) does not match, so it gets no "Show in view" links**, even though face-flow also reports `Unreached` areas.
- **Each PathWarning is also copied into the path's notes** (`strategy.rs:546-566`, segment 0). The app then formats each path note as `"move {segment}: {message}"` (`crates/openchuck-app/src/operation.rs:973-976`), and the pipeline prefixes it with `"operation '<name>': "` (`crates/openchuck-app/src/pipeline.rs:361-364`). As a result, **every PathWarning appears a second time in the Results window as "operation 'X': move 0: <raw text>"**. That copy never goes through `warning_text`, so the flute warning there reads "...move 0: Flute length: the stock ..." with no tool name. The "move 0:" prefix is also misleading, because the warning is not about move 0.
- **Notes** (strategy `notes: Vec<String>`, `PathNote`, and `Strategy::parameter_warnings` strings, which `operation.rs:960` appends to the notes) appear only in the Results window. All of them are shown as Warning, except the feed-limit note, which is summarised as one Info line per operation (decision 0430).
- **Refusals** (`PathError`, `error.rs`): the app wraps them as `"operation '<name>' cannot be generated: <PathError Display>"` (`crates/openchuck-app/src/error.rs:85`, `operation.rs:357-365`). The Display prefixes are: `Parameter` → "parameter <schema key>: <reason>"; `Surface` → "surface: …"; `Region` → "region: …"; `RotaryLimit` → "A axis: …"; `Strategy` → the text alone; `UnknownStrategy` → "no strategy named "X" is available". The Messages panel shows them as Severity::Error with **action Show(op), never ShowSetting, even when the error is a `Parameter` error that names a setting** (`overview.rs:1805-1818`). The **schema key is shown, not the label** (for example "parameter scallop:", "parameter finishing_layers:", "parameter max_hidden_lean:"). Some facing errors use free-text keys such as "arbitrary_faces", "axial margin" and "facing geometry".

Abbreviations used in the table: MP = Messages panel; RW = Results window; chip = operation chip or inspector status; ED = export dialog (acknowledgement); PS = panel-source-only (the text does not name the operation, and the panel row's source link does).

## C. Refusals (PathError): generation fails and no path is made

Common to every row: level = refusal/error (MP Severity::Error, op chip state Error, RW failure). Ack = n/a. Names op = via-prefix "operation 'X' cannot be generated: ". Tool = no, unless stated. Link = Show(op), even for `Parameter` errors. Proposed class = **KEEP-ERROR** for all, because no path is made and the checks must stay. The wording and link proposals are given per row or per family.

**Cross-cutting proposal (C0):** for `PathError::Parameter`, (1) show the field label instead of the schema key ("parameter scallop:" → "Allowed excess:" or "Scallop height:"), and (2) make the MP action ShowSetting(op), because the error names a setting. This changes neither the check nor its level.

## Most important findings

1. **Every PathWarning is shown twice.** The Results window copy reads "operation 'X': move 0: <raw text>" (`strategy.rs:546-566` → `operation.rs:973-976` → `pipeline.rs:361-364`). It skips `warning_text`, so it does not name the tool for flute warnings, and "move 0" is wrong. Proposal: merge it (P30).
2. **Path notes are all shown as Warning in the Results window, but about 30 of the ~45 note templates are pure descriptions** of what was done (ring counts, adaptive passes added, pass order, A smoothing, swarf per-face fit, face-flow pass counts). They should be TO-INFO. About 15 notes are real problems (holes left out P63/P64/P66, chains not cut P59, scallop height ignored P53, material beyond tolerance P71, material left by the grip P65/P46) and never reach the Messages panel or a setting link. They should become PathWarnings with `parameter` set.
3. **Only flute warnings name the operation and tool in their text.** All other PathWarnings (unreached areas, swarf overcuts, face-free-ends safety warnings P6/P7, set-breaking P9/P10, shank breaks P14) rely on the panel source link. To follow decision 0522 they need a lead (for example "Face free ends (operation 'X'): …", "Unreached areas (operation 'X', tool 'Y'): …"). Several also link to the wrong place or to nothing: P2a should link to Stock, P9/P10/P19 to the selection set, P6/P7 to workholding, and P15b offers a Tolerance link while saying Tolerance does not help.
4. **face-flow's unreached-areas warning (P8) gets no "Show in view" links**, because `unreached::lists_areas` matches only the simultaneous and rest prefixes, even though face-flow reports `Unreached` areas.
5. **Refusals never link to a setting and show schema keys.** `PathError::Parameter` shows as "parameter scallop: …", "parameter finishing_layers: …", "lower min_remaining", "max_material_left", and the MP action is always Show(op). Some refusals also show requirement or decision IDs ("(OP-14)", "(SET-09)", "(SET-04)", "(decision record 0021, OI-94)") or a Rust Debug name ("move {} ({kind:?}) collides"). The new Facing construction's ~150 proof refusals (C13) are jargon the user cannot act on. Outside the path crate, the app note "Facing coverage complete (verified path geometry) …" (`crates/openchuck-app/src/operation.rs:983`) says a path is "verified", which should be checked against NFR-12.

The adaptive warning P1 is the only path warning with `requires_acknowledgement: true`, and it stays. No warning is proposed for downgrade.
