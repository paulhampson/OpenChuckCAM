## Decision

1. **The macOS archive carries `OpenChuckCAM.app`** (OI-300). `cargo xtask macos-app --ui <exe> --worker <exe> --out <folder> [--version <v>] [--mtime <secs>]` (`xtask/src/macos_app.rs`, no new dependency) writes `OpenChuckCAM.app/Contents/{Info.plist, PkgInfo, MacOS/openchuck-ui, MacOS/openchuck-step-worker}` (and `Resources/OpenChuckCAM.icns` when an icon is given) from the template `xtask/templates/macos/Info.plist`. The plist names `openchuck-ui` as the executable, the workspace version as `CFBundleShortVersionString` and `CFBundleVersion` (a version macOS refuses, such as one with a pre-release suffix, is a clear error), macOS 11 as the minimum, and the identifier `cam.openchuck.desktop`, under the reverse of the project's domain `openchuck.cam` (question 3). The identifier is lasting: macOS keys the app's preferences, privacy permissions and the **Open Anyway** approval to it, so it must not change between releases. The tree is deterministic: every file and folder gets the commit time (`SOURCE_DATE_EPOCH`), executables 755 and data files 644, and a rebuild replaces an old bundle entirely. The archive holds the bundle, `openchuck-cli`, a second `openchuck-step-worker` beside the CLI (the CLI finds its reader beside itself), and the notices; the plain `openchuck-ui` is dropped, so there is one desktop program, not two. The icon is optional (the owner's decision of 7 Nov 2026, relayed): given a 512 by 512 PNG with `--icon`, the command wraps it as a one-image `.icns` (an `ic09` entry, written with std only, byte-identical for the same PNG) at `Contents/Resources/OpenChuckCAM.icns` and adds `CFBundleIconFile`; without one the bundle has no icon and macOS shows its generic application icon. The build passes `--icon` when `apps/openchuck-ui/assets/icon/icon-512.png` exists, which lane ICON is to deliver; until then the release bundle has no icon (OI-2106). There are no document types (winit does not pass Finder's open-file events to the program). `plutil -lint` checks the plist on the macOS runner. The build then gives the bundle an ad-hoc signature, `codesign --force --deep --sign -` (question 2): it uses no certificate and no Apple account, so the programs stay unsigned in the sense of item 4 (no Developer ID, not notarised), but the seal covers the bundle's `Info.plist` and contents, so a downloaded copy gets macOS's normal "Not Opened" dialog with **Open Anyway** rather than a "damaged" report. `codesign --verify --deep --strict` must pass; `spctl --assess` is printed and is expected to reject the app. `Check the archives` requires `Contents/_CodeSignature/CodeResources`.
2. **The Linux archive is built in Ubuntu 22.04, and its floor is checked** (OI-301). The Linux leg of `build-archives.yml` runs in `ubuntu:22.04` pinned by digest (question 1), installs git, the C and C++ toolchain, CMake and rustup, and passes `variant: ubuntu2204` to `.github/actions/occt`, so its OpenCASCADE install is cached under its own key and never mixed with the runner image's `plain` one (the action and its key format are unchanged; no revision bump; Windows and macOS keys untouched). The floor is stated once, in `build-archives.yml`: `GLIBC_FLOOR` (`GLIBC=2.35 GLIBCXX=3.4.30 CXXABI=1.3.13 GCC=7.0.0`, what Ubuntu 22.04 provides with the libstdc++ of GCC 12) and `LINUX_FLOOR_TEXT` for the README. `cargo xtask glibc-floor` (`xtask/src/glibc_floor.rs`) reads each binary's ELF version-needs table itself and fails if any need is newer than the floor of its family, or belongs to a family with no floor. The build runs it on all three Linux binaries, so a nightly or release build that slips fails. The STEP reader's tests (`cargo test --release -p openchuck-import --features kernel --test step`) run on that build, because decision 0490 made the `ubuntu-latest` STEP kernel job the guard against a reader that crashes at exit, and the shipped reader is now built by a toolchain that job does not use. The nightly UI smoke test gains a leg that launches the Linux archive in the same Ubuntu 22.04 image, which is the proof that the floor holds in practice; its macOS leg launches the program inside the bundle.
3. **The release run reports on the tag protection, and never fails on it** (OI-305). The plan job of `release.yml` warns (an annotation and a line in the summary) when the rulesets API shows no active tag ruleset covering `lib-v*` and `app-v*`, when it cannot read the rulesets, or when the run was not started by the repository owner. It is a warning on every run, real ones included, on the coordinator's instruction of 7 Nov 2026: whether `GITHUB_TOKEN` can read the rulesets is not known until a run shows it, and a check that could not read them must not block the first release. It may become a failure after the dry run proves it (OI-2107). The ruleset itself is the owner's setting; the exact steps are in [releasing.md](../releasing.md#protect-the-release-tags), and the release checklist asks the owner to confirm it before tagging.
4. **The programs ship unsigned for 2026.1-alpha** (the owner's decision of 7 Nov 2026, relayed; OI-135). No code signing, notarisation, signing certificate or installer is built or wired. The archive READMEs, the release notes, the user guide's install page and [releasing.md](../releasing.md#what-the-application-archives-hold) say so plainly, with what a user sees and how to go on: on macOS the "Not Opened" dialog, then **Open Anyway** in Privacy & Security, or `xattr -dr com.apple.quarantine`; on Windows SmartScreen's **More info**, **Run anyway**, or unblocking the zip. The rest of OI-135 stays the owner's, with the lane's recommendation: no Windows installer for the first release; no Intel macOS for the alpha; Linux arm64 later as a matrix row on GitHub's arm64 Ubuntu runners with the same floor container; signing for a later release, with an Apple Developer ID and a Windows certificate.
5. **The Makera Z1 tool data is credited, and OI-269 is closed** (the owner's decision of 7 Nov 2026, relayed: credit, facts-only route accepted). `LICENSES/TOOL-DATA-CREDITS.txt`, shipped in every archive as `TOOL-DATA-CREDITS.txt` and checked by `Check the archives`, and a section of the user guide's tool library page credit Makera (its tool pages and `MakeraInc/CarveraProfiles`) and the Carvera community profiles (`Carvera-Community/Carvera_Community_Profiles`), with the repository addresses, as the sources of the Z1 tools' facts. It is a credit, not a licence grant: neither repository has a licence file, the data is used as facts only (dimensions, parameters, tool numbers and cutting parameters; [decision 0081](0081-slice-23-default-tool-library.md) items 8 to 10), and no legal clearance is claimed (NFR-10). The 54 tool files already name their source per value in their headers and are not changed. This wording does not change the facts-only policy, so it needs no record of its own; it is recorded here because the lane has one.
6. **The tar.gz archives are packed reproducibly**: sorted names, owner and group 0, every time the commit time (GNU tar; `gtar` on the macOS runner), and `gzip -n`. The binaries themselves are not claimed to be byte-reproducible.

## Questions for the owner

Sent to the coordinator on 7 Nov 2026, one per message; the owner answered on 7 Nov 2026 (relayed by the coordinator), and the items above are written to the answers.

1. **Where the Linux archive is built** (item 2, OI-301). Options: (a) an `ubuntu:22.04` container pinned by digest, floor glibc 2.35; (b) the `ubuntu-22.04` runner image while GitHub offers it, same floor, but the floor moves when GitHub retires the image (the check would fail the build); (c) a `manylinux_2_28` container, floor glibc 2.28, widest reach and most build risk; (d) the `ubuntu-24.04` runner, floor 2.39. **Recommended: (a). The owner chose (a).**
2. **An ad-hoc signature on the bundle** (`codesign --sign -`, item 1). This is a question about whether the `.app` opens at all on Apple silicon, not about signing: it uses no certificate and no Apple account, and Apple's linker already puts such a signature on every arm64 binary. A bundle that wraps them without sealing the bundle may make macOS report the downloaded app as damaged instead of offering **Open Anyway**. Options: (a) add it; (b) none, and rely on the `xattr` step; (c) decide after the branch's macOS run. **Recommended: (a), or (c). The owner chose (a)**, with `codesign --verify --deep --strict` and `spctl --assess` run and reported on the branch's macOS run.
3. **The bundle identifier** (item 1): lasting, because macOS keys preferences, permissions and the **Open Anyway** approval to it. Options: (a) `io.github.paulhampson.openchuckcam`; (b) `org.openchuckcam.OpenChuckCAM`; (c) one the owner names. Recommended: (a). **The owner chose (c):** the project owns `openchuck.cam`, so the identifier follows that domain. The lane first wrote `cam.openchuck.OpenChuckCAM`; on accepting this record (7 Nov 2026, relayed) the owner chose `cam.openchuck.desktop` over it (the other forms offered were `cam.openchuck.openchuckcam` and `cam.openchuck.app`). It is not changed after the first release.

## Alternatives considered

- **`cargo-dist` or a bundling crate** for the `.app`: rejected in decision 0031 (no `.app`, slow releases; an `xtask` template adds no dependency).
- **`objdump`/`readelf` in the workflow** for the floor: works, but a shell parse is untested and differs between binutils versions; the `xtask` reads the table itself and is tested on every pull request.
- **Static libstdc++ in the STEP reader** (`-static-libstdc++`): removes the libstdc++ floor but not the glibc one, and changes how the reader links; not needed once the build runs in Ubuntu 22.04.
- **An icon from the toolkit** for the bundle: the owner declined it on 7 Nov 2026; OpenChuckCAM's own icon comes from lane ICON (OI-2106).
- **Keeping the plain `openchuck-ui` beside the bundle on macOS**: two desktop programs, one of which opens a Terminal window (NFR-17). Rejected.
- **Failing the release on the tag check**: rejected for now (item 3).

## Consequences and limits

- The first nightly build after merge builds OpenCASCADE once in the container (about 21 minutes); each build then adds about 1 minute for the container, about 4 for the STEP reader's tests and about 1 for the floor check, and the nightly UI smoke test about 4 for the floor leg. No pull request job and no macOS job is added.
- The shipped Linux reader is built by GCC 11 in Ubuntu 22.04; pull requests test the reader built on `ubuntu-latest`. The tests in item 2 cover the gap on every nightly and release build, not on pull requests.
- A distribution older than the floor (RHEL 9 and its rebuilds have glibc 2.34) cannot run the Linux archive; building from source still works there.
- The `.app` logs into its own folder when that folder is writable (OI-2108).
