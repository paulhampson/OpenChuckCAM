## Context

A model was referenced by its path relative to the project folder, and a file outside the folder was stored with `..` (decision 0008 item 2), for example `../../elsewhere/part.stl`. Moving the folder on its own, zipping it, copying it to another computer or committing it lost the model: `openchuck-cli validate` then reported "model '../../elsewhere/part.stl' is missing" and failed. A file on another Windows drive could not be added at all. Issue #385 asks for a project folder that is self-contained.

## Decision

1. **Copy by default (D1 option B).** Adding a model file from outside the project folder copies it into the folder's `models` folder when "Add to project" is pressed. The import dialog has a tick box "Copy the file into the project folder", ticked by default; clearing it links the file by its relative path as before. `openchuck-cli import` copies unless given `--link`. A file already inside the project folder, anywhere in it, is used where it is and never copied (the tick box is off and says so). The original file is never changed, moved or deleted. The copy holds the bytes that were read and hashed for the check, so the recorded hash is the original's (PRJ-02). Undo of the add removes the model and leaves the copied file; adding the same file again reuses it. Replace file… copies its new file the same way.
2. **The copy's name is its content hash (D2, the owner's direction).** `models/<first 32 hexadecimal digits of the BLAKE3 hash>.<extension>`, the extension in lower case (`ModelRef::copy_path`). The same bytes always give the same name, so a file with the same contents already there is used and nothing is written; 128 bits make two different files of one project meeting on a name no practical risk. The name is lower-case ASCII, so it is valid and distinct on Windows, macOS and Linux whatever the original was called (no reserved device names, no letter-case clashes, no characters a system refuses), and short (44 characters) beside the 100-character project folder rule.
3. **Never overwrite.** A file already at the name whose full hash differs (one edited by hand, or the 1 in 2^128 case) is kept, and the copy takes `<hash>-2.<ext>`, then `-3`, and so on. The copy is written under a hidden staging name and published without replacing anything, as export files are (0267 item 7), then read back and checked against the hash; a failure leaves no partial file under the final name and adds nothing to the project (NFR-07).
4. **The original name is kept (schema 21).** A model reference gains the optional `name`, the file name it had when it was added: a file name only, never its folder, so no user directory is stored, not blank, with no folder separator or control character. It is written only when it differs from the stored path's file name, so a model used where it is, or linked, writes the file exactly as before. The interface shows the name wherever it names a model (the project tree, the inspector's heading, Messages, the action log); a model without one shows its path's file name, as before.
5. **A linked model stays supported (D3 option B, D3a option A).** A path that leaves the project folder is a *linked* model (`RelativePath::is_outside_project`). On opening such a project, each time it is opened, the program asks once for all of them: "This project's model is outside its folder. Copy it into the project now?" (or "This project has 2 models outside its folder. Copy them into the project now?"), with Copy and Not now. Nothing is stored about the answer. The Model inspector's Source section opens with the "Copy model into project" button; `openchuck-cli copy-model <project> [model]` does the same for one model or every linked model, and `openchuck-cli validate` prints a note for each and still passes. Copying changes only the stored path and name, as one undoable step: the ID, hash, unit, placement and the selection sets made on the model stay as they are (PRJ-06).
6. **The setup sheet and messages name both.** `ModelRef::label` is the stored path, or with a recorded name `part.stl (models/d2a8….stl)`. The setup sheet's Part row, the missing and changed file messages and the selection messages use it, so a model without a name reads exactly as before and existing setup sheets are unchanged.
7. **Toolpaths stay current (D6 option A).** The toolpath cache key takes the model's contents hash and format, not where it is stored or the name it is shown by (as operation and setup names, issue 209). Copying a model in, or moving the project folder, makes no toolpath out of date, and the G-code is byte-identical (GC-07, NFR-06).
8. **The wording (D4 option B).**
   - Import dialog, under the tick box: ticked, "It will be copied into the project's models folder and listed as part.stl, so the project folder can be moved, zipped or shared. The original file is not changed."; cleared, "The file stays where it is and is linked by its path. If the project folder is moved without it, the model will be missing."; a file already in the folder, "The file is already in the project folder." The footer keeps "The file is not changed. Its path and hash are stored in the project."
   - Model inspector, Source section: "part.stl, stored in the project folder (models/d2a8b35f….stl)", the hash name cut to 8 digits with the whole path in the tooltip; for a linked model, "part.stl, linked from outside the project folder (../../elsewhere/part.stl). Moving the project folder will lose this model." in the warning colour, with "Copy model into project" (tooltip: "Copies the file into the project's models folder. The original is not changed, and selections and toolpaths stay as they are.").
   - Project tree: a linked model's row has a small link mark (two chain links) after the name and the chip "linked", so it reads without its shape or colour (UI-11), and the tooltip "Linked from outside the project folder: moving the project folder will lose this model. Model inspector, Copy model into project."
   - Messages, as information: "'part.stl' is outside the project folder, so the folder is not self-contained. Model inspector, Copy model into project." The command line uses the same sentences.
9. **Size (D5).** The file's size is shown beside the tick box in plain words ("84.2 MB"). No warning and no different default for large files yet: that waits for version control (OI-1250). A file that cannot be written, a full disk or a file where the `models` folder should be gives a clear error and adds nothing (NFR-07).
10. **Refusals (D7 option A).** "Copy model into project" refuses a linked file that is missing ("'../elsewhere/part.stl' is missing, so it cannot be copied. Use Replace file… to choose it again.") or has changed since it was added ("'part.stl' has changed since it was added, so copying it would change the model. Check it first with Replace file…, which also copies it."), and changes nothing. Selections and toolpaths are never moved onto different geometry.
11. **No index file (D8 option A).** `project.toml` is the index: each model entry has its `name` and `path` side by side. The `models` folder holds only the copies.

## Alternatives not chosen

- **The original file name in `models/`** (the lane's first proposal, with numbered names on a clash): readable in a file browser, but it needs name cleaning for every platform and a clash rule; the owner chose a unique identifier.
- **The model's ID as the name:** unique but random, so the same file imported twice is copied twice, and Replace file keeps the ID, so the new file would clash with the old one.
- **A readable index in `models/`** (D8 B) or **hash plus name** (`d2a8b35f8ea96f41-part.stl`, D8 C): another file two branches can both change, or the name cleaning back.
- **No schema bump:** the model entry is read with `deny_unknown_fields`, so an older build would fail on the new field with "unknown field" instead of the clear "made by a newer version" refusal; a new stored field is a bump (work breakdown, project schema ordering rule 3).
