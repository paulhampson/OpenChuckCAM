## Decision (proposed)

1. **Neutral machine program (slice item 1).** `openchuck_post::to_machine_program` turns the IR into `Step`s in the work frame (`RotaryFrame`): comment, tool change, spindle on, rapid, fed move with its `FeedWord`, and unwind. Machine XYZ comes from the shared kinematics. A rapid at an unchanged tip whose A changes by whole turns is an `Unwind`. Moves with no motion are dropped. A fed move with motion and no duration is an error (the feed cannot be worked out). Tool numbers and spindle speeds come from a `ToolSetting` per IR tool tag (GC-14); a tag with none is refused naming the group and operation.
2. **Post definition and options (items 3 and 4; OI-85).** A post is a folder: `post.toml` (`schema`, `name`, `template`, `feed_rule`, `[options]`) and one template. `PostOptions` is typed (units, A letter, direction, unwind mode and command, header, footer, work offset, tool change, coolant, line numbers, decimals, maximum feed, feed mode, comments); unknown keys, wrong types and out-of-range values are refused at load naming the option, the feed mode must agree with the feed rule, and the template is compiled at load so a syntax error names its line. The template sees every option (unset is `none`). Environment as decision 0019 item 3; fuel is 100,000 plus 400 per step. A direction and unwinding are applied in Rust before the template runs: with `drop_turns` the controller keeps the remainder of A with its sign, so later A values are shifted by whole turns to keep every machine position, which the template then writes unchanged.
3. **Loader rules (OI-84).** Newlines normalised to LF; `posts/** -text` in `.gitattributes`; files over 1 MiB refused; the template must be a plain file name in the post folder; comment text from the project has parentheses replaced by brackets, control characters by spaces and non-ASCII by `?`.
4. **`PostProcessor` and selection (item 2; GC-02).** `PostProcessor::post(&Toolpath, &PostJob) -> PostOutput` (text, clamped feed count, estimated seconds); `TemplatePost` is the first implementation. The two posts ship in `posts/` and are embedded (`builtin`, `builtin_ids`), and load from a folder identically. Tying a machine profile to a post is OI-88.
5. **Shipped posts (items 5 and 6).** `posts/linuxcnc` (GC-10) and `posts/makera-z1` (GC-09) share one template (a test keeps the copies identical) and differ by options and feed rule. Z1: SP-12 conventions, `makera` rule, `G92.4 A0 S0` unwind, no G93, no line numbers, `M5` before `T1 M6`, footer `M5`, `G53 G0 Z-3`, `G28`, `M2`. Numbers go through `fixed` (round half to even, no `-0`). Golden files `testdata/golden/post_*_small_part.ngc` (a 6 mm, three-turn helical groove on a 20 mm cylinder, 45 degree steps, with a three-turn unwind) are reviewed line by line: positions match hand calculation (for example A 45 gives Y -7.071, Z 7.071), the Z1 feed 696.2 is `45 * (2 pi 10 + 30) / 360` mm in 1 s, and LinuxCNC's 459.5 is the 7.658 mm chord in 1 s.
6. **Narrower than GC-04 reads (OI-89).** Millimetres only and continuous A only; other values are refused, not approximated.

7. **Reader, replay, gates 1 and 2 (items 7 and 11).** `openchuck-gcode` has the in-house reader of decision 0005 (f64 values, errors naming line and column, `%`, comments of both kinds, block delete, parameters and O-words refused by name, 4,096-character lines), the modal replay (known G and M lists as in SP-5, `Dialect::Linuxcnc` or `MakeraZ1` which also reads `G92.4 A0 S0` as dropping whole turns; arcs are read, recorded and not followed, OI-68), `static_check` (gate 1: units, distance mode, work offset before the first move, a feed on every cutting move and on every G93 move, spindle on while cutting, X, Y, Z and A limits, feed ceiling, tool change at the safe Z and with the spindle off, an end code) and `compare` (gate 2: every reached position mapped back to a tool tip by the shared kinematics and compared with the IR, A modulo whole turns, A travel without unwinds, the cut time under the controller's feed rule written separately from the post's). The fixtures are in `testdata/gcode/` (OI-46: the corrected arc lines are applied). Two fuzz targets, `gcode_reader` and `post_definition`, are in `fuzz/` and CI. **Measured on the shipped posts:** a project posts to files whose replay agrees with the IR to 0.00064 mm at the tip (three axes of 0.0005 mm rounding combine, so the tolerance is half a unit times root 3, 0.00087 mm at three decimals) and 0 degrees in A.
8. **Feeds come from the positions as written.** The controller times a move from the rounded positions in the file, not the IR's. A first version worked out F from unrounded lengths and the end-to-end test found a move 6.6 % off (a 0.009 mm move written as 0.006, 0.007). The neutral stage now rounds positions to the post's decimals first, drops moves that round onto the position before, and works out lengths and feeds from the rounded values; gate 2 does the same on the IR side. A consequence: a very short move gets a very low F (11.3 mm/min in the test), which is correct for that controller rule.
9. **Application and CLI (item 10; GC-02, GC-05, GC-11).** `Application::set_post(PostSelection)` (a built-in id or a post folder) makes regeneration post each run of consecutive operation groups from one setup to its own file (`01-setup-1.nc`), in the setup's work frame and work offset register, with the project's tool numbers and the spindle speed from the cutting data for the setup's stock material (a missing material or data is an error naming it). Each file is checked by gates 1 and 2 and the result is `Regeneration::reports`. `openchuck-cli regenerate --post <id|folder> --out <folder> [--tool-numbers keep|auto]` writes the files, prints the report and fails if any file does not pass. GC-05's other splits (per operation, per tool, one file for the project) are not built.
10. **Gate 3 (item 9; OI-47).** `tools/linuxcnc/` holds the headless XYZA configuration, tool table, driver and `run_replay.sh`; `openchuck-cli gcode-sim program.ngc report.json` compares the driver's report with the replay (every move reached within the sampling tolerance, no fault reported, same end position). The comparison is tested with reports built from the replay; **the runner has not been run against LinuxCNC** in the session that wrote it (none available). The verification plan names "the xtask replay runner"; the shell script and CLI command are what exists, so the plan's wording needs a change when this is accepted (not edited here).
11. **Reference job set (item 12; [docs/reference-jobs.md](../reference-jobs.md)).** Three generated parts (grooved cylinder, cone, sphere), one tool, helical finishing, both posts, golden files in `testdata/golden/reference/`. The jobs assume the Z1 axis 60 mm below the top of Z travel (OI-60, a placeholder in the profile: with the profile's Z of 0 gate 1 correctly fails every Z). The air-cut plan is drafted there for the operator.
12. **Tool numbers (item 13; GC-14, OI-62).** `tool_number_plan` lists the tools the operations use in order of first use with their numbers; `tool_numbering_command` confirms, renumbers in order of use from 1 or applies numbers by hand as one `Command` (one undo step), refusing a number below 1, above a given machine maximum, used twice, or held by a tool no operation uses. The CLI shows the plan and asks on a terminal, takes `--tool-numbers` otherwise, and has `tool-numbers [--auto] [--set TOOL=N] [--max N]`; changes are saved in the project. The UI dialog is slice 19. The machine's tool number range is not in the profile, so `--max` is given by hand until OI-62 is settled.

## Alternatives considered

- **Feed rule in the template:** decision 0019 item 5 chose Rust.
- **Options as an untyped table:** a mistyped key would pass through `none` checks silently; the typed struct refuses it.
- **A rotary wrap in the template (the spike's `modulo360`):** breaks a cut that crosses the seam; not offered (OI-89).
