## Decision

1. **Two steps.** This step builds slice items 1 to 4 and 6 to 10. The second step, after SP-7's result is accepted, adds helical finishing (the first entry of `Registry::builtin`), applies stock to leave (item 7), measures the chord tolerance factor and the tessellation error on that strategy (OI-08, OI-65), and closes the review items that need it: the helix pitch on a cylinder and the 0.01 mm toolpath deviation. Until then the registry is empty and the tests drive the core through a stub strategy that uses only the public API (which is also the OP-16 check).
2. **Public API of `openchuck-path`.** Plain data from `openchuck-types` in, the neutral IR out (INT-01, INT-02); no parry type appears in it. Modules: `surface` (the `SurfaceSource` port and `MeshSurface`), `cutter` (`ToolLine`, `Contact`, the drop-cutter), `rotary` (`RotaryMapping` and the A-axis functions), `stock` (`StockModel`, `AnalyticStock`, `CollisionOracle`, `AcceptAll`), `params` (schemas, values, the common parameters), `strategy` (`Strategy`, `Pass`, `CutPoint`, `StrategyInput`, `Registry`, `generate`), `assemble` (the shared services) and `parallel` (deterministic parallel maps). Errors are one `PathError` with user-worded messages; a cancelled job is `PathError::Cancelled`.
3. **`SurfaceSource` (slice item 1).** Model-frame queries: `bounds`, `project` (closest point and outward normal), `distance`, `cast_ray`, and `drop_tool` (where a tool moved along a line first touches: tip and contact, decision 0012 item 4). `drop_tool` is in the port, not only in the mesh type, because tool-centre solving is the question every strategy asks of the surface and a host with its own kernel may answer it exactly; architecture section 5.2 lists point, normal, projection, ray and distance queries, so adding "tool drop" to that list is proposed, not made (consequences). `MeshSurface` keeps its own copy of the triangles and facet normals and uses a parry `TriMesh` only as the bounding volume hierarchy: candidate triangles come from `Bvh::leaves`, closest points from `Bvh::find_best`, rays from `Bvh::cast_ray`, and every number comes from our own triangle code (Ericson's closest point, Möller and Trumbore's ray test, evaluated with `+ - * / sqrt` only). **B-rep faces are not decided here**: whether a B-rep `SurfaceSource` evaluates exactly through the kernel shim (decision 0003) or through tessellation under the IMP-02 waiver, and whether it answers `drop_tool` itself, is SP-9's question (OI-69; see "What depends on SP-9").
4. **Tool-centre solving (decision 0012 item 4).** The drop-cutter of SP-13, ported: vertex, facet and edge tests over the profile's lower envelope `h(r)` and its pieces, distances evaluated directly, golden-section search on convex pieces and sampling then refinement on concave arcs. It works for a tool line in any direction (the line's own orthonormal frame), so 4-axis poses need no rotated mesh. Candidates are the BVH leaves whose box (by its bounding sphere) comes within the cutting radius of the line, sorted by index and then visited from the highest down, stopping when none can lift the tip (valid because `h(r) >= 0`). The climb of decision 0015 item 2 and the normal-offset fast path are not built: the continuous family arrives in slice 13.
5. **Rotary mapping and A-axis management (OP-15; proposes the answer to OI-06).** `RotaryMapping { axis, sense, range }` is taken from the machine profile, and maps model points to coordinates fixed to the machine with the rotary axis through the origin (`along`, `across`, `height`) through the shared kinematics, so the rotary axis stays a parameter; `tool_line(x, a, across)` gives the line a vertical tool moves along, and `a_facing(normal)` the A at which a normal's in-plane part faces the tool (decision 0015 item 3). The policy, for the owner's agreement:
   - Within a pass A is continuous: each angle is replaced by its equivalent nearest the one before, so no step turns more than half a turn.
   - Each pass is moved by whole turns to start as near the previous pass's end as the range allows. On a limited range a pass that spans more than the range is refused, naming the pass: the axis cannot unwind in the middle of a cut, and an unwind needs a retract.
   - Links take the shorter way round, because passes start at the nearest equivalent; reversals within a pass are the strategy's, and `reversals` counts them for tests and reports.
   - A group ends with an unwind to (-180, 180] at the safe Z: a rapid to the same model tip with A changed by whole turns, as decision 0001 item 1 describes. How it is written (a real rotation, or the Z1's `G92.4 A0 S0`, decision 0007 item 4) is the post's choice in slice 6.
6. **Strategies (OP-16).** A `Strategy` has a stable registry `name`, a `label`, a `schema` and `passes`: ordered `CutPoint`s (tip, A, contact) cut without lifting. `generate` resolves the operation's values against the schema, reads the common parameters, runs the strategy and hands its passes to the shared services, so a strategy never writes links, A unwinding or durations itself. A `ParameterSchema` lists each parameter's name, label, one-sentence description and kind: a number with unit, optional minimum (inclusive or exclusive), optional maximum and optional default (none means required); a whole number with range; a flag; or a choice from a list. `resolve` refuses an unknown name, a missing required value, a wrong kind, a non-finite number, a value out of range and a choice not in the list, each naming the parameter; a whole number is accepted where a number is expected (decision 0008 item 6). The registry refuses a second strategy of the same name and an empty name.
7. **Common parameters (OP-11 core; proposes defaults, OI-70, and the stepover meaning, OI-63).** Every schema starts with them:

   | Name | Meaning | Default |
   | --- | --- | --- |
   | `tolerance` | toolpath tolerance, mm, greater than 0 | 0.01 (NFR-05) |
   | `stepover` | distance between neighbouring passes, mm, greater than 0 | none: from the tool's cutting data |
   | `stock_to_leave` | material left on the surface, mm, at least 0 | 0 |
   | `feed` | contact feed while cutting, mm/min | none: from the cutting data (speed x flutes x feed per tooth) |
   | `plunge_feed` | feed along the tool axis into material, mm/min | none: from the cutting data |
   | `retract` | links at the safe cylinder (`clearance`) or at the safe Z (`safe_z`) | `clearance` |
   | `approach_distance` | a rapid approach stops this far above the stock, mm | 1.0 (proposed) |

   The application fills `feed`, `plunge_feed` and `stepover` from the tool snapshot's cutting data for the setup's stock material when the operation leaves them out (TL-05). The feed is the material's cutting feed (spindle speed x flutes x feed per tooth), so two materials on one tool give two feeds, and the IR's durations follow from it. Three rules keep the material from being bypassed unseen (agreed by the owner, 12 Oct 2026):
   - **An operation's own value wins**, and when it differs from the material's, regeneration says so in `Regeneration::notes`, naming the value, the tool and the material ("feed 250 set on the operation overrides 400 from the cutting data of '4 mm ball' for 'oak'"). A value equal to the material's says nothing.
   - **A required value with no source is an error naming the cause**: the operation, the missing values, and whether the setup has no stock material, the tool has no cutting data for the named material (names match exactly, OI-61), or the operation has no tool. It does not fall back to another material's data.
   - **The feed is one number per material and tool.** Nothing adjusts it per move for depth of cut or engagement (that belongs to slice 14's engagement work and SIM-10); the only change to a programmed feed is the machine's feed limits (item 8), which lengthen a move and add a note. **Stepover (OI-63, proposed):** a length measured on the part's surface between neighbouring passes; each strategy's description says how: for helical finishing the axial advance per turn, for axial and indexed finishing the arc length at the selection's largest radius (so it is never exceeded). **The rest of OP-11 is not in this step.** OP-11 also asks for stepdown, lead-in and lead-out, ramping, stock to leave per selection and a retract strategy; the work breakdown places them in later slices, and nothing here builds them:

   | OP-11 parameter | Slice (work breakdown) | In this step |
   | --- | --- | --- |
   | Tolerance, stepover, feeds | 5 | Built (table above) |
   | Retract strategy | 5 (core), 14 (completes) | The two choices above only: safe cylinder or safe Z |
   | Stock to leave, per operation | 5 lists it; applied with the first strategy | Parameter only, see below |
   | Stock to leave, per selection | 12 (item 4) | Not built; needs selections (OP-02, slice 14) |
   | Lead-in and lead-out, ramping | 12 (item 5) | Not built. The IR has `LeadIn` and `LeadOut` move kinds; nothing produces them |
   | Stepdown, ramped entry | 14 (item 4, rotary roughing) | Not built. Tools carry a default stepdown (TL-05), which no operation reads yet |
   | **Helical entry** | **Not named in any slice** | **Not built; OI-71** |

   What the shared services do today is a straight plunge at the plunge feed, from the approach distance above the stock to the first cut point of each pass (item 9). That is acceptable for a finishing pass on a ball or flat tool at low depth, and it is not an entry strategy: it does not ramp, and a roughing pass or a tool that cannot plunge needs one. OP-11 closes in slice 14 (`xtask/traceability.toml`), so it is not a failing P1 requirement now.

   **Stock to leave** is a parameter now and is applied with the first strategy (item 1), by dropping a tool whose profile is grown by it; it is not silently ignored, because no strategy exists to ignore it.
8. **Contact feed and duration (OP-13).** For a cutting move with contact feed `f` (mm/min) whose contact moves from `c0` to `c1`, `duration = 60 |c1 - c0| / f` seconds and `contact_length = |c1 - c0|`; the post derives the machine feed from the move and its duration (compensated per minute, or inverse time). No move is shorter than the slowest axis allows at the machine's feed limits (rapid limits for rapids); where that lengthens a cutting move the contact feed there is below the programmed one, and a `PathNote` says so with the real value. Moves without a contact (rapids, plunges, exits) measure the tip. **Contact smoothing:** the contact positions of a pass are averaged over five points (two either side, a centred window shrinking at the ends) before the lengths are taken, because a drop onto a mesh places the contact by facet orientation (decision 0015: "about radius times the facet angle"). Measured on a helical groove (Z and A move together, the ball 3 mm off the axis, 1 degree steps), comparing the IR's contact length per move with the contact path on the exact surface followed through the machine's linear XYZA motion:

   | Mesh (along X x around) | Raw contacts, worst | Smoothed: median, 95th percentile, worst |
   | --- | --- | --- |
   | 0.05 mm x 0.5 deg | 2.45 % | 0.24 %, 1.09 %, 2.01 % |
   | 0.025 mm x 0.5 deg | | 0.24 %, 1.09 %, 1.86 % |
   | 0.025 mm x 0.25 deg | | 0.21 %, 0.75 %, 0.98 % to 1.62 % |

   The mesh's own error is below 0.0002 mm in every row, so the chord tolerance alone does not bound the feed error: the facet size does. The ±2 % limit (verification plan 4.1) is met at the finest row, which the test uses; the rule for the facet size the feed needs is OI-68, set with the tessellation measurement (OI-65) and smoothed normals (OI-67).
9. **Linking (OP-14) and the ports.** In the fixed coordinates of item 5 every link moves in the plane at the retract height above the rotary axis (the safe cylinder's radius, or the safe Z); every point of that plane is at least that far from the axis, so a link at any A and any position across the axis stays outside the safe cylinder, and the group is refused when the stock reaches beyond the retract height ("enlarge the setup's clearance"). A pass is left along the tool axis at the plunge feed until the tip is the approach distance above the stock on that line (the stock model may not know what this operation cut), then the tool rapids up to the retract height, across and round to above the next pass, rapids down to the approach distance above the stock or the first point, whichever is higher, and plunges (a straight plunge is the only entry in this step; item 7 lists lead-in, ramping and helical entry as not built). The group starts and ends at the safe Z. Every move is put to the `CollisionOracle`; a refused move is an error, since P1 has no way round. `StockModel` answers `contains`, `ray_entry` and `max_radius`; `AnalyticStock` covers cylinder and box stock and bounding-box stock once the part's bounds are known, and refuses imported stock (SET-04, P2). `AcceptAll` is the default oracle (verification plan section 5).
10. **The application (slice items 8 and 10).** `openchuck-app::operation` maps an operation to the library's plain data: the setup's part (imported and placed as the model inspection does), stock, clearance (the setup's or the machine's), the machine's rotary mapping and feed limits, the tool snapshot's profile, the parameter values, and tags holding the operation, setup and tool IDs. The library never sees the project. An operation that cannot be generated is refused with a message naming it and the missing piece (machine, setup, part, stock, tool, an unknown strategy); an operation limited to selections is refused until OP-02 (slice 14) rather than machined whole. Regeneration runs every operation in machining order and stops at the first failure; `Regeneration` gains `notes`. `Application` holds a strategy registry (`Registry::builtin()`), and `register_strategy` lets a host add its own. The `Operation` type of slice 1 already holds strategy, tool, setup, selections and parameters; no project schema change.
11. **Independent gouge and coverage checker (OP-12; architecture section 9).** In `openchuck-testkit::gouge`, ported from SP-13 and extended to any tool axis: it shares only the profile's segment data, samples the exact surface of an analytic part (never the mesh), classifies each sample against the tool's closed revolved outline by a crossing count and measures depth as the distance to the outline. `coverage` checks that every exact surface sample in a range comes within a limit of some pose's tool surface.
12. **Determinism (NFR-06).** Strategies parallelise through `parallel::map_in_order`: fixed chunks of 64 on the caller's rayon pool, results in input order; the library spawns no threads. The assembly is sequential. Within one platform the output is identical at 1, 2 and N threads (tested). Across platforms our own maths uses only correctly rounded operations, apart from the shared kinematics' `sin_cos`; parry contributes only which triangles are visited, not any number in the output. OI-64 stays open: nothing yet compares hashes across platforms.
13. **Test build profile.** The pathing tests drop tools on meshes of up to a million triangles; unoptimised they take minutes. `openchuck-path`, `openchuck-testkit`, `parry3d-f64` and `glamx` build at `opt-level = 3` in the dev profile, so the whole path test suite runs in about 20 s in a debug build. Release builds are unchanged.
14. **Example host (INT-01, INT-08; OI-30).** `crates/openchuck-path/examples/host.rs` builds a mesh, registers its own strategy and generates a toolpath through the public API alone; CI runs it with the other examples.

## Alternatives considered

- **`drop_tool` only on `MeshSurface`, not in the port.** Strategies would then need to know the surface is a mesh; a host with an exact kernel could not serve them. Kept in the port, with the architecture wording proposed below.
- **parry's own triangle queries** (`TriMesh::project_local_point`, `cast_local_ray`). They return the same answers, but our own tests keep every output number in code we control, which matters for OI-64 and decision 0012's precision findings.
- **A per-strategy linking and A-axis policy.** Every strategy would repeat it, and OP-14 and OP-15 would be tested once per strategy. Shared services, as architecture section 5.2 names them.
- **Raw mesh contacts for the contact length.** Measured above: up to 2.45 % off on a mesh whose error is below 0.0002 mm.
- **Rapid retracts straight from the cut.** The analytic stock model does not know what the operation has cut, so a rapid could pass through uncut stock; a fed exit to the approach distance above the stock costs a little time and is safe.
- **Unwinding at every link on a continuous axis.** It adds time and reversals for no gain; the Z1 drops whole turns without motion (`G92.4`), so unwinding at the end of a group is enough.

## Verification

Tests named after the requirement IDs (decision record 0004 item 14), in `crates/openchuck-path/tests/` and `crates/openchuck-app/tests/operation.rs`:

- **OP-12 (tool-centre solving and the checker):** ball and flat drops on a cylinder match their closed forms from 0 to twice the mesh error at 41 offsets, and the contact is one ball radius from the centre; ball drops on a sphere at six A angles from -725 to 359 degrees match within 0.01 mm; for ball, flat, bull-nose and V-bit tools at 54 poses off the top of a cylinder the independent checker finds no gouge beyond twice the mesh error, and finds more than 0.02 mm when every tip is lowered 0.05 mm; a ball typed as two arcs drops within 1e-9 mm of the standard ball; ray, projection and distance queries agree with the exact cylinder; generated rings pass the gouge check and full coverage at 0.02 mm, and fail coverage with one ring removed and the gouge check with the tips lowered 0.03 mm.
- **OP-13:** on a helical groove, every cutting move's contact length over its duration is the programmed feed to 1e-9, and the contact path on the exact surface under the machine's real motion is within 2 % of the programmed feed (item 8's table); a low rotary feed limit lengthens moves and adds a note.
- **OP-14:** with both retract choices no rapid enters the stock (51 samples along each rapid's machine motion), moves along or around the axis stay outside the safe cylinder, every plunge starts the approach distance above the stock and runs at the plunge feed; stock beyond the retract height is refused.
- **OP-15:** nearest-turn, continuity through the 0/360 seam, reversal counts with a dead band, whole-turn fitting into a limited range (preferring the turn nearest the previous angle, refusing a pass wider than the range and naming it), unwinding to (-180, 180]; four generated rings keep A continuous in one direction and end unwound; every IR pose maps through the machine frame and back through the independent oracle within 1e-6 mm for both A senses, with the tool axis matching; a property test of 64 random sequences finds no NaN, no step over half a turn and only whole-turn changes; the analytic stock answers rays.
- **OP-16:** a stub strategy registers, is found by name, refuses a duplicate, publishes the common parameters first, and runs; an unknown name is `UnknownStrategy`.
- **OP-11, TL-05 (materials):** a second material on the same tool gives its own feed (400 for oak, 120 for steel from 10000 rpm x 2 flutes x 0.02 mm and 6000 rpm x 2 x 0.01 mm), plunge feed and stepover; a material with no cutting data ("pine"), a name that differs in case ("Steel") and a setup with no material are each refused with a message naming the operation, the missing values, the material and the tool; setting the values on the operation is the way out; an override that differs from the material's raises one note, and an equal value raises none.
- **OP-11:** defaults fill in, a whole number reads as a number, and bad values (zero tolerance, negative stock to leave, text for a feed, an unknown retract, an unknown name, a NaN) are refused naming the parameter; through the application the feed, plunge feed and stepover come from the tool's cutting data for the setup's material, an operation's own feed wins, and a bad tolerance is refused naming it.
- **OP-01:** regeneration through the application is refused naming an unregistered strategy, then runs, keeps the tip outside the part, and gives the same toolpath after save and reopen on a different pool size; a missing tool is named; cancellation stops generation; the stub's output is identical at 1, 2 and N threads.
- **NFR-07:** empty meshes, out-of-range indices and NaN coordinates are refused with a message; degenerate triangles do not break queries; random parameter values give a result or an error.
- **INT-01:** the example host runs in CI using only the public API.

The slice 5 review checklist is not ticked: the helix pitch and the 0.01 mm deviation need helical finishing (item 1).
