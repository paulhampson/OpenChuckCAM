## Context

The export dialog wrote names fixed by the code: `NN-<setup>[-<operation or tN-tool>].<ext>` for the programs and `<project>-setup-sheet.html/.pdf` for the sheet. The owner asked for names the user can change with simple templates, kept as a per-user setting (#308, #310), and for the sheet to list the program files it goes with, what each holds, and a hash of each file's bytes (#309). Review of OUTPUT-1 (#329) found that new destinations were created at their final names (#332) and that Messages added a full stop after the last path of an export result (#331).

## Decision

1. **Template language (OI-1070, owner option A).** Fields in braces, `{{` and `}}` for literal braces. Nothing else: no code, conditions or formatting. An unknown field, an unmatched brace, `/` or `\`, an empty template or one over 200 characters is an error with a sentence under the field. The extension is not part of the template: the post gives the program's, the sheet is always `.html` and `.pdf`. Program fields: `{n}` (place in write order, two digits), `{contents}` (what today's name says after the number), `{project}`, `{machine}`, `{post}` (built-in id or folder name), `{setup}`, `{setup_no}`, `{operation}`, `{operation_no}` (number among enabled operations, as the sheet numbers them), `{tool}`, `{tool_no}`, `{date}` (`YYYY-MM-DD`, UTC, from the application clock, as the sheet's Generated line). The sheet's template may use only `{project}`, `{machine}`, `{post}` and `{date}`.
2. **Defaults keep today's names.** `{n}-{contents}` and `{project}-setup-sheet` give exactly the names written before, for every grouping; the G-code bytes do not depend on the names (GC-07, NFR-06).
3. **Clean names.** Each field value is written in today's form (lower-case ASCII letters and digits joined by hyphens, at most 40 characters). The whole stem is cleaned again with the project folder rules of #219 (`openchuck_project::new_folder::folder_name`: forbidden and control characters become `_`, invisible characters go, leading and trailing dots and spaces go, a Windows device name gets `_` in front, at most 100 characters), then the extension is added. A clean stem is unchanged.
4. **A field must have one value for its file.** `{operation}` and `{operation_no}` need one operation in the file; `{tool}` and `{tool_no}` one tool. Otherwise the export is refused, naming the file and the fix (for example "choose one file per operation, or remove {operation}"). A field is never silently empty.
5. **Hash (OI-1071, recommended option A, awaiting the owner).** The sheet gives each program file the SHA-256 of its exact bytes, all 64 hexadecimal digits, with a sentence saying how to check it with `certutil -hashfile <file> SHA256` (Windows), `shasum -a 256 <file>` (macOS) or `sha256sum <file>` (Linux). No short form. SHA-256 comes from the RustCrypto `sha2` crate 0.10.9 (MIT or Apache-2.0; score 85 in the crate selection, where it is the listed alternative to blake3; first published 2016; no agent-instruction files; pinned once in `[workspace.dependencies]`, used only by `openchuck-app`). It brings `digest`, `block-buffer`, `crypto-common`, `generic-array`, `typenum` and `cpufeatures`, all MIT or Apache-2.0. Fallback: BLAKE3 through the existing `ContentHash` (no new crate, but shops rarely have a checker for it). NFR-14 record: `docs/dependencies.md`.
6. **Naming problems block writing (OI-1072, recommended option A, awaiting the owner).** Every name, all program files and both sheets, is settled before preflight. Names are compared without letter case, as Windows and macOS do. A template problem, a field with no single value, or two names for one file is shown in red under the File names fields and in the files list (each name a dash), and disables Write G-code with the same sentence in the footer. Nothing is renamed automatically and nothing is created.
7. **Staged, no-clobber publication (#332, the owner's instruction).** Every file is first written in full, and flushed, under a uniquely claimed hidden name in the destination folder (`.openchuck-export-<process>-<n>.part`). A new destination is then published without replacing anything: a hard link to the final name, which fails if a file is there. On a file system without hard links (FAT and exFAT memory cards, some network shares) the final name is claimed exclusively as an empty file and the staged file is renamed over that claim. An approved replacement renames the staged file over the old one, never deleting it first. The staging file is removed in every case; a failure to remove it is reported. So a stopped write leaves a hidden staging file, or on the fallback an empty file, but never part of a program under its final name. 0240 item 4's no-overwrite rule is unchanged: a file that appears at a new destination after the review is kept, and the write fails with that reason. Flushing is best effort, not a durability promise; the batch is still non-atomic and stops at the first failure (0240 item 3).
8. **The setup sheet lists its program files (#309).** Before its Notes the sheet has a *Program files* section: a sentence with the count and how to check the hashes, then for each file, in the order they run, a section "File N: <name>" with its setup (number and name), size in bytes and SHA-256, and a table "File N: operations in order" with step, operation number, operation, tool (`T<n> <name>`) and tool change. A tool change is marked at a file's first tool and at each later different tool number, as the post writes `M6`. The hashes are of the frozen bytes the plan writes (the same `Regeneration` text, 0189), and the sheets are written after every program file, so a sheet is written only when every file it lists has been written. A sheet written without program files (the toolpath-only preview, or the command line's `--setup-sheet` without `--post`) says that none were written with it.
9. **Where it lives.** `openchuck-app::output_names` holds the templates, the engine and the hash; `Application::output_files(run)` gives every final name or the reason there is none, and `prepare_output` uses it, so the dialog's preview and the write share one source. `Application::set_file_name_templates` sets them. `Application::setup_sheet_file_names` now returns a `Result`. The templates are `UserSettings::file_names` (`[interface.file_names]` in `settings.toml`), additive, clamped when read; never in the project. The dialog sets them when it opens and the shell keeps a change once it is confirmed: a template being typed is a draft under 0233 and is not saved until confirmed. Replacement approval is revalidated against the templates too.
10. **Messages (#331).** The retained report text ends with the sentence "End of the export result.", so the Messages sentence ending is never added to a path line. Each path line is exactly the path.
11. **Unchanged.** The command line keeps the default names (it has no user settings; 0240 item 6). The pending-edit guard, the running-job restrictions, the GC-15 stale checks, GC-16 and skip-stock acknowledgements, the NFR-12 notice and the dialog's layout and fixed footer are as before.

## Alternatives considered

- **Templates in the project file.** Rejected by the owner's request (a per-user setting) and to avoid a schema change.
- **Readable field values** (case and spaces kept). Not chosen (OI-1070 option B): names would differ in style from the defaults, and spaces are awkward on some controllers. A user can still type literal text.
- **Automatic suffixes on clashes** (OI-1072 option B). The names would differ from the template and the preview.
- **`renameat2(RENAME_NOREPLACE)` / `MoveFileExW` without replace.** Needs `unsafe` or a platform crate; the hard link with an exclusive-claim fallback gives the same guarantee with the standard library.
- **Compute the hash from the file read back after writing.** It would hash what the file system returns, not what was written, and add a read; the plan's frozen bytes are the bytes written.
