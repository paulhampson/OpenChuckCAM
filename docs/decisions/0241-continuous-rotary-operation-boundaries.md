## Evidence

On main `1a90435654c734c05e4fa3f110c4a7f3f8e5859f`, the owner's `blisk_bad_roughing` plunge case emits 84,856 segments. After the last cut and safe retract, segment 84,855 (zero-based) moves from A593275 to A-5 at work Z50: 1,648 backward turns and 9,888 seconds in playback. Timeline samples confirm that rotation.

LinuxCNC line 84,857 is the physical modal rapid `A-5.000`. Makera line 84,856 is `G92.4 A0 S0`, which changes coordinates without physical rotation. The historical project needed an explicit diagnostic spindle speed of 13000 in a separately migrated copy to post; that is not a machining recommendation. Both current application replay checks pass. No hardware or material-removal verification is claimed.

The cause is the unconditional final `unwind_turns` in shared assembly, implementing decision 0018 item 5. Deleting it alone is insufficient: subsequent operations are generated near A0 and posting emits their starts as rapids. The new requirement regression fails on unchanged code with last cutting A1375 and terminal A-65; uninstrumented test time is 0.15 seconds.

The existing Makera command `G92.4 A0 S0` rebases the live A counter by whole turns without moving the part. For example, A593275 becomes A355: the angular datum modulo 360 is unchanged. With no XYZ words it does not reset XYZ, and its S branch does not write the saved work offsets. This is not the ordinary `G92 A0` operation of declaring the current angle to be zero. The changed numeric readout is visible to the operator; every following absolute A word must use the adjusted coordinates. This description is based on [firmware 1.1.2 source, Robot.cpp lines 666–695](https://github.com/MakeraInc/MakeraZ1Firmware/blob/b3a2e26/src/modules/robot/Robot.cpp#L666) and the earlier recorded air-cut evidence, not a new hardware test.

Requirement tests added after acceptance exposed a boundary mismatch in both posting and replay: firmware only reduces A when its magnitude is greater than 360, whereas both software paths also reduced exactly +360 and -360 to zero. For example, after resetting at A360, writing A10 would request -350 degrees rather than the intended +10. Both paths must retain the boundary value and adjust the following command to A370. The tests failed before the correction; the existing replay could not detect this because it shared the same wrong assumption as the post.

## Accepted rule

1. **Scope and cutting.** Apply one boundary policy to every strategy using shared assembly, including legacy Facing. Preserve cutting geometry, within-pass unwrapped rotary travel, feeds, Facing defaults, size semantics and equal-depth layers. Never reduce every cutting A coordinate modulo 360. A whole-turn offset applied consistently to a complete group preserves its internal rotary travel.

2. **Continuous-axis end.** Keep the existing leave and safe retract. Do not append physical rotary travel merely to return A to a canonical interval. At an operation/program end with no required destination orientation, retain the final cutting orientation and accumulated physical A. Required machine/post safe-position and footer actions remain.

3. **Operation links and tool changes.** For consecutive operations in the same setup and program, place the next group by a constant whole-turn offset nearest the preceding physical A, subject to all machine limits and clearance checks. Shift its start and every subsequent pose consistently. Keep tool changes at their required safe positions with existing spindle-stop behavior. Account for both tools' envelopes when establishing a tool-change link. An explicit required orientation takes precedence over a free equivalent-angle choice.

4. **Equivalent-angle ties and limits.** Compare valid destinations by absolute rotary travel. For an exact half-turn tie with both directions valid, choose positive machine A travel; if only one is valid, choose it. This tie rule applies to boundary destination selection, not a reinterpretation of cutting moves. Limited axes retain range-constrained pass fitting; any whole-group offset must keep every pose in range. Do not remove a limit-required reposition or introduce a canonical return outside the range. Refuse an impossible connection rather than wrap through a limit or change cutting geometry.

5. **Clearance and visibility.** Establish the connection at clearance sufficient for the stock, part, held regions, tabs and configured tool/fixture geometry, respecting linear travel limits. Validate the complete connecting motion; endpoints and Warn-only sampling are insufficient. Refuse if clearance cannot be established. Include generated physical inter-operation moves and their durations in the assembled sequence used by playback, simulation and posting. Do not hide a real link in the post.

6. **Controller coordinate resets.** Keep a non-moving coordinate reset distinct from physical motion. The Makera post may retain its supported whole-turn reset after safe retract at group boundaries, including the final group, to avoid carrying accumulated coordinates across operations. It has no rotary-motion duration and must not animate an unwind. Track its coordinate offset through all subsequent A words and replay comparisons. Match firmware 1.1.2 semantics, including signed remainders and the exact positive/negative 360-degree boundary. A rotate-only post must not substitute a physical full-turn return for this bookkeeping action. Do not introduce a cable/coolant unwind setting or new in-cut resets.

7. **Programs, caches and standalone use.** Assemble links in actual machining order within each setup/program. Never reorder operations to reduce rotary travel. Reassemble each exported file from context-independent groups: an operation/tool split must not inherit a previous file's connecting move or controller offset. Keep cached operation geometry independent of predecessor placement; derive contextual offsets and links without mutating cached paths. The first move from an unknown controller position remains outside generated inter-operation motion; do not claim to optimise that unknown move. Library hosts need the same documented assembly contract as the application.

8. **Output and compatibility.** This intentionally changes physical unwind/link output, some subsequent A words and duration comments across affected strategies, including legacy Facing. It is the owner's accepted narrow exception to legacy Facing byte identity; it does not authorise changing its cuts or planning. Required post headers, footers, work offsets and tool-change commands remain. Ramp-option-off identity is checked with this same rotary policy and software version. No project-format change is required by this record. Any necessary public library API break follows decision 0048 with a workspace minor bump and host migration notes.

## Alternatives and limitations

Roughing-only behavior leaves the same defect in finishing/Facing and duplicates boundary policy. Removing only the final segment moves the unwind to the next operation. Modulo-normalising every A changes cutting travel. Removing all controller resets can worsen coordinate magnitude/precision on the Z1.

Nearest-equivalent placement changes posted numbers and demands careful offset, cache and file-boundary handling. Retaining group-boundary resets does not solve precision within an already very long cut. Hardware tool-change/footer behavior remains subject to OI-41 and existing machine verification; replay currently does not simulate G28 homing/parking. This work neither waives those limits nor verifies G-code for machining. If implementation requires a further machining-policy change, return it to the owner before proceeding.
