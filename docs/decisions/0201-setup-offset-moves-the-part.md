# 0201: The setup's offset along X moves the part, and the model's placement is shared (lane SETUPPOS; issues #175 and #181)

- **Status:** proposed (lane SETUPPOS, 21 Oct 2026). Item 1 is the owner's decision on issue #175 (option C), settled with the coordinator on 21 Oct 2026; the rest is the lane's proposal and waits for the owner's acceptance.
- **What it amends:** [decision 0011](0011-slice-3-machine-stock-setup.md) items 1 and 2 (the machine frame and the meaning of `part_offset`), and the interface specification's sections 6 and 11.3 (edited with this record). No requirement changes: SET-05 already asks to "position the part relative to the rotary centreline and work coordinate system". The architecture says nothing about the frames' details (section 4, step 2, "part position"), so it is not changed.
- **Date:** 21 Oct 2026.
- **Open items:** none new. OI-780 (record 0202) is the lane's question on what the head and tail tab buttons make; it does not touch this record.

## Context

Trial feedback F-20 (issue #175): the Setup inspector's "Offset along X" had no effect, not on the Setup diagram, the 3D view, the simulation, the toolpaths or the G-code. The owner also found that it overlapped the Model step's placement steps, which can translate the part too (F-25, issue #181, asks for a placement row under the model in the tree).

The lane traced the value. Decision 0011 defined `part_offset` as where the model origin lies on the machine, measured along the rotary axis from the profile's rotary reference point (the chuck face, say). The stock, the work zero and (later, decision 0041) the tabs were all given in the model frame, fixed to the part. So the offset moved the part, the stock, the tabs and the work zero together: it changed only machine coordinates, which are used by the travel checks and by what the work offset register should hold (`expected_work_offset`). Toolpaths are written in the model frame and the G-code in the work frame, so neither could change, and nothing in the diagram or the view moved. That was consistent, but it is not what a user expects, and it duplicated the placement steps without saying so.

Requirements: SET-05 (P1), SET-06, UI-03, UI-06, GC-07 and NFR-06 (deterministic output), NFR-12 (the user verifies the G-code). Records read: 0004 item 5, 0010 (placement steps), 0011, 0041 and 0045 (workholding data), 0129 (the Setup panes), 0123 (OI-366, the Part position section), 0160 and 0161 (held regions).

## Decision

1. **Two positions with clear roles (the owner's option C).**
   - The **Model step's placement** (the placement steps, IMP-05) is the import placement: it puts the model on the rotary axis and is shared by every setup.
   - The **setup's Offset along X** is the per-setup position: it moves the part along the rotary axis, after the placement, against the stock, the held regions and tabs and the work zero, which stay where they are. It reaches the Setup diagram, the 3D view, the toolpaths, the simulation, the checks and the G-code.
   - The **combined position** is shown read-only in the Part position section.
   - The interface explains the difference in plain words (item 5).
2. **The setup's frame (amends decision 0011 items 1 and 2).** A setup's model frame keeps its X axis on the rotary axis, and its origin is now always the machine's rotary reference point: the machine frame is `RotaryFrame::of_profile` for every setup. The stock, the held regions and tabs, the work zero and the toolpaths are given in it. The part is put in it by its placement steps and then moved along X by the setup's `part_offset` (`SetupFrame::place_part`, `PartExtent::in_setup`). `expected_work_offset` is the rotary reference point plus the work zero's X; the part offset no longer changes it. `RotaryFrame::machine(profile, setup)`, which moved the frame by the offset, is removed (a breaking change of `openchuck-types`; library family 0.15.0, decision 0048).
3. **One place reads a setup's part.** `openchuck-app` places a setup's part in one function (`model::setup_part`, and `PlacedPart::in_setup` for a part already read): generation (mesh and B-rep, so selections, swarf and edges follow), the scene and therefore the Setup diagram, the workholding checks and default tabs, the simulation's comparison target, the stock playback's deviation colours and the setup checks (`check_setups` and the overview). A zero offset (of either sign) returns the part untouched, so a project without an offset keeps its toolpaths and G-code byte for byte (GC-07).
4. **Older projects keep their output (project schema 17).** Before schema 17 the offset moved the part, the stock, the tabs and the work zero together. The 16 to 17 step moves an older setup's cylinder or box stock, its tabs and its work zero along X by its offset, so it machines exactly as before, at the same machine positions. Stock that follows the part (the bounding box plus an offset) needs no change, and the held regions are measured from the stock's ends. A setup with no offset is unchanged. Schema 16 is lane BUG-SPINDLE's; this branch passes through a step that changes only the number until that lane's real step replaces it. A fixture (`tests/fixtures/schema-15-offset`) covers the step, with whole numbers and a missing work offset table.
5. **The interface (specification sections 11.3 and 11.2, edited).**
   - **Offset along X**, tooltip: "Moves the part along the rotary axis in this setup only, from where the Model step's placement puts it. The stock, the held regions and tabs and the work zero stay where they are, so the toolpaths and the G-code move with the part. Use it to choose where the part sits in the stock. To move the part in every setup, change the placement in the Model step instead."
   - **Position**, a read-only row under it: "X 12.500 to 42.500 mm (placement X 0.000 to 30.000 + offset 12.500 mm)", with the tooltip "Where the part is along the rotary axis in this setup: the Model step's placement plus this setup's Offset along X, measured from the machine's rotary reference point (the chuck face). Read only." The extent comes from the project checks (`Overview::model_extent`), so it shows as soon as the model has been read.
   - **Zero at X**, tooltip: "Where the work zero (the program's X0) lies on the rotary axis, measured from the machine's rotary reference point, like the stock. It stays put when the part is moved with Offset along X."
   - **Model step, Placement section**: a muted line, "The placement puts the model on the rotary axis and is shared by every setup. To move the part along the axis in one setup only, use that setup's Offset along X (Setup step, Part position)."
   - The setup sheet's "Part offset" and the command line's `setup` print say "part moved N mm along the rotary axis from where its placement puts it"; the CLI's `--part-offset` help says the same.
6. **The model's child rows in the tree (issue #181).** Section 6 of the specification already lists "child rows for its placement and mesh check" under each model; they were not built. Each model now has a **Placement** row (chip: "as in file", "1 step" or "N steps"; tooltip the Placement line of item 5) and a **Mesh check** row (the model's status mark). Clicking one selects the model and opens and scrolls to that section of its inspector. The issue's "Positioning" row is the Placement row: under item 1 the model's own position is its placement, and the per-setup position is the setup's Part position row, which already exists. The rows follow the tree's rules (marks, selection highlight); keyboard access is the tree's, as for the setup's child rows.

## Alternatives considered

- **Option A, the placement is the only position (remove Offset along X).** Simple, but every setup would then share one position along the axis, and a second setup (SET-07, P2) usually holds the part elsewhere. The owner chose C.
- **Option B, the offset is the only position (no translation step along X in the placement).** Placement steps are the import's general tool (IMP-05; rotate, mirror, centre); taking X out of translation would be a special case, and a part needs its placement before any setup exists.
- **Keep decision 0011's meaning and show it.** The offset would have moved the drawing's machine features (the chuck face, the travel limits), not the part against the stock, and the toolpaths would never change. It does not meet "wired through the toolpaths and G-code".
- **Move the stock and work zero by the offset as well (the old meaning) and leave old projects alone.** Not consistent with item 1; the migration (item 4) keeps every old project's output instead.
- **Read the work zero as fixed to the part.** The G-code would never change with the offset, which the owner's decision rules out; the work zero is set on the machine against the stock or the chuck, which stay put.
- **Apply the offset where each consumer reads the part.** Rejected: one function (item 3) means no consumer can miss it.

## Consequences

- `openchuck-types` (breaking): `RotaryFrame::machine` removed (use `RotaryFrame::of_profile`); `SetupFrame::place_part`, `SetupFrame::moves_part` and `PartExtent::in_setup` added; `expected_work_offset` no longer adds the part offset; `SetupCheck::part` is the part as the setup places it. Library family 0.15.0 with a changelog entry.
- `openchuck-project`: project schema 17 (claimed in the work breakdown), the 16 to 17 step and fixture; schema 16 passed through for lane BUG-SPINDLE.
- `openchuck-app`: `model::setup_part`, `setup_mesh`, `mesh_in_setup`, `PlacedPart::in_setup`; `setup_form::PLACEMENT_EXPLAINED`, `PART_OFFSET_EXPLAINED`, `POSITION_EXPLAINED`, `position_on_axis`; `Overview::model_extent`. The setup panes' Z+ travel limit no longer depends on the offset (it never did in practice: the offset is along the axis).
- `openchuck-ui`: the Position row; the Placement line; the model's child rows; the workholding facts are worked out again when the offset changes.
- G-code: unchanged for every project without an offset (the golden files are unchanged); an older project with an offset is migrated to the same output (item 4).
