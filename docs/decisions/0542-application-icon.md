# 0542: The application icon (lane ICON)

- **Status:** accepted by the project owner on 7 Nov 2026, relayed by the coordinator (decision 0049), as written. Proposed by lane ICON on 7 Nov 2026. It records the owner's choices of 7 Nov 2026, relayed by the coordinator: the design (concept A, variation A6 in the one-colour palette C3) and its colour on each surface (option d), embedding the Windows program icon with no new dependency (option 1), and rendering the PNGs with `resvg` in `xtask` only (option 1).
- **What it amends:** nothing in the requirements or the architecture. It adds files to `openchuck-ui` (its assets, a build script and one module), a command to `xtask`, a dependency to `xtask` only, the user guide's favicon and logo, and the logo at the top of the repository README. No library API change and no project schema change.
- **Date:** 7 Nov 2026.
- **Open items:** closes OI-2106 (OpenChuckCAM has no icon of its own on any platform, raised with [decision 0541](0541-macos-app-bundle-linux-glibc-floor-and-release-tags.md)). Raises OI-2109 (the owner's check on Windows, issue #590). The macOS Dock is checked by CI only (issue #588).

## Context

Until now the program had no icon of its own:

- the window and taskbar showed eframe's default icon, the egui logo, which the owner will not ship;
- the Windows `.exe` embedded no icon, so Explorer showed the generic one;
- the macOS bundle (lane PACKAGING, decision 0541) had none of its own (OI-2106).

No requirement names an icon; the work is release work for milestone 2026.1-alpha, asked for by the owner through OI-2106.

## Decision

1. **The design.** The owner chose variation A6 of concept A in the one-colour palette C3, from three concepts and one refinement round. The sheets are on the throwaway branch `claude/icon-concepts`, never merged: `icon-concepts/contact-sheet.png`, `icon-concepts/refine/contact-sheet-refine.png` with the scores against the logo tests in `icon-concepts/refine/NOTES.md`, and `icon-concepts/surfaces/surfaces-sheet.png`.
   The mark shows a chuck seen end-on: three jaws around round stock, inside an arrow for the A-axis rotation. It is drawn on a 512-unit canvas with a 32-unit grid, so its ring, jaws and gaps land on whole pixels at 16 px. It does not resemble the egui logo, a white hexagon with a four-part cross; four jaws were not offered because they would.
   **Colour on each surface (option d).** A tile-less mark in one fixed colour cannot be seen everywhere. Windows draws a program's icon as it is on a taskbar or folder background of the user's theme, and its `.exe` icon has no light or dark version: ink on a dark taskbar is 1.0:1. macOS 26 puts an application icon that does not fill a rounded tile inside a grey tile of its own. So:
   - every application icon (the Windows program file, window and taskbar, the Linux window, the macOS Dock and bundle) is the mark in white (`#F2F4F7`) on a near-black rounded tile (`#1B1F24`, rim `#3A4048`), 15.0:1;
   - the user guide's favicon and any one-colour use show the mark without a tile, in ink (`#1B1F24`) on light backgrounds and white on dark ones. The favicon switches by itself through `prefers-color-scheme` in an SVG.
   The other options were one fixed mid-tone without a tile (about 2.8 to 4.3:1, weak everywhere), ink or white by surface (impossible for the program file) and a tile on macOS only (Windows and Linux would still need one fixed colour).
2. **Licence.** The icon is original work, drawn for the project with no third-party artwork or fonts, and licensed under the project's licence, AGPL-3.0-or-later (NFR-10). The SVG carries the SPDX identifier; `apps/openchuck-ui/assets/icon/README.md` gives the licence of the binary files.
3. **Files.** `apps/openchuck-ui/assets/icon/` holds `icon.svg` (the master of the application icon), `mark-ink.svg` and `mark-white.svg` (the tile-less mark), `favicon-adaptive.svg`, `icon-512.png`, `icon-256.png`, `icon-128.png`, `icon-64.png`, `icon-48.png`, `icon-32.png`, `icon-16.png`, `icon.ico` (256, 64, 48, 32 and 16), `icon.res` and the README with the licence and the colours and their contrast. The folder is in the UI crate, beside its fonts, because the window icon is embedded with `include_bytes!` and architecture section 12 has no top-level assets folder (agreed with lane PACKAGING through the coordinator).
4. **Generation.** `cargo xtask icon` writes every generated file from `icon.svg` and `favicon-adaptive.svg`; `cargo xtask icon --check` writes nothing and lists the files that differ: each PNG may differ from a fresh rendering by at most 2 in 255 in any channel, because the renderer's anti-aliasing can differ by a step between x86-64 and ARM processors (the workspace tests run on both); the favicon SVG, `icon.ico` and `icon.res` must match byte for byte, the last two against the committed PNGs they are made of. The rendering uses `resvg` 0.49.0 (Apache-2.0 OR MIT), a dependency of `xtask` only, never of a product crate (owner's choice, option 1; NFR-14 row in `docs/dependencies.md`). The generated files are committed, so building the application needs no renderer and no network.
5. **Window and taskbar icon (Windows and Linux).** `openchuck-ui` embeds `icon-256.png` and passes it to `ViewportBuilder::with_icon` for the application and the benchmark windows (`src/app_icon.rs`). It decodes with `eframe::icon_data::from_png_bytes`, which uses the `image` crate eframe already brings, so no dependency is added. If the PNG ever failed to decode, the window would keep the default icon rather than fail to open (NFR-07).
6. **Windows program icon.** `cargo xtask icon` also writes `icon.res`, a compiled Windows resource (one `RT_GROUP_ICON` of the five PNG-compressed `RT_ICON` images), and `apps/openchuck-ui/build.rs` passes it to the linker when the target is `windows-msvc`. The MSVC linker accepts a `.res` file as an input, so no resource compiler and no new crate are needed (owner's choice, option 1, over the `winresource` and `embed-resource` crates). On a `windows-gnu` target the build script warns that the program gets no embedded icon; CI and the release archives use `x86_64-pc-windows-msvc`.
7. **macOS bundle.** Lane PACKAGING's `cargo xtask macos-app` reads `apps/openchuck-ui/assets/icon/icon-512.png` when it exists (decision 0541); this lane does not edit PACKAGING's files.
8. **User guide favicon.** `cargo xtask icon` copies `favicon-adaptive.svg` to `user-docs/favicon/favicon.svg` and writes `favicon.png` beside it, the application icon at 32 pixels, for browsers that do not take SVG favicons. `user-docs/tools/build.py` copies both to the root of each built guide, and the page template links them. They are kept out of `user-docs/theme/` because mdBook would copy them from there under a hashed name. `user-docs/tools/assemble.py` also copies them to the site's root, and links them from the redirect, versions and not-found pages. Nothing is requested from another site (NFR-19).
9. **Logo in the README and the user guide** (scope added by the owner on 7 Nov 2026, relayed). The repository `README.md` opens with the tile-less mark, 96 pixels, in a `<picture>`: `mark-white.svg` when the reader's colour scheme is dark, `mark-ink.svg` otherwise. The user guide's header shows the mark beside its title, as an inline SVG in the page template. It is drawn in the text colour, so it follows the guide's light and dark themes, and it is hidden from screen readers because the title beside it names the guide. It is inline, not an `<img>`, because the guide's check wants every image in a captioned figure. It is a copy of `mark-ink.svg`'s shapes, so a change to the mark is made there too (`assets/icon/README.md`).
10. **Owner items** (OI-2109):
    - the native check of the icon (see Open items);
    - the GitHub social preview, uploaded in the repository's Settings, Social preview: `icon-concepts/social/social-preview-1280x640.png` on the throwaway branch (the white mark and the name in IBM Plex Sans, the interface's OFL font, on the near-black colour);
    - the repository's or the owner's avatar, if wanted: `icon-512.png`.

## Verification

Done in the lane's container (Linux, x86_64) on branch `claude/lane-icon` at commit `27cdfac` (the code and assets; later commits change documents only), pull request #585.

- `cargo test -p xtask icon`: the renderer gives the asked size, scales the drawing and is deterministic; invalid input is an error, not a panic (NFR-07); the ICO directory has one entry per PNG with the right size bytes, length and offset; the RES file holds the empty first resource, one `RT_ICON` per PNG and one group whose entries match; `generate` makes every committed size; `icon_same_image_allows_an_anti_aliasing_step_but_not_a_changed_drawing` checks the tolerance; `icon_the_bundle_takes_the_committed_512_pixel_png` checks that `cargo xtask macos-app` (decision 0541) accepts the committed `icon-512.png`; and `icon_committed_files_match_the_svg` checks that every committed file is what the SVG gives.
- `cargo test -p openchuck-ui icon`: `icon_window_icon_is_the_embedded_256_pixel_image`, `icon_window_viewport_carries_the_icon` and `icon_native_options_carry_the_application_icon` (the window the application and the benchmark open carries the 256 by 256 icon).
- `icon.res` was linked with `rust-lld -flavor link /dll /noentry /machine:x64` into a test DLL, and `pefile` read back five `RT_ICON` resources of the PNG sizes and one `RT_GROUP_ICON` (language 1033), so the linker accepts the file. ImageMagick's `identify` reads `icon.ico` as five PNG images of 256, 64, 48, 32 and 16 pixels.
- `python3 -m unittest discover -s user-docs/tools/tests` (66 tests, including `test_the_favicons_are_copied_to_the_site_root`, `test_the_template_links_the_copied_favicons`, `test_the_site_pages_carry_the_guide_favicon` and `test_a_guide_without_a_favicon_still_assembles`). The guide was built with mdBook 0.5.4 through `build.py`, assembled with `assemble.py` and checked with `check.py`: 0 errors. The one warning, that the tutorial screenshots' capture commit is not in this shallow checkout, is not from this change. Screenshots of the header show the logo in the light and dark themes. lychee and the Nu HTML Checker were not run here; the pull request's `docs` job runs them.
- `cargo nextest run -p xtask -p openchuck-ui`: 814 tests passed (every icon test under 1 s uninstrumented); `cargo clippy -p xtask -p openchuck-ui --all-targets -- -D warnings`, `cargo fmt --all`, and `cargo xtask deps`, `licences`, `records` and `trace` (105 of 105 P1 requirements have tests) passed. Coverage: `openchuck-ui` is report-only and `xtask` is not in `xtask/coverage.toml`.
- Not verified here: the icon on a real Windows title bar, taskbar and Explorer, which cannot be seen headless. The Windows check is OI-2109 (issue #590). The macOS Dock is not checked by hand: the owner has no Mac, so it is checked by CI only (issue #588). The Windows CI build links the resource on every pull request.
