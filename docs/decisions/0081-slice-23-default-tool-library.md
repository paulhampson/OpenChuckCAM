## Decision

1. **Source and licence of the Makera data (OI-269).** The owner named `MakeraInc/CarveraProfiles`. Read at commit `de08a657bdc9c230a094dbdba792acd70bfcdf32` (5 Aug 2026, shallow clone). It holds post-processors and tool files for many CAM programs (FreeCAD `.fctb` bit files, Fusion 360 `.tools` files, VCarve, Kiri:Moto and DeskProto files), a `Makera_Z1.fcm` machine file and Z1 design files. **It has no licence file** (no `LICENSE`, `COPYING` or `NOTICE`) and its README states no licence. The only licence text in it is on the post-processor code: Autodesk's copyright line on `Carvera.cps`, and sliptonic's LGPL-2.1 notice on the FreeCAD posts. **None of the tool data files carries a licence.** With no grant the data is under its owner's default copyright, so it is not clear that it may be embedded in an AGPL project (NFR-10). **Nothing was copied from the repository and no Makera value was re-keyed from it.** The owner then chose the route in item 8. Routes put to the owner: (a) ask Makera for a written grant; (b) write the Z1 tools from Makera's public product specifications with a recorded source per tool, citing the repository as a reference only (OI-269's own fallback); (c) re-key the facts by hand, which the lane will not do without the owner's say-so.
2. **Draft issue text for route (a), not sent.** "OpenChuckCAM is an AGPL-3.0 CAM program for 4-axis machining. We would like to ship the Makera Z1 tool list (types, dimensions and tool numbers) from `CarveraProfiles` as the default tool library. The repository has no licence file. Could you add one, or confirm in writing that the tool files may be copied and redistributed under the AGPL-3.0, with attribution if you wish?"
3. **Standard tools (OI-268), approved by the owner** (17 Oct 2026, in the orchestrator's session, relayed to lane TL by the orchestrator, decision 0049). The owner has 3.175 mm and 6 mm collets, which matches the shank sizes. 23 tools, all metric, defined for this project: nominal dimensions of a generic tool of each type, not taken from any vendor catalogue. Flat 1, 2, 3, 3.175, 4, 6 mm; ball 1, 2, 3, 3.175, 6 mm; bull-nose 3 mm r0.5 and 6 mm r1; tapered ball r0.25 on a 3.175 mm tool at 5 and 10 degree half angle; V-bit 30, 60 and 90 degree (6 mm, 0.1 mm tip); 90 degree chamfer (6 mm, 1 mm tip); drill 1, 2, 3 and 5 mm at 118 degrees. Shank equals diameter from 3 mm up, 3.175 mm below that; two flutes except the V-bits (one). The standard tools' own material is left unset: no source. The owner may adjust the list or the shank sizes later. The one list is `STANDARD` in `defaults.rs`, over files in `defaults/tools/`, so a change is a file edit and one line.
4. **Cutting data (OI-270), owner-decided** (17 Oct 2026, relayed to lane TL by the orchestrator, decision 0049): the standard tools ship none; the Z1 tools ship the Makera reference values for the bits the rule in item 10 gives. See item 10.
5. **Delivery.** The files are in `crates/openchuck-project/defaults/tools/` (standard tools), `defaults/z1/` (Makera Z1 tools) and `defaults/tool-sets/` (the Z1 tool set), and embedded with `include_str!` (NFR-09, no network). `ToolLibrary::install_defaults` writes them into the user's library on first run in the existing file format (no schema change, no schema number claimed); `openchuck_app::library::install_default_tools_in_default_folder` runs it, and the UI calls it at start-up, reporting a failure without stopping. The command line does not install.
6. **Update policy (OI-271), owner-decided** (17 Oct 2026, relayed to lane TL by the orchestrator, decision 0049: option A, the explicit-action policy). A ledger file `.installed-defaults` in the library folder lists the IDs of the defaults installed. A listed ID is never installed again (a deleted tool stays deleted); an installed tool is never rewritten (an edited tool stays as edited); an ID the ledger does not know is installed (a later release adds a default); a default already in the library, for example by import, is recorded and not rewritten; a damaged ledger can only cause a missing default to be reinstalled, never an overwrite. **Chosen option (explicit action):** an installed default is never changed silently; an unedited tool is not replaced when a new version ships. The other option, silent update of an unedited default (needs a content hash in the ledger), was not chosen and is not built. A changed default reaches the user only through the explicit action `ToolLibrary::restore_defaults` ("Restore default tools"), which installs every default the library does not hold and never overwrites an existing file. Not built: a UI button for it, and delivery of a changed version of a tool that is still present (it would need a new ID or a copy beside it; to decide when a default first changes). The ledger does not end in `.toml`, so the library does not read it as a tool. A default tool set is ledgered by machine name and treated the same way: installed only when the library has no tool set for that machine and holds every tool it names, never overwritten, and not restored by a run.
7. **Room for further sets.** The embedded lists are `STANDARD`, `Z1` and `TOOL_SETS` in `defaults.rs`; another set of tools or another machine's tool set is added as files and one line, with no format change.

10. **Cutting data on the Z1 tools (OI-270), owner-decided** (17 Oct 2026, relayed to lane TL by the orchestrator, decision 0049). ## Alternatives considered

- **Copying the Makera files now.** Rejected: no licence (item 1).
- **Marking defaults with a flag inside the tool file.** Would change the tool file format and need a schema number; a ledger beside the library does not.
- **A label on the cutting data ("not verified on the Z1").** The owner decided against it: feeds and speeds are tied to the tool type, not the machine.
- **Reinstalling a deleted default on update.** Rejected by TL-12.

## Verification

Tests named after the requirement IDs in `crates/openchuck-project/tests/default_tools.rs` and `crates/openchuck-app/tests/library.rs`: every default validates and has a unique ID, and the standard tools have no cutting data; every type in TL-02 and TL-03 is present; each shape equals its closed-form silhouette at 301 radii within 1e-9 mm; a first run installs the 77 tools (23 standard, 54 Z1) and the Z1 tool set and a second installs nothing; the Z1 tool numbers are unique, in range 101 to 504 and match each tool's category (shanks 3.175, 4 or 6 mm); the Z1 tools are carbide; cutting data exists exactly for the 35 bits and the materials item 10 gives, each entry validates, reproduces the page's rpm, plunge feed and depth of cut and, through the feed per tooth, its feed, and carries the stepover its source states (the conflicts are listed in item 10) (a reference table of the page values is a test data file); an edited default is kept; a deleted default is not restored; an edited or deleted tool set is not overwritten or restored by a run, and the explicit restore brings it back over nothing; a new default is installed; a damaged ledger overwrites nothing; restore reinstalls a deleted default and touches nothing present; installing needs no source tree or network.

## Consequences

- The TL-12 wording now says the Z1 tools come from Makera's published tool pages with tool numbers assigned by the project ([decision 0078](0078-tl12-wording-project-assigned-tool-numbers.md)). TL-12 is met for the standard tools and the Makera Z1 tools and tool set, except what is still open: thread mills as a P2 item (OI-281) and the Z1 tool numbers being ours (OI-280, the owner may replace them). Slice 23 stays open in the work breakdown for those.
- No dependency, no schema number, no change to `requirements.md` or `architecture.md`. `openchuck-project` gains a public API (`InstallReport`, `LEDGER_FILE`, `default_tools`, `standard_tools`, `z1_tools`, `default_tool_sets`, `ToolLibrary::install_defaults`, `ToolLibrary::restore_defaults`), a minor addition.
