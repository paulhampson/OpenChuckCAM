## Context

The release workflow's `library` job runs `cargo publish --dry-run` on the four library crates, and it was red by design (decision 0091 item 4, OI-302): `openchuck-post` embedded the built-in posts from `posts/` at the repository root, outside the crate, and `openchuck-path` and `openchuck-post` dev-depended on the unpublished `openchuck-testkit` through a workspace entry with a version, which cargo keeps in a published manifest. [Decision 0103](0103-built-in-posts-live-in-the-post-crate.md) (accepted 17 Oct 2026) put the built-in posts inside the crate and already changed architecture section 12's table to `crates/openchuck-post/posts/`. Decision 0091 item 4 left real publishing, the name reservation and the token to this lane (OI-303), and the owner asked for a publish step gated on a manual input and a repository secret, publishing nothing in this change.

Requirements touched: INT-01 (the engine as a standalone library), INT-03 (post-processing on its own), INT-07 (a versioned API with a changelog), INT-08 (documentation; the README is the crate's page), INT-09 and NFR-10 (AGPL, the SPDX licence on each crate), NFR-12 (the G-code notice), NFR-14 (no new dependency). Architecture section 12 ("Release tooling", "Names and tags").

## Decision (proposed; items 6 and 7 decided by the owner, relayed)

1. **The built-in posts move into the crate,** as decision 0103 says: `git mv posts crates/openchuck-post/posts`, so their history is kept. `include_str!` reads `../posts/...`. Every reference follows: the `.gitattributes` line, the CI and end-to-end path filters (the `crates/**` and `crates/openchuck-post/**` filters now cover them, so the `posts/**` lines go), the fuzz corpus step in CI and the nightly workflow, the `openchuck-post` tests (a `posts_path` helper beside the crate), the `openchuck-app` tests and the `openchuck-ui` export panel test, the build script's watch list (`crates/` already covers the posts), the fuzz target's comment, the READMEs, `docs/fuzzing.md` and the verification plan's path-filter sentence. The test that keeps the two posts' shared template identical (`req_gc_09_req_gc_10_the_two_posts_share_one_template`) is kept. The Docker LinuxCNC image and the replay tools read only `testdata/golden/`, so they need no change. No user-facing behaviour changes.
2. **The testkit dev-dependency is stripped from published manifests,** in the way cargo documents: the workspace entry `openchuck-testkit` is a path with no version, so cargo leaves the dev-dependency out when it packages a crate. Every other project entry keeps its version. The packaged `openchuck-path` and `openchuck-post` manifests were checked to hold no `openchuck-testkit`.
3. **Each library crate has an `include` list:** `src/`, `README.md`, `CHANGELOG.md`, and `examples/` (`openchuck-types`, `openchuck-path`) or `posts/` (`openchuck-post`). The tests stay out of the packages: they read the repository's `testdata/` and the unpublished testkit, so they could not build from a package. Cargo prints "ignoring test ... not included in the published package" for each, which is expected. Keywords and categories are added where missing (item 7). The READMEs link the repository by its URL (a relative link breaks on crates.io), and the `openchuck-gcode` and `openchuck-post` READMEs and crate documentation drop status lines from slice 6 that no longer held.
4. **`cargo xtask publish`** (`xtask/src/publish.rs`) checks every pull request, without a build, that each library crate is publishable: not `publish = false`; a description; `license = "AGPL-3.0-or-later"`; a repository; a readme inside the crate and in its `include` list; a `rust-version`; 1 to 5 keywords that crates.io accepts and 1 to 5 categories; an `include` list; every file its sources embed with `include_str!` or `include_bytes!` inside the crate and in the list; every normal or build path dependency with a version; no normal or build dependency on a crate that is never published; and no dev-dependency on such a crate that carries a version. It is part of `cargo xtask all` and a step of CI's fast checks. Its tests break each rule in turn, include both causes of OI-302, and check the real workspace. CI's "Each library alone" job also runs `cargo publish --dry-run --locked` on the four crates (on Linux only: packaging does not depend on the platform), so a regression shows on the pull request, not first at a release.
5. **The release workflow can publish the family, only when asked.** A new `publish_crates` input (default off) and a `publish-crates` job: it runs only for a manual run on a `lib-v` tag with `dry_run` unticked and `publish_crates` ticked, after the release gate and the publish dry run pass, in a GitHub environment `crates-io` (where the owner can require a reviewer), and only with the `CARGO_REGISTRY_TOKEN` secret, which the owner creates; without it the job fails and publishes nothing. `plan` refuses `publish_crates` on any other run before the gate. A `lib-v` tag push alone never publishes a crate. The job publishes with plain `cargo publish --locked`, crate by crate in dependency order (`openchuck-types`, then `openchuck-gcode`, `openchuck-path`, `openchuck-post`), and skips a crate already on crates.io at that version, so a run that stopped part way can run again. This amends decision 0091 item 4 ("the workflow cannot publish a crate") and the condition the orchestrator set on 17 Oct 2026. [docs/releasing.md](../releasing.md) says what the owner does: the token's scope, the secret, the environment and each release's steps.
6. **Architecture section 12, "Release tooling" (wording agreed by the owner, 20 Oct 2026, relayed; applied to `architecture.md` in this change, that bullet only).** The first two sentences of the bullet "Library family: `cargo-release`. It is a local command that bumps versions, updates the changelog, tags and publishes, so a maintainer stays in control before 1.0." would read: "**Library family: published by the release workflow (decision 0138).** A maintainer bumps the shared version, updates the changelogs and pushes a `lib-v<semver>` tag by hand (`cargo-release` may do this locally, without publishing). The release workflow then publishes the four crates with `cargo publish`, in dependency order, only when started by hand on that tag with publishing asked for, after the release gate and the publish dry run pass. The maintainer stays in control before 1.0: nothing is published by a tag push alone." `crate-selection.md` is unchanged.
7. **Names, version, metadata and credential (decided by the owner, 20 Oct 2026, relayed).** The four library names are already the owner's: crates.io holds `0.0.0` placeholders published by the owner's account on 11 Oct 2026, with `openchuck-geom`, `openchuck-import`, `openchuck` and `openchuckcam`, so no placeholder is needed, and the workflow never publishes one. Decided: no further reservations (the application crates stay unpublished); the first real publish is at the workspace version current when the owner cuts the `lib-v` tag (0.11.0 today), so the lockstep and the tag check stay; the keywords and categories in the four manifests as proposed; no `homepage` or `documentation` field (crates.io then links the repository and docs.rs); the AGPL text stays out of the packages (crates.io shows the SPDX licence and links the repository; OI-410 closed); the credential is a crates.io API token with the `publish-update` scope only, the crate pattern `openchuck-*` and an expiry, stored as `CARGO_REGISTRY_TOKEN` in the `crates-io` environment, where the owner adds a required reviewer; Trusted Publishing is a later improvement (OI-411).

Publishing the library family needs no other crate published: its crates depend only on each other and on third-party crates (`cargo xtask deps`), `openchuck-buildinfo` is used only by the two front ends (decision 0151), and the application crates are not published.

## Alternatives considered

- **Leave the version on the testkit entry and strip it per crate** (a crate-level `openchuck-testkit = { path = "..." }` in two manifests). The same result, but it splits the declaration that the workspace keeps in one place (NFR-14 records rule).
- **Package the tests too.** They would be in the package but could not build there (no testkit, no `testdata/`), so a user's `cargo test` on the downloaded crate would fail. Leaving them out is clearer.
- **`cargo-release` in the workflow.** Architecture section 12 names it for library releases, but in the workflow it would add a tool to install and assess, for what `cargo publish` (which publishes several packages and waits for the index since Rust 1.90) does alone.
- **crates.io Trusted Publishing (OIDC) instead of a token.** No stored secret, and possible now that the crates exist; it needs the `rust-lang/crates-io-auth-action` action, assessed under NFR-14, and each crate linked to this workflow on crates.io. The owner chose a token first; Trusted Publishing is a later improvement (OI-411).
- **Publish on a `lib-v` tag push.** One step fewer, but a tag pushed by mistake would publish, which cannot be undone. The owner asked for a manual input.
- **Keep publishing local (`cargo publish` on the maintainer's machine).** No secret in the repository, but nothing ties the published commit to a passed gate. Offered to the owner as option B of item 6; not chosen.

## Verification

- `cargo publish --dry-run --locked -p openchuck-types -p openchuck-gcode -p openchuck-path -p openchuck-post` passes: the four crates package and build from their packages alone, with cargo resolving them against each other in a local registry. `cargo package --list` shows `posts/` in `openchuck-post` and no tests in any package; the packaged `openchuck-path` and `openchuck-post` manifests hold no `openchuck-testkit`.
- `cargo nextest run -p xtask`: the `publish` tests (each rule broken in turn, both causes of OI-302, keywords, the real workspace). With the old `include_str!` path and the old testkit entry put back, `cargo xtask publish` reports three findings naming them.
- The `openchuck-post` tests, including the shared-template test, and the `openchuck-app` and `openchuck-ui` tests that read the LinuxCNC post, pass with the posts at their new path.
- The workflows were linted with `actionlint`. Not run: the release workflow (OI-304) and any real publish. Nothing was published and no token was created.
