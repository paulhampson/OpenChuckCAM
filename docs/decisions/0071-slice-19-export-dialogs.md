It builds on [decision 0028](0028-slice-19-output-options-and-setup-sheet.md) (grouping, comments, setup sheet; accepted), [decision 0020](0020-slice-6-post-and-round-trip.md) item 12 (tool numbers in the application), [decision 0029](0029-slice-8-viewport-and-shell.md) (the shell and floating dialogs; accepted) and the interface specification of [decision 0038](0038-ui-specification-and-requirements.md) (accepted), section 11.6. It claims record **0071**, **OI-247 to OI-252** (OI-247 to OI-251 assigned by the orchestrator, and OI-247 given to the shell-level tests by its later request, so the five items of this record are OI-248 to OI-252, one past the block) and **no project schema number**: nothing is stored in the project (item 2). Requirements: GC-02, GC-04, GC-05, GC-12, GC-14, GC-15, GC-16, NFR-12.

## Context

Slice 19 items 1 to 3 and 5 are built. `Application::set_output_grouping`, `Application::setup_sheet` and the tool numbering functions (`tool_number_plan`, `tool_numbering_command`) exist with no dialog. Specification section 11.6 describes the dialog (board 5): post and files on the left, tool numbers, the checks before writing, a files list and preview on the right, an amber notice with a tick box, and a footer with the setup sheet button, Cancel and "Write G-code". Section 13 keeps the acknowledgement per user on each computer, keyed by the project folder (OI-165, closed). Neither the steps (section 4) nor the footer primary action (section 5) nor a user settings store are built.

## Decision (proposed)

1. **Where things live.** The decisions are in `openchuck-app`, so the CLI and tests use them and the dialog only draws:
   - `export` module: `post_summary` and `builtin_post_summaries` (what a post says: units, rotary letter, wrap, feed mode), `ExportChecks` and `export_checks`, `write_gcode_files`, the fixed notice text and the tick box label; `Application::planned_files` (the files a grouping would write, with name, setup and programmed time, before posting), `Application::start_regenerate_with_post` (a run with a post and grouping of its own that leaves the application's own as they were, so a later Generate does not post G-code unasked), `Application::write_setup_sheet` (HTML and PDF named for the project).
   - `acknowledgement` module (item 6).
   - `openchuck-ui`: `export_panel.rs`, opened from File, "Post and export…" and with Ctrl E, in a floating window (decision 0029 item 17; `floating_unscrolled` is the same window without the scroll area, so the footer stays in view). Until the steps of section 4 exist there is no step 5 to open it from.
   No library crate changes its public API incompatibly: only additions, so no version bump.
2. **Nothing is stored in the project; schema 13 is not taken.** GC-14's numbers are already stored (the tool snapshots' controller numbers), changed by one undoable command and kept when the user saves the project. The post, the grouping and the output folder are chosen in the dialog and not remembered (GC-05 does not ask for it, and section 13 does not list them as user settings). Defaults are the first built-in post, one file per setup (decision 0028) and an empty folder, which "Write G-code" names as missing. Remembering them per user is OI-248.
3. **Renumbering does not make results out of date.** The pipeline cache key hashed the whole tool snapshot, including the controller number and offsets, which only the post reads. A renumbering would have marked every operation out of date, forced a regeneration of toolpaths that cannot change, and blocked export under item 4. The key now leaves the controller mapping out. Cached results are in memory only, so no stored data is affected. Test: renumbering keeps the checks passing.
4. **Checks before writing (GC-15).** `export_checks(project, run, posted, last_error)` where `run` is the latest generation (with its simulation if one was made), `posted` the dialog's own run made with the chosen post, and `last_error` the message of a later failed run:
   - **Blocking:** no enabled operation; nothing generated yet; the last generation failed (its message is shown); an enabled operation is **out of date**, found by the pipeline's own cache key (an edit to the operation, its setup, tool, machine, selections or any operation before it, the same rule that decides what regenerates); a file made with the post failed gate 1 or 2 (decision 0020; this is one step beyond the specification, which names stale and error only. The application must not offer a file it has itself found to disagree with the toolpath. Easy to relax to a warning).
   - **Warnings:** an enabled operation the run did not simulate; machine values not confirmed on the machine (the provenance list).
   - **Listed, not posted:** disabled operations. The sentence of the rule is shown under the list.
   - **Also refused:** a number used twice or outside the machine's range (GC-14), no post folder chosen when "A post folder" is selected, an empty toolpath, no output folder, a box not ticked. "Write G-code" is disabled with the first of these as its tooltip and as the line beside it (section 5, "disabled means explained").
   - **Error is per run, not per operation:** the application keeps no per-operation error state yet (UI-11 needs the project tree states of lane A and T), so a failed generation blocks as a whole. OI-249.
   - **Model file changes** are not compared (the project's own files are what the key reads), as in the staleness badge already built. OI-249.
5. **The files list and preview.** The dialog makes its files with `start_regenerate_with_post` when the choices or the project change and nothing blocks it, so cached operations are reused and only posting and its two checks cost time. Each row shows the name, the setup, the line count and the programmed time (decision 0028 item 3: the sum of move durations; the interface calls it "Programmed time" until SIM-08). The preview is the first 14 lines of the chosen file.
6. **The acknowledgement (GC-16, UI-15).** `Acknowledgements` reads and writes the `[export] acknowledged` list (canonical project folder paths, sorted) in `settings.toml` in the `OpenChuckCAM/` configuration folder (the folder of decision 0029 item 15; section 13). It reads and writes only that key and keeps every other key, so the other settings of section 13 can share the file. A missing file is "not acknowledged" with no message; an unreadable or invalid one is "not acknowledged" with a sentence, never a crash (NFR-07), and is renamed to `settings.toml.bad` before a new one is written, so nothing is lost. The box is ticked before the first export of a project on the computer; the acknowledgement is **kept when the first file write succeeds**, not at the tick (closing the dialog without writing does not count as an export). Once kept the box shows ticked and disabled with "Acknowledged for this project on this computer". A sentence under the box says another computer asks again. The notice itself, in the specification's fixed words, is shown every time. Nothing is written to the project (tested by comparing every file of the project folder before and after). If the configuration folder cannot be found the box is asked every time and the dialog says so.
7. **Tool numbers (GC-14).** One row per tool in use (name, the operations that use it, program number), the machine's range, and "Keep as saved", "Renumber in order of use" or "By hand" (typed numbers). A choice is checked live with `tool_numbering_command`, which names a duplicate, a number below 1 or above the machine's range, and is applied by "Confirm numbers" or "Use these numbers" as one undoable command. The dialog does not save the project file; the shell's own Save and unsaved-changes prompt do, so the numbers are in the project once the user saves it. The CLI's `--tool-numbers` already saves.
8. **Feed mode is shown, not chosen.** GC-04 puts the feed mode in the post's definition and the post's checks require it to agree with the feed rule, so the dialog shows it with the units, the rotary letter and the wrap as read-only lines under the post choice. The specification's wording ("units per minute, or inverse time where the post offers it") could be read as a choice; OI-252.
9. **Setup sheet (GC-12).** The footer button writes `<project>-setup-sheet.html` and `.pdf` into the output folder, with programmed times when a generation exists. It is disabled until a folder is chosen.
10. **CLI.** `regenerate` gains `--grouping project|setup|operation|tool` (default `setup`) and `--setup-sheet` (writes the sheet into `--out`; `--out` needs `--post` only when no sheet is asked for). The CLI asks no acknowledgement: it prints the notice every time, as before, and runs unattended in the reference jobs and CI. Whether GC-16 applies to it is OI-251.

11. **Shell-level tests for the selection keys, and two fixes (owner's request, OI-247).** Lane M's CodeRabbit finding on pull request 59 (no shell-level tests for Esc and dialog routing) is taken here because this slice adds dialogs to the same shell. `apps/openchuck-ui/src/shell/keys_tests.rs` draws the whole shell without a window, presses keys and clicks widgets: Q, W, E and R choose the click mode (also from a saved set); the keys do nothing when nothing is picked; a text field that has the keyboard keeps them; an error dialog, the export dialog, the results window and the add-operation dialog keep them and Esc behind them does not leave picking nor close them; Esc cancels a running region pick and keeps picking on, a second Esc leaves picking, also from a saved set; the tools box buttons choose the mode by a click; "Select in view" loads a set as the working selection and a swatch and "Default" set and clear its colour. Two behaviours the tests found are fixed: (a) the keys were skipped only for `Dialog`, so Q, W, E, R and Esc still reached picking behind the export, results and add-operation windows; the shell now skips them while any of these is open (`Shell::window_open`); (b) egui lets go of a text field's focus at the start of the frame an Esc arrives in, so Esc that ended an edit (renaming a set, say) also left picking; `SelectionPanel::keys` now also skips a frame in which a text field had the keyboard at the end of the previous one. Test hooks, all `#[cfg(test)]`: `SelectionPanel::choice_name`, `has_region_pick`, `working_triangles` and `hold_region_pick` (keeps a region pick pending however fast it is, since a flood fill on the test part ends before a frame does). Nine tests, 1 s together, uninstrumented.

## Alternatives considered

- **Store the post, grouping and folder in the project (schema 13).** A project would then open ready to export. They are choices about a machine and a computer, not about the part; the folder in particular is personal. Not taken; OI-248 offers the per-user file instead.
- **Make the dialog generate the toolpaths when none exist.** It would hide the stale state the specification wants shown ("Generate stale (n)") and make export slow without warning. The dialog only posts what has been generated.
- **Keep the tool number in the cache key** and regenerate after a renumbering: correct but wasteful, and it would make the numbers dialog look broken. Rejected (item 3).
- **Record the acknowledgement when the box is ticked:** a user who ticks and cancels would not be asked again though nothing was exported. Rejected (item 6).
- **Block only on stale and error, as written.** Leaves a file that failed its own replay writable. Item 4's addition is the safer reading of NFR-12.

## Verification

- `cargo test -p openchuck-app --test export_dialog` (15 tests): checks (none generated, fresh with warnings, simulation clearing them, an edit making that operation and the ones after it out of date and an undo making them current, a failed generation, disabled operations, unconfirmed machine values), planned files equal written files for every grouping, a project file across two setups refused in the plan, tool numbers (duplicate, range, by hand, saved and reopened with byte-identical G-code, a renumbering not making results out of date, undo), the acknowledgement (per project, per settings folder, never in the project, bad file with message and `.bad` copy, other keys kept), writing files, the post summary, a run with a post leaving the application's own alone, the setup sheet files.
- `cargo test -p openchuck-ui export_panel` (5 tests): nothing made before generation, the full flow through the dialog's own state (blockers in order, writing, acknowledgement kept and not asked again, another computer asking, an edit blocking), typed numbers, the notice's wording (never "safe" or "verified").
- `cargo test -p openchuck-cli req_gc`: `--grouping` and `--setup-sheet`.
- Not done: a person looking at the dialog on a screen at 1366 by 768 (UI-16); the tests draw it without a window. Gate 3 is not affected (no post or template changed).
