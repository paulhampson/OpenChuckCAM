## Decision (accepted)

1. **Dexel stock (item 1).** `openchuck_sim::DexelStock`: material intervals along model Z on an (x, y) grid of columns in the model (part) frame, built from cylinder, box and offset bounding-box stock; imported stock (SET-04, P2) is refused. The requested cell is shrunk slightly per axis so a whole number of columns spans the stock; each column stands for the prism one cell across around its centre. A guard refuses a grid over 64 million columns. The stock keeps a bound on its distance from the rotary axis, set when made (material only shrinks). It implements the pathing library's `StockModel`: `contains`, `ray_entry` (exact along Z; otherwise marched at a quarter cell and bisected) and `max_radius` (over column centres, so a new cylinder never reads larger than it is).
2. **Tool solid and span solver (item 2; OI-101).** `ToolSolid` copies the profile's lower envelope from `RevolvedProfile` into plain closed forms, so every tool type of TL-03, custom profiles included, sweeps through the same code. The tool is `{ r <= R, h(r) <= w <= top }` (the flutes; the shank is not modelled, collisions are COL-05's). The span of a column line inside the tool is solved per pose: clipped to the cylinder and the flute slab in closed form; at or above `H = h(R)` the solid is the plain cylinder, so only the part of the line below `H` needs the envelope. Convex profiles then need one root, found by the Illinois method to 1e-9 mm (a golden-section peak search only when the whole line lies below `H`); non-convex profiles are marched at the smaller of `R / 8` and the cell and refined, so a span missed there is shorter than one cell. The search is limited to the material the column still holds.
3. **Sampling (OI-102).** Moves are replayed as the controller runs them, linear in machine X, Y, Z and A, through the shared kinematics (`machine_xyz`, `tool_tip_in_model`, `tool_axis_in_model`), and sampled so that no point of the tool that can reach material moves more than one cell between poses (the reach is the tip's distance from the axis plus the tool's extent, capped by the stock's). The swept volume between poses is not built. Rapid moves are cut alone, and one that removes material is reported with its move number and volume (a toolpath fault; collision checking proper is COL-01).
4. **Simulator, checkpoints and jobs (items 4 and 8).** `Simulator` runs toolpath groups in machining order on one stock. It keeps a checkpoint at the start and after each group, and optionally every N moves; `stock_at(group, move)` replays from the nearest checkpoint before it, and gives the same stock as running up to that move (hash-equal). Poses are cut in batches of 32,768 between cancellation checks and progress reports. Work runs on the caller's rayon pool, one task per row of columns; each column takes the poses in order, alone, so the state never depends on the thread count.
5. **Resolution setting (item 3; SIM-07, OI-100).** `openchuck_types::simulation::SimulationSettings { cell }`: default 0.1 mm, finest 0.025 mm, coarsest 1.0 mm; a finer setting is never the default. The setting reports its cost relative to the default: time about the cube of the ratio, memory the square. It is a **project** setting, not an application one, because later operations are generated against the simulated stock (item 7), so the G-code depends on it and must follow from the project alone (GC-07). It is kept in `project.toml` as a `[simulation]` table written only when it differs from the default, so existing projects are unchanged on disk except the schema number. Project folder schema 5 (the migration from 4 changes only the number). `Command::SetSimulation` sets it as one undoable step; an out-of-range cell is refused and changes nothing.
6. **Deviation against the target (item 5; SIM-05). Accepted by the owner first, 14 Oct 2026.** The target's surface is sampled no further apart than the cell (sub-triangle centroids). At each sample the deviation is the **closest distance** to the stock's boundary, each column taken as its prism: when the point is in material, the distance to the nearest empty space (remaining, positive); otherwise the distance to the nearest material (overcut, negative). The search runs ring by ring over columns, up to 3 mm (a larger value is reported as at least 3 mm). An overcut counts as one beyond one cell (the simulation's own error, verification plan 4.1). The result lists every sample, the worst remaining and overcut values with their places, the number of samples overcut, and up to ten overcut places at least 2 mm apart. The distance along the surface normal was tried first and rejected: at a part's edge the normal runs along the cut surface, where the half-cell quantisation across a column read as a 0.2 mm overcut on a correct path.
7. **Carry-over in the pipeline (item 4; SIM-06).** The first operation of a setup is generated against the setup's stock definition (exact, so single-operation output and the golden files do not change). Each later operation in the same setup is generated against the simulated stock the earlier ones left, through the `StockModel` port (`generate_operation_on`). A setup's operations are simulated whenever another follows them, and all of them when a simulation is asked for (`Application::simulate`, `start_simulate`). A new setup starts from its own stock definition (OI-113). The pipeline's simulators keep no checkpoints (`Simulator::without_checkpoints`; each checkpoint is a copy of the stock), and the final stock moves into the report without a copy; jumping to a move is for playback (slice 9).
8. **Results as plain data (item 6).** `Regeneration::simulation` holds a `SimulationReport`: settings, and per setup the volumes, grid, memory, per-operation moves, poses, removed volume and rapid cuts, the deviation and the stock itself. `stock_mesh` gives the stock as a closed blocky mesh (two triangles per cap and wall face; quads do not share vertices). No drawing code; smoothing and colouring by deviation are the viewport's (slice 9, OI-115).
9. **CLI (item 7).** `openchuck-cli simulate <project> [--cell MM]` regenerates and simulates every operation, sets and saves the cell first when given, prints the cell and its cost, per setup and operation the removal, rapids that cut, the worst remaining and overcut with places, and the run time. It exits with an error when anything is overcut beyond one cell or a rapid removes material.
10. **Build.** `openchuck-sim` uses `rayon` (already in the selection; the register row now names it) and is optimised in test and debug builds, as decision 0018 did for `openchuck-path`. The budget test needs an optimised build and a quiet machine, so it is ignored by default (OI-114).

## Alternatives considered

- **Deviation along the surface normal:** rejected (item 6).
- **Resolution as an application option:** simpler, but two machines with different settings would post different G-code from the same project (GC-07).
- **Simulating the first operation's stock too, for uniformity:** changes approach heights by the dexel quantisation and every golden file, for no gain; the definition is exact.
- **Carry-over across setups:** needs the transform between setups' part frames and refixturing rules; not needed for any P1 job so far (OI-113).
- **Smaller batches (8,192 poses):** finer cancellation, but too few rows of columns per batch to keep four threads busy (39 s against 21 s on the reference job).
