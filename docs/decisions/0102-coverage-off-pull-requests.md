# 0102: Coverage leaves the pull request run: a 95% line target per crate, checked nightly

- **Status:** proposed. The wording and each sub-decision below are the owner's, relayed by the orchestrator session ([decision 0049](0049-relayed-acceptance-of-records.md)); the owner accepts the record.
- **Date:** 17 Oct 2026.
- **Open items** are tracked in [docs/open-items.md](../open-items.md): OI-322, OI-323 and OI-324 are new.
- **Amends:** [decision 0052](0052-ci-speed-up.md) (the "every gate stays" bullet and the status of option 6(c), for Coverage only); verification plan section 8; `AGENTS.md` and `CLAUDE.md`.

## Context

The Coverage trend job is the longest job of a pull request run: 19.4 to 25.5 min on ordinary runs, and 69 to 72 min on two runs of slow runners (pull requests 64 and 97), in a run whose other jobs took 13 to 22 min. Sharding it, ordering its tests and selecting the tests of changed crates were examined (the Coverage sharding report, 17 Oct 2026): sharding gains at most 1 to 3 min on a pull request while Windows Build and test (about 17 min) follows it, and crate selection helps 13% of recent merges (the other 87% touch path, sim, types, testkit or the workspace files). Coverage has also been a trend only (verification plan section 8: "not a target on its own"), so nothing has told a lane how much of its new code its tests reach.

## Decision

1. **Coverage runs nightly and by hand, and nowhere else.** It does not run on pull requests or on pushes to `main`. `.github/workflows/coverage.yml` has the steps and the artifacts the old job had, and runs the whole suite, the long-running tests included (the nextest profile `coverage-full`: every test, the slowest first). The nightly series is the trend; there is no per-commit coverage artifact any more. There is no timeout. The run takes well over half an hour (estimate: the long tests are 6 to 11 times slower instrumented, the longest alone about 18 to 33 minutes); the first run is the first timing. `CI required checks` keeps its name and rule; `coverage` leaves its `needs` and its check list, and the aggregator now fails if a job is listed in `needs` and never checked. Build and test still runs every test on every pull request; no test is skipped.
2. **The target is 95% of lines in each product crate**, a development target, written into `AGENTS.md` and `CLAUDE.md` (a lane checks the crates it changed locally before it pushes) and verification plan section 8. `cargo xtask coverage` computes it from the lcov file: it adds up `LF` and `LH` of the files under `crates/<name>/src/` and `apps/<name>/src/`, per crate. `xtask/coverage.toml` lists the gated crates, the report-only crates, the excluded crates and any temporary floors.
3. **Gated crates:** types, geom, path, sim, post, gcode, project, import, app. **Report only:** ui, viewport, cli (windowing, GPU and command-line wiring that the headless run cannot reach). **Excluded:** testkit (test support code); xtask stays out of the lcov file as before. A crate in the lcov file that the file does not list, and a gated crate with no data, fail the run.
4. **Every run enforces, once enabled.** A gated crate under its threshold fails the run when `enforce = true` is set in `xtask/coverage.toml`; until then the run reports the table and fails only on a configuration problem.
5. **One issue per failing scheduled job, a comment each night, closed by a green run (the fuzz job: closed by a pull request).** A scheduled job that fails opens one GitHub issue (label `nightly-<job>`, a fixed title, the run link, the commit and the failing legs of a matrix job). While that issue is open, the issue's first text is not changed and no second issue is opened: each night the job still fails adds a comment (date, run link, commit, the night count and the date it started failing; for Coverage also the per-crate table with the failing crates marked). The first run in which the job passes closes the issue with a comment naming the run; for Coverage, "passes" means every gated crate meets its own threshold (95%, or its floor while the ratchet is on), and report-only crates do not decide. A new failure after that opens a new issue. This covers every job of the Nightly workflow (fuzz, STEP mutations, the sanitizer, the long tests, the beta build) and the Coverage job. The steps are written once, in the composite action `.github/actions/nightly-issue`; a last job in `nightly.yml` and the `issue` job of `coverage.yml` call it, and are the only jobs with `issues: write`, so the jobs that build and test hold a read-only token. A manual run can simulate a failed job to try the flow.
   **The fuzz job is the exception** (the owner's change, relayed 17 Oct 2026): a green run never closes a fuzz issue. It is closed only by a pull request that addresses the failure ("Fixes #N" in the pull request; the issue text tells the fixer so and says that green runs do not close it). Consecutive failing nights add a comment to the open fuzz issue, as for the other jobs. A fuzz failure after a green run opens a NEW issue even if an earlier fuzz issue is still open, because it is likely a different failure. "After a green run" is read from the run history, not from state kept in the issues: the most recent earlier run of the Nightly workflow on `main` (scheduled or by hand) in which the fuzz legs ran to a result is green if every leg succeeded and failed if any leg failed or timed out; runs that were cancelled, and runs in which the fuzz job was skipped, are passed over (up to the last 15 runs). If no earlier run decides, the failure comments on the newest open fuzz issue (or opens the first one), so an unknown history does not open a second issue. When two fuzz issues are open, comments go to the newest. The setting is per job (`policy` in the action's job list: `green`, the default, or `fix`); every other job, STEP mutations included unless the owner says otherwise, keeps the green-run closing.
6. **First measurement before enforcement.** The workflow merges with `enforce = false`; the first measurement is a manual run of `coverage.yml` after the merge, which prints the table; the owner reads it, and a follow-up change sets `enforce = true` with a floor for each crate under 95% (the floor is the measured value rounded down; the run fails when a crate falls below its floor, and a lane raises a floor as it adds tests).
7. **The target does not change how tests are chosen.** Test-driven development from the requirements, the architecture and the decisions stays the primary technique: each test is written first, from the behaviour it checks, and named by requirement ID. Coverage is a check on that work, not its goal. A line the requirement-based tests do not reach is a prompt to ask whether a test or a requirement is missing or the code is not needed; a test written only to run lines, or that asserts whatever the code happens to do, is not verification evidence.

## Alternatives considered

- **Keep a coverage run on every push to `main` too.** The owner decided against it: the nightly series is the only trend, so no run takes runner time per merge.
- **Keep Coverage on every pull request and speed it up.** Priority ordering gains about 2 min, sharding 1 to 3 min on the pull request as a whole; neither helps the slow-runner runs, which an owner decision left without a timeout.
- **Select tests by changed crate.** 87% of the 53 code merges since 1 Oct would still run at least 99% of the test cost; it needs an amendment to 0052's "no test is skipped"; and it makes a pull request's report partial.
- **Merge per-shard lcov files; shard by crate group.** Rejected in the sharding report for losing region data, and for balance, respectively.
- **For the fuzz job, keep a marker in the issue's comments for the last failing run, or comment a green night.** Rejected: it needs a comment (or a body edit) on every green night, and the history of the runs already says whether the previous run passed.
- **Edit the issue's text each night instead of commenting.** Quieter for subscribers, but the history of the failing nights is lost; the owner chose a comment per night.

## Consequences

- **Documents:** `AGENTS.md` and `CLAUDE.md` gain the rule above; verification plan section 8 changes its Coverage row and adds a paragraph; decision 0052 gains two pointers to this record.
- **CI:** `.github/workflows/coverage.yml` and `.github/actions/nightly-issue` are new; `ci.yml` loses the `coverage` job; `nightly.yml` gains a last job that reports every nightly job; `xtask` gains `coverage` and `xtask/coverage.toml`. `.config/nextest.toml` gains the profile `coverage-full` (every test, the long tests first, then the six next-slowest). The `coverage` profile (without the long tests) is no longer used by CI; it stays for a lane's local check. The priority ordering that [pull request 103] proposed for it has no job to speed up and is replaced by the ordering in `coverage-full`.
- **Figures:** inline `#[cfg(test)]` modules count as lines (3% of `src/` in path, 21% in ui) and test code is covered, so a crate's figure is higher than its production coverage by about the test share times the uncovered share (at most about 1 point; OI-323). The STEP kernel code behind the `kernel` feature is not built in the coverage run and is not in any figure.
- **Fuzz issues:** an open fuzz issue stays open until a pull request closes it, so a fuzz failure that is never fixed stays visible; several can be open at once (one per failure that followed a green run). A fuzz failure that comes back unchanged after a green run (a flaky target) opens a new issue each time it does. The action's `policy` setting is the only code that differs between the jobs.
- **Risk:** a numeric target invites tests written to raise the figure. The counter is the wording in `AGENTS.md`, `CLAUDE.md` and verification plan section 8 (item 7), review of the tests against the requirements, and the report-only crates, whose low figures are not a failure.
- **Cost:** a lane that skips the local check learns of a shortfall a night later, from an issue. A job that fails for a flaky reason now opens an issue too, and a comment each night until it passes. None of these workflows can run before they are merged (GitHub runs a workflow file from the default branch), so the first manual runs on `main` are the test; OI-324. Because nothing exercises the workflow before the nightly, a mistake in it shows as a failed nightly.
