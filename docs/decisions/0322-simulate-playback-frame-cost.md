## Context

Issue #382: with a fine-stepover finishing (a V-bit with a 0.1 mm tip at a 0.03 mm stepover) the Simulate step takes minutes before the cut part appears, and during playback the tool seems not to move. Lane CARVEPERF ([decision 0292](0292-carving-finishing-speed.md)) profiled the owner's project and split the display side into this lane.

Since issue #333 ([decision 0040](0040-slice-9-display-and-playback.md), "Issue 333 correction") the tool is shown at the cursor of the cut part on screen until the next cut part is ready, so the time of one cut-part frame is how long the tool stands still.

### Measurement

`crates/openchuck-app/examples/playback_times.rs` times, through the public API: generate and simulate, prepare playback (the second simulation, with checkpoints), the surface job at seven jumps along the run (and, alone, the mesh and the picker on the stock it shows), and forward play as the viewport does it: a new surface is asked for at the clock's cursor when the last one is finished, eight frames from 30% of the program time at 10x, 100x, 1000x and "whole program in 60 s". Given an STL it builds the project around it in a temporary folder; given a project folder it opens it. It prints counts, sizes and times only.

Test piece: lane CARVEPERF's carving (`CarvedRelief::STANDARD` at 0.1 mm, written by its `carving_model` example, not committed), cylinder stock 28 mm by 34 mm, rotary roughing with a 3 mm ball, then axial finishing with a 60 degree V-bit with a 0.1 mm tip at a 0.03 mm stepover: 539,133 moves in 2 groups, 17,929 s of machining, 10 checkpoints, a stock copy of 3.8 MB, cut-part meshes of 0.76 to 1.07 million triangles. Machine: a 4-vCPU cloud container, release build, 4 threads, nothing else running, two runs of each build. There is no graphics adapter, so the upload and the drawing of a frame are not measured.

### Where a frame's time goes (`main`)

| Part of a cut-part frame | Test piece | Owner's project (CARVEPERF) |
| --- | --- | --- |
| Stock replayed from the nearest checkpoint (up to 1/8 of an operation) | 0 to 5 s | 0.01 to 18.5 s |
| Colours: the final comparison's nearest sample for each triangle, one thread | about 2 to 2.5 s | about 2 to 4 s |
| Picker (`MeshPicker::new`, a hierarchy over every triangle) | about 1 to 2 s | not split out |
| Stock mesh | 0.05 s | 0.05 to 0.1 s |

A frame with nothing to replay took 3.5 s. The last frame of the run replayed from the last checkpoint inside the operation, although a copy is kept after it (7.9 to 9.2 s). Before any of this, generating and simulating took 71 to 75 s and preparing playback 52 to 56 s (owner's project: 250 s and 131 s).

## Decision

1. **Colours are shared over the job's threads** (`SurfaceSamples::bands`). Each triangle's value depends on that triangle alone, so the triangles are split into fixed chunks of 4,096 and coloured in parallel, and the chunks are joined in order: the values are the same at any thread count (NFR-06). The cancel flag is looked at before each chunk, as before. About 2.2 s down to 0.85 s on the test piece.
2. **The stock of the last request is kept as a checkpoint** (`StockPlayback`; `Simulator::stock_at_from` in `openchuck-sim`). After each request the stock after its whole moves (before the swept part of the current move) is kept, one copy for the whole playback. The next request replays from it when it is nearer than every checkpoint before the point asked for; otherwise it is ignored. Replaying from any checkpoint gives the same stock as running up to the point (decision 0025 item 4), so forward play replays only the moves since the last frame and shows the same stock. The copy is counted: the checkpoint limit already counts one copy more than a setup keeps (`groups + 2 + moves / every`), and the kept stock is one copy of one setup's stock.
3. **The end of an operation is its checkpoint.** A request for the stock after the last move of a group uses the checkpoint after the group, and a request that lands on a checkpoint (or on the kept stock) is a copy of it, with nothing replayed.
4. **Checkpoints are held packed** (`DexelStock::pack`, `PackedStock` in `openchuck-sim`). A working stock keeps one allocation per column (about 95,000 on the test piece), and with hundreds of checkpoints (item 5) those allocations made the memory used about twice the bytes counted: preparing playback peaked at 3.4 GB for a budget of 1.5 GB. A checkpoint is now held as two flat arrays (the span ends per column and the spans), unpacked into a working stock when a replay starts from it. Unpacking gives the same stock bit for bit, with the same state hash (decision 0025 item 4), and the bytes counted are the bytes held.
5. **Checkpoints are spaced by a memory budget the user sets (the owner's decision D1).** "Memory for playback checkpoints (MB)" in Settings, an application preference kept in the user's settings (`SimulateSettings::playback_memory_mb`), never in the project (no schema change): 1,536 MB by default (the old limit), 256 to 8,192 MB in steps of 256; a value out of range or between steps is brought to the nearest step, and a settings file written before it existed reads the default. "Prepare playback" counts the copies that must be held: the start and after each operation in every setup, and two for the replay (the stock kept from the last request and the one being replayed). If they do not fit, it is refused with a message naming the setting and the simulation cell, as before (NFR-07). The rest is shared by checkpoints inside the operations, spaced evenly over all the moves to fill it (`checkpoint_spacing`) and never closer than 1,000 moves. The simulator counts each copy at its packed size (item 4), which changes as the part is cut, and does not keep one that would pass the budget (`Simulator::with_checkpoint_budget`): fewer checkpoints, the same stock. A change applies the next time the cut part is prepared. On the owner's project (CARVEPERF's numbers: 290,548 moves, a copy of 7 MB) the default gives about 225 copies, about 1,300 moves apart, instead of 10 (measured on the owner's project: 292, since a packed copy is smaller while less is cut); a jump then replays at most about 0.7 s there.
   The budget used is also capped at a quarter of the computer's physical memory (the owner's decision on OI-1315), read once at start (`apps/openchuck-ui/src/memory.rs`: Linux `/proc/meminfo`, macOS `sysctl -n hw.memsize`, Windows `GlobalMemoryStatusEx` through `windows-sys`, already a dependency, with its `Win32_System_SystemInformation` feature; no new dependency). The setting is kept as the user set it; when the cap is below it, Settings shows "This computer: at most N MB". On the owner's laptop and desktop (32 GB) the cap is 8,192 MB, so no value in the range is capped there. When the memory cannot be read, the setting applies alone.
6. **Frames made while playback plays have no picker (the owner's decision D5, option B).** `Application::start_playing_stock_surface` makes the same mesh and colours as `start_stock_surface` without the picker (`StockSurface::can_pick` is false and `pick` finds nothing), and the playback panel asks for it while playing. When playback is still (paused, stopped at the end, stepped or jumped) and the frame shown has no picker, the frame at the cursor is made again with one, so the probe and pins work as before. While playing, nothing is read under the pointer and a kept value is not drawn.
7. **Not done: the picker built beside the colours.** Running the picker and the colours at once (`rayon::join`) was tried and made frames slower (about 5 s instead of 2 s: each waited on work the other's thread held), so they run one after the other as before.
8. **While playing, the tool follows the clock and the cut part follows behind it (the owner's decision D3, option B with a cut-part bar).** This amends decision 0040's "Issue 333 correction" while playback plays: the tool is drawn at the play head, and the cut part shown is the newest one made, at an earlier move. When playback is still (paused, stopped, stepped or jumped) the rule of issue #333 applies again: the tool stays where it is, and the cut part at that move is made and shown, so the two match exactly. Pausing never moves the tool back. A thin bar under the position bar, on the same scale and in the stock colour, shows where the cut part on screen is: a solid fill up to it with a mark at its end, an outline from there to the play head while it is behind, and a lighter fill growing with the progress of the cut part being made or of preparing playback. Its words, at the right end, are "Preparing the cut part N%", "Cut part N s behind" (program seconds, while playing) or "Updating cut part N%", and nothing when the cut part on screen is the one at the play head; the tooltip says that the cut part may follow behind the tool while playing and catches up on a pause. The position bar's own progress line no longer says "Preparing cut part"; while it shows the simulation being prepared, it takes the bar's place, so the dock needs no more height than before (the cut part on screen is then from the run being replaced). The cut part shown, its colours and its picks are unchanged.
9. **A jump and preparing playback report one total each.** Replaying to a point spans several ranges of moves (from a checkpoint, across the end of an operation); the replay reports its progress against the total moves it will replay, every 256 moves, and preparing playback against all the moves of every setup, so the cut-part bar's percentage only grows.

## Starting brief for lane SIMSPEED (the owner's decision D4)

Goal: make `Simulator::run_group` (`crates/openchuck-sim/src/simulation.rs`, cutting each swept tool into the dexel columns, `dexel.rs`) faster, with the same stock bit for bit. A gain counts three times: in the pipeline's run, in preparing playback (the same simulation with checkpoints, `stockplay.rs`) and in every cut-part frame's replay (item 2). Then measure again and put D2 (OI-174, the pipeline keeps the checkpoints) back to the owner with the new numbers.

Where the time goes, on the owner's project at 4 threads (temporary timers around the pipeline's stages, 30 Oct 2026; generation on `main`'s code before CARVEPERF's pull request 392): generation 451 s, the pipeline's simulation 96 s (92.6 s of it the V-bit finishing's 287,000 moves; roughing 3.3 s), the comparison with the part 14 s (already parallel), preparing playback 97 s. With pull request 392, generation is expected to be about 75 to 80 s, so the simulation, run twice, is the largest wait. On the test piece of this record (539,133 moves) the pipeline's run was 71 to 76 s and preparing playback 52 to 73 s.

The first question is thread use. Decision 0025 item 4: poses are cut in batches of 32,768 between cancellation checks, one task per row of columns, each column taking the poses in order, alone. A 0.1 mm V-bit pass at a 0.03 mm stepover touches few columns a move, so few rows may have work in a batch. Time the finishing's simulation at 1, 2 and 4 threads before changing anything. `examples/playback_times.rs` (this record) builds a project from an STL and times generate and simulate, preparing playback and frames; give it `THREADS`. The owner's project is the owner's only (kept outside the repository; numbers only), through the coordinator.

Determinism checks the change must pass (GC-07, NFR-06; decision 0025 items 4 and 7):
- The same stock bit for bit, by `state_hash`, at 1, 2 and N threads, on the test piece and on a carving finishing. The existing `req_nfr_06_simulation_is_identical_at_1_2_and_n_threads` (`openchuck-sim/tests/simulation.rs`) is the pattern.
- Later operations are generated against the simulated stock (carry-over, SIM-06), so a stock one bit different can change a later toolpath and the G-code: a carry-over project's G-code must stay byte-identical (`req_gc_07_reference_jobs_are_identical_at_1_and_n_threads` in `openchuck-app/tests/reference_jobs.rs`, and the golden files under `testdata/golden/`).
- Replay from a checkpoint must still equal running up to the point (`req_sim_04_req_nfr_04_jumping_from_a_kept_stock_matches_running_up_to_it`), and a packed checkpoint must still unpack to the same stock (item 4).
- The order in which one column takes the poses may not change; only which columns are visited, how the work is batched and shared, and allocation.

One file conflict to expect: CARVEPERF's pull request 392 also adds `crates/openchuck-app/examples/playback_times.rs`, separately. Whichever of the two pull requests merges second resolves the add/add conflict by keeping this lane's version, which grew out of CARVEPERF's and adds the STL project builder, the surface job, forward play and the memory argument.

- UI specification: section 13 (the setting and its cap), and 11.5's probe (nothing read while playing), synchronized cut playback and the cut-part bar (item 8).
