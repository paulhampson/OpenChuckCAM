# 0014: Slice 4 design refinement: tool data, profile validation, the tool library, tool sets and snapshots

**Status:** Proposed (12 Oct 2026), partly agreed. Built and tested on branch `claude/slice-4-tool-library`; the review checklist is not ticked yet. ## Decision

1. **The profile in `openchuck-types`** (`tool::profile`), as decision 0012 items 1, 2 and 5 say. `ToolProfile::validate` applies the monotone rule and returns a `RevolvedProfile`: the lower envelope `height_at(r)`, the envelope pieces in radius order each with a convexity flag, `is_convex`, and `point_for_normal` for convex profiles. Errors name the segment twice, as a field path (`tool.profile.segments[2]`) and in words ("segment 3"). `Tool::profile` builds a whole tool's outline from the tip to the flute length; that is the form path solving (slice 5), the gouge checker and the sweep (slice 7) read. The spike's code was ported, not depended on; distances are evaluated directly.
2. **Standard types** map by decision 0012 item 3: the cutting end runs from the tip to the tool radius, then a vertical side to the flute length, and a cutting end taller than the flute length is rejected. A tapered ball's diameter is where its taper ends; a drill is a sharp V of its point angle; a chamfer mill is a V with a tip diameter. A custom profile describes the cutting end: it must end at the tool radius (within 1e-6 mm), and the same vertical side is added up to the flute length if it ends lower (accepted 12 Oct 2026). Impossible values are rejected: a corner radius above the tool radius, an included or point angle of 0 or 180 degrees, a tip diameter not below the diameter, a tapered ball with no taper inside the diameter, a flute length above the overall length, zero flutes.
3. **TL-04 parameters on `Tool`.** **(owner)** `overall_length` replaces `stickout`, `flute_count` and an optional `material` (the tool's own material, such as carbide; not the stock material) are added. Corner radius, taper angle and tip angle stay inside the shape, where they mean something. Stickout is the distance from the holder face to the tip; it changes each time a tool is put in a collet, and its use is collision checking of shank, collet and holder (COL-01 to COL-07, P2), which needs the tool assembly (TL-08, P2). No P1 code reads it: the P1 collision oracle accepts every move and relies on the clearance geometry, so P1 cannot warn that a holder reaches the part on a deep cut either way, and that stays the user's check (NFR-12). It returns as a field of the assembly, so one library tool can be held at several stickouts. The overall length gives the tool's full length for display and the slice 7 simulation, and lets the flute length be checked against it. This changes `openchuck-types`' public API, so the workspace goes to 0.3.0 (INT-07); no crate is published, so only code in this repository is affected.
4. **Tool numbers belong to the project (TL-06; agreed 12 Oct 2026).** A library tool holds geometry and cutting data only; a project's tool snapshot holds `ControllerMapping { number, length_offset, diameter_offset }`, the values the post writes. The offsets are the controller's tool length register (`H`, used with `G43`) and cutter radius compensation register (`D`, used with `G41`/`G42`). They are optional and default to the tool number (`T3 H3 D3`). The Z1 uses neither: it measures tool length itself after `T<n> M6` and has no `G43` (decision 0007), and OpenChuckCAM's 4-axis paths are computed at the tool centre, so the Z1 post will not write them; they are kept for controllers such as LinuxCNC, as TL-06 asks. Each value must be at least 1, since 0 means "no tool" or "cancel" on common controllers. The machine's own limits (how many tools, which numbers) belong to the post (OI-62).
5. **Cutting data (TL-05; accepted 12 Oct 2026).** `CuttingData { spindle_speed, feed_per_tooth, plunge_feed, stepover, stepdown }` with a new unit `SpindleSpeed` (rev/min); the cutting feed is derived (speed x flutes x feed per tooth), not stored. A tool holds a `CuttingTable`, keyed by the stock material name a setup gives (decision 0011 item 9). Names match exactly; no case folding or aliases until the material library (TL-09, P2) gives materials an identity (OI-61). Stepover and stepdown are lengths in millimetres; a stepover above the tool diameter or a stepdown above the flute length is rejected. What stepover means for a wrap or rotary strategy is for slice 5 to settle with OP-11 (OI-63).
6. **Custom profile text file (TL-03; decision 0012 item 6).** TOML, `schema = 1`, then `[[segments]]` with the `ToolProfile` fields: `type = "line"` or `"arc"`, `to = { radius, height }`, and for an arc either `centre = { radius, height }` or **(owner)** `radius` and `curve = "convex"` (bulging away from the tool, like a ball end) or `"concave"` (like a corner-rounding cutter). Under the monotone rule the two centres a radius allows are told apart by that one word. Written back, arcs carry their centre. Errors name the file and the segment. Drawing a profile in the UI is slice 8 (TL-03 closes there).
7. **The library is a folder (TL-01; agreed 12 Oct 2026).** One TOML file per tool (`schema = 1`, `id`, `name`, `[tool]`, `[tool.shape]`, `[cutting_data.<material>]`) and machine tool sets in `tool-sets/` (item 8). The ID inside a file identifies the tool; the file name is a label, made from the tool's name when the program writes a new tool (`6 mm flat` becomes `6-mm-flat.toml`, then `6-mm-flat-2.toml` for a second tool of that name), and a file the user renames keeps working. Every change is written to that tool's own file at once and other files are left alone, so a one-value edit is a one-line diff in one file and two people editing different tools merge cleanly. A file that cannot be read, or that repeats another file's ID, is skipped and reported, so one broken file does not hide the rest. Import copies tools from another library folder or a single tool file (a new ID gets a new file, a known ID rewrites that tool's file, an identical tool is left alone, and nothing is written if any source file is broken); export writes chosen tools into a folder another user can import. There is still no default library location: the CLI takes `--library <FOLDER>` (OI-53 now covers tools too).
8. **Machine tool sets (TL-11; agreed 12 Oct 2026).** A file in the library's `tool-sets/` folder names a machine profile (`machine = "Makera Z1"`, matched by name without regard to case) and lists `[[tools]]` with `number`, `tool` (a library tool ID) and optional `length_offset` and `diameter_offset`: the tools that machine normally holds, for example those kept in its tool changer. A number or a tool may appear once; a tool set naming a tool that is not in the library is reported. When a tool is added to a project, it takes the number the tool set of the project's machine gives it; if another tool in the project already uses that number, or no tool set covers the tool, it takes the lowest number that no project tool uses and the tool set does not keep for another tool. The number is then the project's, and the user can change it. The tool set stays in the library, not in the machine profile, so profiles stay machine data and one library can hold sets for several machines; the project keeps only the numbers it chose. With a library given, the tool check reports a project tool whose number differs from its machine's tool set.
9. **Snapshots (TL-07).** **(owner)** A project's `ToolSnapshot` keeps the library tool's ID, so a snapshot and its library tool are matched by ID, not by name or number. The snapshot holds everything the library tool does, plus its controller values, so the project opens and gives the same output with the library absent. Editing the library never touches a project: `compare_snapshot` reports `Same`, `Differs(fields)` (dotted paths such as `tool.diameter` or `cutting_data.oak`; a changed shape type is reported once as `tool.shape`; controller values are the project's and not compared) or `NotInLibrary`. Updating a snapshot from the library is an explicit, undoable `Command::Replace` that keeps the project's number; nothing updates silently.
10. **Project schema 4 (accepted 12 Oct 2026).** Tool snapshot files gain `[controller]`, `[cutting_data.<material>]` and the TL-04 fields. A schema 3 tool file is refused with a message saying what to add, rather than guessed: a flute count and tool number cannot be inferred, and stickout is not an overall length. No front end could write a tool before this slice; a fixture (`tests/fixtures/schema-3-tool/`) covers the refusal. Other files migrate by their number only.
11. **Checks, commands and CLI.** `openchuck-app::tools::check_tools` returns warnings, never errors: two snapshots sharing a tool number, an operation whose setup's stock material has no cutting data for its tool, and with a library each snapshot's comparison and any difference from its machine's tool set. `default_controller` gives a new snapshot's number (item 8). Adding, updating, renumbering and removing snapshots are the existing `Add`, `Replace` and `Remove` commands, so they undo (UI-08). The CLI gains `tools <project> [--library FOLDER]`; `tool <project> TOOL [--add | --update] [--library FOLDER] [--number N] [--length-offset H] [--diameter-offset D] [--remove]`, where `--add` takes a library tool by ID, name, or `T<n>` in the project machine's tool set; and `library FOLDER list | import FROM | export TO [TOOLS…] | profile TOOL PROFILE_FILE | store PROJECT TOOL | tool-set MACHINE [--set N=TOOL]… [--unset N]…`. `validate` and `report` print tool warnings.
12. **Corpus and fuzzing (NFR-07).** `testdata/tools/library/` is a sample library with one tool of every type and a Makera Z1 tool set (sample numbers, not the machine's real tool changer layout); `testdata/tools/broken/` holds damaged tool and tool set files; `testdata/tools/profiles/` holds good and damaged profile files. Corpus tests read every one and check that each damaged file names its fault. Two fuzz targets, `tool_library_toml` (tool files and tool set files) and `tool_profile_toml`, run for 1 minute on pull requests and 1 hour nightly, seeded from those folders; both check that what reads also writes and reads back the same. Property tests run the profile rule on random segments and the tool file and tool set parsers on damaged or random text in every test run.
13. **Tool numbers before posting (GC-14; agreed 12 Oct 2026, built in slice 6).** Before G-code is written the application lists the tool numbers the program will use; the user confirms them, renumbers automatically in order of first use by the operations, or renumbers by hand, and duplicates are refused. The choice is saved in the project as undoable commands, so the next post gives byte-identical output (GC-07). The CLI asks on a terminal and takes an option otherwise; the UI dialog comes with export in the UI (slice 19). Nothing in slice 4 depends on it; slice 4's numbers are what that step starts from.
14. **OI-54 stays open.** The machine-copy comparison it asks for needs the copy to record its source; tool snapshots solve that with a shared ID, but a machine profile has no ID yet. It is proposed for slice 8, when the UI needs it, rather than widening this slice.

## Alternatives considered

- **Keeping `stickout` beside `overall_length`.** Two lengths that must agree, one of which depends on the holder; it returns with the assembly (TL-08) instead.
- **Tool number in the library tool** (this record's first draft). Rejected by the owner: the same cutter has different numbers on different machines and in different jobs. The number lives in the project, with the machine's tool set as the default.
- **Tool set inside the machine profile.** It would travel with the project's machine copy, but it would tie machine data to tool IDs that only mean something with one particular library. Rejected by the owner in favour of the library folder.
- **A library as one file** (this record's first draft). One exchange file and simple export, but hard to maintain by hand and a merge conflict whenever two people edit different tools. Rejected by the owner.
- **File names made from IDs** (as project item files are). Unambiguous, but unreadable in a file browser; a library is browsed and edited by hand, so names come from the tool name and the ID inside the file is the identity.
- **Matching snapshots to library tools by name or number.** Names are edited and numbers repeat across machines; an ID survives both.
- **Updating snapshots from the library automatically on load.** Would break GC-07 (the same project gives the same G-code anywhere) and TL-07's "snapshot wins".
- **Migrating schema 3 tool files with guessed values** (two flutes, number 1, stickout as overall length). Silent guesses about a cutting tool are what NFR-12 warns against.
- **Case-insensitive material keys.** Two entries "Oak" and "oak" would then collide in ways the file does not show; deferred to TL-09.

## Verification

Tests named after the requirement IDs (decision record 0004 item 14):

- **TL-02, TL-03 (profiles):** every standard type's lower envelope matches its closed form within 1e-12 mm at 301 radii and ends at the tool radius and flute length; impossible values are rejected naming the field; self-intersecting, undercut, disconnected (an arc whose start is not on its circle), zero-length, on-axis, non-finite and over-quarter-turn custom profiles are rejected naming the segment; a ball typed as two arcs, a split flat, a hand-typed bull-nose and a split V agree with the standard tools within 1e-12 mm; a concave profile is valid but not convex and refuses the normal-offset fast path; random segments never panic and an accepted profile has a non-decreasing envelope.
- **TL-01:** a tool file round-trips byte for byte and holds no tool number; the library folder writes one file per tool, a same-named second tool gets its own file, a one-value edit changes one line of one file, and reopening gives the same library; a broken or duplicate file is skipped and reported while the rest read; export then import is lossless, a second import changes nothing, a changed tool replaces in place; the sample library reads every type.
- **TL-11:** a tool set file round-trips, is found by machine name without regard to case, and reassigning a number moves it; a number or tool listed twice, number 0 and an empty machine name are rejected; a tool missing from the library is refused on save and reported on read; a new project tool takes its tool set number, the next free number skipping numbers the set keeps, or the next free number when the set's is taken; a project number that differs from the set is reported; the CLI scenario adds a tool by `T4` through the Z1 tool set.
- **TL-03 (file):** profile files read arcs by centre and by radius and curve, write back with centres and read back the same; the profile corpus reads or names the faulty segment; the CLI refuses a bad profile naming the segment.
- **TL-04 to TL-06:** parameters survive JSON and the snapshot file; cutting data validates and gives the feed; offsets default to the tool number and 0 is refused; shared numbers and missing cutting data are warned; the CLI sets a number and length offset.
- **TL-07:** a project opens with the library absent and renders byte-identical files; editing or removing library tools leaves a saved project unchanged and is reported field by field, controller values excluded; the CLI scenario adds tools from a library, reports a library edit, validates with the library deleted and removes the tools.
- **PRJ-04:** every file is schema 4; a schema 3 tool snapshot is refused with what to do.
- **NFR-07:** the two fuzz targets and the property tests above. The fuzz targets compile; they were not run locally (no nightly toolchain in the session), so their first run is the pull request's fuzz job.
