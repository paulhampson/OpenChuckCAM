## Decision

1. **The profile in `openchuck-types`** (`tool::profile`), as decision 0012 items 1, 2 and 5 say. `ToolProfile::validate` applies the monotone rule and returns a `RevolvedProfile`: the lower envelope `height_at(r)`, the envelope pieces in radius order each with a convexity flag, `is_convex`, and `point_for_normal` for convex profiles. Errors name the segment twice, as a field path (`tool.profile.segments[2]`) and in words ("segment 3"). `Tool::profile` builds a whole tool's outline from the tip to the flute length; that is the form path solving (slice 5), the gouge checker and the sweep (slice 7) read. The spike's code was ported, not copied as a dependency; distances are evaluated directly.
2. **Standard types** map by decision 0012 item 3: the cutting end runs from the tip to the tool radius, then a vertical side to the flute length, and a cutting end taller than the flute length is rejected. A tapered ball's diameter is where its taper ends; a drill is a sharp V of its point angle; a chamfer mill is a V with a tip diameter. **(owner)** A custom profile describes the cutting end: it must end at the tool radius (within 1e-6 mm), and the same vertical side is added up to the flute length if it ends lower. Impossible values are rejected: a corner radius above the tool radius, an included or point angle of 0 or 180 degrees, a tip diameter not below the diameter, a tapered ball with no taper inside the diameter, a flute length above the overall length, zero flutes.
3. **TL-04 parameters on `Tool`.** **(owner)** `overall_length` replaces `stickout`: stickout depends on how the tool sits in its holder, which is the tool assembly (TL-08, P2), not the tool. `flute_count` and an optional `material` (the tool's own material, such as carbide; not the stock material) are added. Corner radius, taper angle and tip angle stay inside the shape, where they mean something. The tool number lives in the controller mapping (item 4), since TL-04 and TL-06 both list it and it must have one home. This changes `openchuck-types`' public API, so the workspace goes to 0.3.0 (INT-07) and the changelog records the break.
4. **Controller mapping (TL-06).** `ControllerMapping { number, length_offset, diameter_offset }`, beside the geometry rather than inside it. **(owner)** The offsets are optional and default to the tool number (`T3 H3 D3`), the common convention, so a file states them only when they differ. Each must be at least 1, since 0 means "no tool" or "cancel" on common controllers. The machine's own limits (how many tools, which numbers) are not known yet and belong to the post (OI-62).
5. **Cutting data (TL-05).** `CuttingData { spindle_speed, feed_per_tooth, plunge_feed, stepover, stepdown }` with a new unit `SpindleSpeed` (rev/min); the cutting feed is derived (speed x flutes x feed per tooth), not stored. A tool holds a `CuttingTable`, keyed by the stock material name a setup gives (decision 0011 item 9). **(owner)** Names match exactly; no case folding or aliases until the material library (TL-09, P2) gives materials an identity (OI-61). **(owner)** Stepover and stepdown are lengths in millimetres; a stepover above the tool diameter or a stepdown above the flute length is rejected. What stepover means for a wrap or rotary strategy (an arc length at which radius, or an angle) is for slice 5 to settle with OP-11 (OI-63).
6. **Custom profile text file (TL-03; decision 0012 item 6).** TOML, `schema = 1`, then `[[segments]]` with the `ToolProfile` fields: `type = "line"` or `"arc"`, `to = { radius, height }`, and for an arc either `centre = { radius, height }` or **(owner)** `radius` and `curve = "convex"` (bulging away from the tool, like a ball end) or `"concave"` (like a corner-rounding cutter). Under the monotone rule the two centres a radius allows are told apart by that one word. Written back, arcs carry their centre. `openchuck-project::tools::parse_profile` reads it; errors name the file and the segment. Drawing a profile in the UI is slice 8 (TL-03 closes there).
7. **The library (TL-01).** **(owner)** One TOML file per library with its own schema (`schema = 1`, then `[[tools]]` with `id`, `name`, `[tools.tool]`, `[tools.controller]` and `[tools.cutting_data.<material>]`). The same file is the import and export format: export writes chosen tools to a new file, import merges a file in (a new ID is added at the end, a known ID replaces that entry in place, an identical one is left alone). **(owner)** Tools keep their order in the file and an edit never moves one, so a one-value edit is a one-line diff (the checklist's "diffs cleanly"); a folder of one file per tool, as machine libraries are, was the alternative (below). Every tool is validated on read, and two tools may not share an ID; two tools may share a number in a library (different machines), but not without a warning in a project (item 10). There is still no default library location: the CLI takes `--library <FILE>` (OI-53 now covers tools too).
8. **Snapshots (TL-07).** **(owner)** A project's `ToolSnapshot` keeps the library tool's ID, so a snapshot and its library tool are matched by ID, not by name or number. The snapshot holds everything the library entry does (geometry, controller mapping, cutting data), so the project opens and gives the same output with the library absent. Editing the library never touches a project: `compare_snapshot` reports `Same`, `Differs(fields)` (dotted paths such as `tool.diameter`, `controller.number`, `cutting_data.oak`; a changed shape type is reported once as `tool.shape`) or `NotInLibrary`. Updating a snapshot from the library is an explicit, undoable `Command::Replace`, and the CLI's `tool --update`; nothing updates silently.
9. **Project schema 4.** Tool snapshot files gain `[controller]` and `[cutting_data.<material>]` and the TL-04 fields. **(owner)** A schema 3 tool file is refused with a message saying what to add, rather than guessed: a flute count and tool number cannot be inferred, and stickout is not an overall length. No front end could write a tool before this slice, so no real project holds one; a fixture (`tests/fixtures/schema-3-tool/`) covers the refusal. Other files migrate by their number only.
10. **Checks, commands and CLI.** `openchuck-app::tools::check_tools` returns warnings, never errors: two snapshots sharing a tool number, and an operation whose setup's stock material has no cutting data for its tool; with a library it adds each snapshot's comparison. Adding, updating and removing snapshots are the existing `Add`, `Replace` and `Remove` commands, so they undo (UI-08). The CLI gains `tools <project> [--library FILE]` (list with checks and comparison), `tool <project> TOOL [--add | --update] [--library FILE] [--remove]`, and `library FILE list | import FROM | export TO [TOOLS…] | profile TOOL PROFILE_FILE | store PROJECT TOOL`; `validate` and `report` print tool warnings. A tool is named by ID, by name or as `T<number>`.
11. **Corpus and fuzzing (NFR-07).** `testdata/tools/` holds a sample library with one tool of every type, damaged library files, and good and damaged profile files; corpus tests read every one and check each damaged file names its fault. Two fuzz targets, `tool_library_toml` and `tool_profile_toml`, run for 1 minute on pull requests and 1 hour nightly, seeded from that folder; both check that what reads also writes and reads back the same. Property tests run the profile rule on random segments and the library parser on damaged text in every test run.
12. **OI-54 stays open.** The machine-copy comparison it asks for needs the copy to record its source; tool snapshots solve that with a shared ID, but a machine profile has no ID yet. It is proposed for slice 8, when the UI needs it, rather than widening this slice.

## Alternatives considered

- **Keeping `stickout` and adding `overall_length`.** Two lengths that must agree, one of which depends on the holder; rejected for P1, stickout returns with the assembly (TL-08).
- **Tool number inside `Tool`.** Simpler to pass around, but it mixes controller values into the geometry the solvers read and gives TL-06's offsets no natural home.
- **A library as a folder of one file per tool** (like machine libraries). Merges more cleanly when two people edit different tools in Git, but import and export become file copies with no single exchange file. One file with stable order gives one-line diffs too; revisit if libraries are shared in Git (the format can move to a folder without changing the project).
- **Matching snapshots to library tools by name or number.** Names are edited and numbers repeat across machines; an ID survives both.
- **Updating snapshots from the library automatically on load.** Would break GC-07 (the same project gives the same G-code anywhere) and TL-07's "snapshot wins".
- **Migrating schema 3 tool files with guessed values** (two flutes, number 1, stickout as overall length). Silent guesses about a cutting tool are the kind of thing NFR-12 warns against; rejected.
- **Case-insensitive material keys.** Convenient, but two entries "Oak" and "oak" would then collide in ways the file does not show; deferred to TL-09.

## Verification

Tests named after the requirement IDs (decision record 0004 item 14):

- **TL-02, TL-03 (profiles):** every standard type's lower envelope matches its closed form within 1e-12 mm at 301 radii and ends at the tool radius and flute length (`req_tl_02_req_tl_03_standard_profiles_match_their_closed_form_silhouettes`); impossible values are rejected naming the field; self-intersecting, undercut, disconnected (an arc whose start is not on its circle), zero-length, on-axis, non-finite and over-quarter-turn custom profiles are rejected naming the segment; a ball typed as two arcs, a split flat, a hand-typed bull-nose and a split V agree with the standard tools within 1e-12 mm; a concave profile is valid but not convex and refuses the normal-offset fast path; random segments never panic and an accepted profile has a non-decreasing envelope.
- **TL-01:** the library file round-trips byte for byte; a one-value edit is a one-line diff; export then import is lossless, a second import changes nothing, a changed tool replaces in place; the sample library reads every type; damaged library files name their fault.
- **TL-03 (file):** profile files read arcs by centre and by radius and curve, write back with centres and read back the same; the profile corpus reads or names the faulty segment; the CLI refuses a bad profile naming the segment.
- **TL-04 to TL-06:** parameters survive JSON and the snapshot file; cutting data validates and gives the feed; offsets default to the tool number and 0 is refused; shared numbers and missing cutting data are warned.
- **TL-07:** a project opens with the library absent and renders byte-identical files; editing or removing library tools leaves a saved project unchanged and is reported field by field; the CLI scenario adds a tool from a library, reports a library edit, validates with the library deleted and removes the tool.
- **PRJ-04:** every file is schema 4; a schema 3 tool snapshot is refused with what to do.
- **NFR-07:** the two fuzz targets and the property tests above. The fuzz targets compile; they were not run locally (no nightly toolchain in the session), so their first run is the pull request's fuzz job.

## Consequences

- No change to `requirements.md`, `architecture.md` or the verification plan: architecture 5.1 and 5.6 already describe one profile and a separate library store with snapshots, and the TL rows of the verification plan are met as written.
- Work breakdown slice 4 gains a status line pointing here; its checklist is ticked when the owner reviews it.
- `openchuck-types` 0.3.0: `Tool` loses `stickout` and gains `overall_length`, `flute_count` and `material`. Slice 5 reads `Tool::profile()` for the drop-cutter; slice 6's post reads `ControllerMapping` and the derived feeds.
- No new dependency.
