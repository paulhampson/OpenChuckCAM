## Context

Trial findings F-88 (issue 259), F-89 (issue 260), F-91 (issue 262) and F-59 (issue 215, the remainder in OI-571). Requirements: NFR-12 (the user verifies the G-code; what is on screen must not mislead), UI-06 (a disabled operation is left out), UI-10 (the primary action), UI-11 (state by shape as well as colour), UI-16 (the window is usable), SIM-04 (playback) and SIM-05 (the comparison and its worst values). Records read: 0168 and 0169 (Simulate controls, playback window), 0172 and 0173 (the stale state, a removed path, the step bar), 0187 (the dock height), 0190 (the stock cache).

The owner's answers on the issues: a parameter change or a turn-off in Simulate leaves "the old simulation on screen, unchanged" with the dock empty and no way to simulate again from Simulate; the controls come back after simulating again. The owner asks for the result to be kept to compare, but marked out of date in plain words on the result itself (the view, the colours, the histogram, the worst values and the playback), and for the run action in the dock in place of the missing controls.

What the code did on `main` (reproduced in the rig with the cube project):

- A parameter change kept the run on screen. The results inspector added one muted line ("The project has changed since this simulation. Simulate again."), which compared the whole project, so a rename or a hidden toolpath raised it too. Nothing offered the action, and the numbers looked current.
- A turn-off dropped the playback run (0172 item 3), so the Playback tab showed only the tick box and "Run the simulation to play the cut.", while the results inspector still showed the old numbers. Turning off the last operation changed no other key, so the Simulate primary action said "Continue to post and export" although the export check blocked writing.
- The dock's panel frame was drawn only as tall as its contents. With little in the tab, the rest of the dock was left undrawn (the window's clear colour, the black area of issue 259) and the panel's stored size changed between frames (the flicker).
- While a new run's playback was prepared, the tab replaced its transport row with a "Preparing…" line, so "Skip stock simulation" dropped one row and the controls disappeared (issue 215: "the playback box moves down when the simulation runs").

## Decision

1. **One test.** A run is out of date when the export check's stale set for it is not empty: an operation it holds was removed or turned off, an operation's chained key changed (a parameter, its tool, setup, selections, the simulation settings, an operation before it), or an enabled operation is not in it. `openchuck_app::simulation_out_of_date` gives the reason in a plain sentence, in that order of precedence ("Operation 'Roughing' was turned off.", "Operation 'Finish' has changed since this simulation.", "The simulation settings have changed since this simulation.", "Operation 'Third' is not in this simulation.", with "1 more operation is out of date too." when there are more). A rename or a hidden toolpath is not a change (decision 0172 item 1). Simulate, the dock, the results inspector and the export check therefore agree.
2. **Where it is shown.** While the latest run is out of date, one banner says so in three places: over the top of the 3D view on Simulate (on the result), in the Playback tab under its controls (item 8), and at the top of the results inspector. The banner has the stale mark (the amber diamond, so not by colour alone), the title "Simulation out of date", the reason, and the Simulate step's primary action as its button ("Generate and simulate op 1", "Run simulation", or "Generate stale (n)" when the stock simulation is skipped), so the user simulates again from where they are. With no operation enabled it says "Turn on an operation to simulate again." and has no button. The old numbers (worst values, histogram, by operation) stay, dimmed to 55% opacity under "Results of the out-of-date simulation:", and the playback controls the tab still has are dimmed the same way. The result is never drawn as current, and never written: the export check already blocks a stale run.
3. **An operation turned off or removed (OI-730, the owner's answer: option A).** Decision 0172 item 3 stands. The playback run leaves the 3D view at once, because it holds a path that will not be written. The old numbers stay in the results inspector, marked as in item 2, and the dock shows the banner in place of the controls. A parameter change keeps the run drawn, with the banner, the dimmed numbers and the playback controls under the banner. The options not taken: B, keep the old run drawn and playable until the user simulates again (amending 0172 item 3); C, also hide the playback controls after a parameter change. While the project skips the stock simulation (decision 0168), the action in this state is "Generate toolpaths", which generates without the stock simulation, never "Run simulation"; with "Generate stale (n)" or "Generate toolpaths" the banner says "Generate the toolpaths again to see the effect." ("Generating the toolpaths again…" while it runs), not that it simulates.
4. **The primary action follows the run.** The overview counts Simulate as complete only while the latest successful run holds exactly the enabled operations (the generation record keeps that run's operations). A run that holds an operation turned off or removed since makes Simulate's health "Out of date: an operation in the simulation was turned off or removed", and its primary action "Run simulation".
5. **The dock is drawn whole.** The dock's contents take the whole panel, whatever the tab holds, so no part of it is left undrawn and its size does not change from frame to frame (issue 259).
6. **The transport row keeps its place.** With nothing to play (no run yet, a run dropped, or a new run's playback still being prepared), the Playback tab draws the transport buttons disabled in their places and "Skip stock simulation" after them, where the row with a run has them; the preparing line goes under it (issue 215).
7. **The controls used most do not scroll (issue 262).** The Playback tab is a strip that does not scroll (the transport row with "Skip stock simulation", the timeline and the window strip) and, under it, a scroll area for the rest (the speeds, go to move and the window fields, the readout, the view's tick boxes and the notes). The scroll area's bar takes a strip of its own, so it never lies over a control or the timeline. At the default dock height (260), at 1920 × 1080 at 100% and 120%, everything fits without scrolling; in a shorter dock, or with the banner of item 2, the strip stays whole and the rest scrolls, with its bar to say so; in a dock too short for the strip itself (down to the shortest, 120), the strip scrolls with the rest. The dock keeps the height it was given: the scroll area takes what room is left, however little (egui's 64-pixel minimum would otherwise grow the dock, to 317 of 260 under the banner). The owner saw the timeline under the floating scroll bar (maximised at 1920 × 1080); the old layout fails the new test the same way (the bar over the timeline's last move number).
8. **The banner never covers or pushes out a control (the owner's feedback on issue 260, build 0.14.0).** In the Playback tab the banner comes under the controls (the transport row with "Skip stock simulation", the timeline and the window strip, or the waiting row with no run), at the top of the part that scrolls, never above them. Above them it pushed the strip down, and in a shorter dock the dock grew past its height (to 253 of 200 at 1920 × 1080), over the footer and off the window, so the controls could not be reached. The whole-dock layout test checks the out-of-date state at 260, 200, 170 and 120, at 100% and 120%: the banner is under every control and the dock keeps its height. The banner over the 3D view covers only the view itself, no control.

## Alternatives considered

- Compare the whole project (the old line): rejected, a rename or a hidden toolpath would mark the result out of date, and it disagreed with the export check.
- Clear the results when the run goes out of date: rejected, the owner wants them kept to compare.
- A message only in the status bar or the Messages tab: rejected, the owner asks for it on the result itself and in the dock.
- Regenerate automatically on every change in Simulate: rejected for the reason of 0172 (wasteful, and not what UI-11 asks).

## Consequences

- `crates/openchuck-app`: `export.rs` (`simulation_out_of_date`), `overview.rs` (`RecordState::last_run`, the Simulate step's completeness and health, `SIMULATION_HOLDS_GONE`). An application crate: no library API change, so no version bump.
- `apps/openchuck-ui`: `shell/out_of_date.rs` (new: the cached test, the banner, the view banner), `shell/dock.rs` (the Playback tab: the dock fill, the strip and the scroll area), `shell/inspector.rs` and `results_panel.rs` (the banner and the dimmed numbers), `playback_panel.rs` (`waiting_row`, `show_strip`, `show_rest`).
- Deterministic output is untouched (GC-07, NFR-06): display and state only.
- Interface specification sections 9 and 11.5 edited.
