## Decision (proposed)

1. **Grouping (GC-05).** `OutputGrouping` has four values, set with `Application::set_output_grouping` and defaulting to `Setup` (what slice 6 built):
   - `Setup`: one file for each run of consecutive operations in one setup (a setup that reappears after another setup gives a second file).
   - `Operation`: one file for each operation.
   - `Tool`: one file for each tool in each setup run, holding every operation that tool cuts there in machining order. The files together reach the same fed moves as the setup file (tested by comparing the sorted end positions of the fed moves the replay reaches; the rapid to a group's start is written only when the position changes, so rapids differ with the grouping); the order of moves across files differs by design.
   - `Project`: one file. Because a program has one work frame and one work offset, and the operator refixtures between setups, a project with **more than one setup run is refused** with a message that names the choice of the other groupings (OI-92, narrowed). With one setup run it is the setup file under the project's name.

   Every file passes gates 1 and 2 on its own against the groups it holds. File names are `NN-<parts>.<ext>`: a running number from 01 in machining order, then the setup name (the project name for `Project`), then for `Operation` the operation name and for `Tool` `t<number>-<tool name>`; each part is lower-case ASCII letters and digits joined by hyphens, cut at 40 characters, with a fixed fallback when nothing is left. The number makes every name unique, so two operations of one name never overwrite each other. The title comment of an `Operation` or `Tool` file adds the operation or `T<n> <tool>` after the setup name.
2. **Comments (GC-06).** Each operation's comment now reads `operation <name>, tool T<n> <tool name>, about <s> s`. The operation is named by the project's operation name (the post job carries a map from the IR's operation tag to the name; a tag with no name is written as it is, so the post library still works on bare IR). Slice 6 wrote the operation's internal ID and no tool number. Text goes through the same comment cleaning as before (decision 0019 item 4, OI-84). The comment lines of the reference job goldens were already replaced by `(operation <id>)` in their tests, so those files are unchanged; the two small-part goldens in `testdata/golden/` change in the comment line only.
3. **Times (work breakdown finding 6).** The IR carries each move's duration, so the comment and the sheet show the **programmed time**: the sum of move durations at their programmed feeds, with no acceleration, tool changes or fixturing. It is labelled as such and is not the SIM-08 estimate. This reverses nothing already built (slice 6 wrote "about N s" in the comment) but it is the choice finding 6 left open, so the owner is asked to confirm it (OI-123): the alternative is to drop the time from the comment and the sheet until SIM-08.
4. **Setup sheet (GC-12).** `SetupSheet::new(&Project, Option<&Toolpath>)` in `openchuck-app` builds one document of facts and tables, which `to_html()` and `to_pdf()` both write, so the formats cannot disagree. Sections: **Job** (project, machine, counts, programmed total), one **Setup** section for each setup (part model, stock, material, work offset register and zero, part offset, clearance when set), **Tools** (only tools an operation uses, with the controller tool number, type, diameter, flutes, flute, overall and shank lengths, and the setups it is used in), **Operations** (number, name, strategy, setup, tool with number, spindle speed from the cutting data for the setup's material, programmed time) and **Notes** (what the time means and the NFR-12 notice). The page and the PDF carry no date, clock or random identifier, so the same project gives the same bytes (GC-07, tested at 1, 2 and 4 threads).
   - **HTML** is written in Rust with an escaping helper and one inline stylesheet (white paper, `@media print`, `@page A4`). It has no script, link, font or image, so it opens offline.
   - **PDF** is written by about 150 lines of in-house code: PDF 1.4, A4 pages of fixed-width text in the built-in Courier and Courier-Bold fonts, nothing embedded or compressed. A fixed-width font means a column always fits the width worked out for it. Characters outside ASCII are written as `?` (the built-in font has none), the same rule as comments.
   - **Why not the architecture's route.** The template engine's environment is configured for G-code (no auto-escape, strict undefined) and lives in `openchuck-post` only (`docs/dependencies.md`); a second environment in `openchuck-app` would add the dependency there and an escaping setting that is safe only if every template remembers it. The sheet is not user-edited in GC-12, so a template buys nothing now. `printpdf` 0.12.8, tried in a scratch crate, locks 105 packages with its default features off; the plain tabular sheet does not need that, and the fallback if layout quality matters is `pdf-writer` (survey 75) or `printpdf` (90) behind the same document model, which is the only thing the PDF code reads.
5. **Gate 2 fix found on the way.** Comparing a file that holds more than one operation failed on every project with two operations in one setup: "A travel 13860 differs from the IR's 13500". The post writes the move to a group's start as a plain rapid, so the A it turns between two groups is travel in the G-code, and `compare` did not count it on the IR side. It does now (`crates/openchuck-gcode/src/compare.rs`). Slice 6 posted one operation per setup in its tests, so it never met this.
6. **Tests and golden files.** `crates/openchuck-app/tests/output_options.rs` (names carry the requirement IDs): every grouping's names, contents and gates; the same moves in every grouping; bytes at 1, 2 and 4 threads for every grouping; refusal of a project file across setups; comment text and its cleaning; file names for odd operation names; the sheet's tools, stock and operations; escaping; offline; a PDF whose cross-reference table is checked entry by entry; a long sheet over several pages; non-ASCII. Golden files: `testdata/golden/grouping/<grouping>/` for the G-code of each grouping (the Z1 post, a cube with three operations and two tools at coarse steps) and `testdata/golden/setup_sheet/small_project.html` and `.pdf` for the sheet.
7. **Proposed edits to the documents (not made).** Architecture sections 5 and 7 and the crate selection say the sheet is HTML from the template engine and the PDF comes from `printpdf`. If item 4 is agreed, they should say: HTML and PDF are written in `openchuck-app` from one document model; the PDF writer is in-house; `printpdf` and `pdf-writer` stay the fallbacks. `docs/requirements.md` and `docs/architecture.md` are not edited here (project rule).

## Alternatives considered

- **Several setups in one project file** (a work offset line, a program stop and a comment between setups, one header and footer). Possible in the template, but gate 1 and gate 2 work in one work frame with one set of limits, so a combined file could not be checked as it stands. Refusing is honest; a combined file with per-section checks is OI-92.
- **One file per tool across setups**: files would mix work frames. Not offered.
- **Operation IDs in the comment**: stable but meaningless to the operator; the name is what the sheet and the screen show.
- **A date or version on the sheet**: it would make the bytes differ between runs (GC-07). A revision identifier can be added the way VC-06 adds it to the G-code header.
