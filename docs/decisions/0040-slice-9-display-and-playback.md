## Decision

1. **The application tells the front end which group is which.** The IR's tags are names as text (the application writes the operation's ID there), so a group cannot be mapped back to its operation, setup or tool from the toolpath alone. `Regeneration::groups` (`GroupInfo`: operation ID, setup ID, the tool's revolved profile, the placed part's bounds) runs parallel to `Regeneration::toolpath.groups`. These are application types, outside the library family's semver check.
2. **A timeline and a cursor (SIM-04; `openchuck_app::playback`).** `Timeline::new(project, run)` lays the moves of all groups end to end in program time (the sum of the moves' durations). A `Cursor` is the number of moves done and the fraction of the next. `Timeline::sample(cursor)` gives the pose (`PoseSample`): the tip and unit axis in the part's frame, A, **X, Y, Z and A as the G-code lines give them** (the work frame of the setup), the move's kind and feed, and the program time. Between two poses the controller moves X, Y, Z and A together in a straight line in machine coordinates, so the pose is interpolated there and brought back through the shared kinematics, as the simulation samples moves (record 0025 item 3); the tip therefore follows a curve in the part's frame when A turns. At a move's start or end the pose is the IR's own, exactly.
3. **Playback controls with no clock (SIM-04).** `Playback` holds the cursor, whether it plays and the speed (program seconds per second of the clock). `advance(timeline, seconds)` moves by the clock the front end gives it and stops at the end; `play` at the end starts again; `step(±n)` moves by whole moves (back from part-way into a move goes to its start first); `jump_to_move(n)` goes to just after move n, where the machine stands when the G-code line that writes it has run; `jump_to_group` goes to an operation's first move; `seek(fraction)` goes to a fraction of the program's time. A bad speed is ignored. The interface offers 1× to 10 000× and "the whole program in 10 s or 60 s". Speed is program time: feed overrides and the machine's own acceleration are not modelled.
4. **The tool at a point, and the workpiece turned by A (SIM-02).** `tool_meshes(tool)` turns the tool's profile (the same outline the tool editor draws) into a cutter solid up to the flute length and a shank above it, built with the tip at the origin and the axis along +Z. They are uploaded once; a transform places them each frame. A pose is given for two views (`ViewFrame`): **the part's frame** (the part is fixed, the tool leans and moves round it) and **the machine view** (the tool stands upright at the point the shared kinematics gives, and the workpiece with its toolpath, stock and highlights turns by `sign * A` about the rotary axis, `sign` from the machine's A sense). The interface's "Turn the part with A" switch chooses. The machine view is drawn for a rotary axis along X, the only axis the first release allows (SET-02 is P2).
5. **The renderer gains layers, slots and translucency.** `Layer` (scene, stock, paths, tool, overlay) are uploaded and replaced separately, so a pointer move, a cursor move or a visibility switch never uploads the 1M-triangle part again. `Slot` (fixed, part, tool) names a moving frame; `Frame::transforms` gives one rigid transform per slot each frame, and the renderer multiplies it into the item's matrix and carries the eye into the item's own frame, so shading follows an item that moves. A mesh can be `translucent` (drawn after the opaque ones, blended, without writing depth), for the stock around the part. `camera::{place, rotation_x, rigid_inverse}` build the transforms. Tested on a real software adapter (`openchuck-viewport/tests/render.rs`): an item in a slot lands where the slot's transform puts it, a turned item shades by its own normals, glass blends over what is behind it.
6. **Toolpaths drawn by class and by operation (SIM-01).** `ToolpathDisplay::build` cuts the toolpath into runs of one `PathClass` per group (rapid, link, entry for plunges and leads, cut), in the part's frame; a move that turns A by more than 5° is drawn as the arc the tip takes. The interface draws each class in its own colour, and each operation has a switch ("Operations shown"). Runs are joined (a run starts where the one before ended), so a polyline is not broken at a change of class.
7. **The operation flow (item 7; UI-06, UI-09).** `Application::add_operation(name, strategy, setup, tool)` and `delete_operation` are one undoable step each and refuse, saying why, an empty name, an unknown strategy (listing the choices), setup or tool; `strategy_choices` lists the registry. The interface has Add operation (menu and tree), Delete operation (the operation's panel), Generate (F5), Generate and simulate (Shift+F5), a status bar with the job's progress and Cancel, a Results window (what was generated, what was reused, notes, the G-code checks, and after a simulation the material removed and the worst remaining and overcut values with places, SIM-05), and a tag beside each operation ("generated", "reused", "out of date"). "Out of date" is a comparison of the project with the project as it was when the run started, so every kind of edit is caught. Editing is the existing parameter and selection panels; generating reuses unchanged operations by the chained cache of record 0030.
8. **Responsiveness and cancel (checklist; limits for verification plan 4.1).** The interface thread only polls (`try_result`, `drain_events`); every slow step is a job: generate, simulate, prepare the display, choose the path detail, prepare stock playback, the stock at a move, the deviation bands. Limits: while a job runs the interface thread's poll-and-draw gap stays under **17 ms**, half the 33 ms frame of NFR-03; **cancel stops a run within 2 s at the default cell** and leaves no partial result (the run is an error, the cache holds only whole operations). Measured in this container with every pool thread busy: 800 to 870 polls of a simulating job, p50 2.1 ms (2 ms of it the test's own sleep), p95 2.2 ms, worst 7.3 to 9.0 ms; cancel of the small test job 6 to 12 ms (`req_ui_09_*` in `openchuck-app/tests/playback.rs`). The first version of this test cancelled once, 20 ms in, and passed only because that landed early in path generation: a cancel from about 40 ms to 1.2 s into the run waited about 1.3 s for one batch of 32,768 poses to be cut (the macOS runner of pull request 52 took 2.07 s and failed the 2 s limit). The cut and the comparison with the part now watch the flag themselves (`DexelStock::cut_cancellable` looks every 16 poses in each row of columns; `compare_cancellable` looks before each chunk of samples), so the worst stop for a cancel asked every 10 ms across the run is 5 to 20 ms, and an uncancelled run is no slower (1.49 s against 1.64 s in a release build). The test now cancels at six points and also requires the worst stop to be under a quarter of an uncancelled run on the same machine, which a stage that ignores the flag fails whatever the machine's speed. Measured on the small test job only: OI-116 stays open for a large job, and the stock build and the checkpoint copies are not checked.
9. **Level of detail for paths of millions of moves (item 8).** `ToolpathDisplay::lines(visible, max_points)` chooses the finest of seven levels whose visible points fit the budget (**1,000,000 points**, about 24 MB of vertices): level 0 draws every point; levels 1 to 6 simplify each run to within 0.01, 0.03, 0.1, 0.3, 1 and 3 mm. A level is made the first time it is needed and kept. The error of the level in use is shown ("Drawing 666,668 of 2,000,001 points, simplified to within 0.03 mm"). The simplification is a **sleeve method** (`simplify`: Reumann and Witkam, linear in the points, deterministic) with a stated bound: every dropped point is within 0.72 of the tolerance of the line drawn. The first version used Ramer-Douglas-Peucker and took 61 s on a two-million-point spiral, because its splits are uneven on a long spiral; the sleeve takes 0.13 s (release) or 0.44 s (debug) for the same job. Measured, a helical path of two million moves: timeline 33 ms, runs 57 ms, lines 130 ms in a release build (`req_nfr_04_a_path_of_two_million_moves_is_displayed_within_its_budget`). The budget is not yet measured as a frame time on a GPU (OI-176).
10. **Simulation display (item 5; SIM-05).** The part is drawn in six bands by the worst deviation sampled on each triangle (`openchuck_sim::triangle_values` gives the value per triangle, since the samples are in triangle order and a triangle's share follows from its size): overcut deeper than the simulation's cell, on the surface (within one cell), up to 0.25 mm left, 0.25 to 1 mm, more than 1 mm or only a bound, and not measured. The viewport draws one item for each band over a shared edge item. The legend names each band with its triangle count. The stock left is a translucent closed mesh around the part. Both are in the workpiece's slot, so they turn with A in the machine view.
11. **The stock at any move, from checkpoints (item 6; SIM-04).** The pipeline's simulation keeps no checkpoints (record 0025 item 7). "Show the stock…" runs the simulation again with checkpoints at the start, after each operation and every N moves (`StockPlayback`, a job with progress and cancel), N so that about eight lie inside an operation and never fewer than 1,000 moves apart. The stock at a cursor is replayed from the nearest checkpoint (`Simulator::stock_at`, hash-equal to running up to the move, record 0025 item 4) as a job; while playing, a new request starts when the last finished, so the picture lags rather than stalls. A setup whose checkpoints would hold more than **1.5 GiB** is refused with the cell to coarsen. The stock shown is for the moves done, not part-way into the next.
12. **Where the code is.** Playback, tool meshes and timeline in `openchuck-app::playback`; runs, levels, bands in `pathview`; stock playback and the jobs in `stockplay`; adding and deleting operations in `opflow`; per-triangle deviation in `openchuck-sim`; layers, slots and translucency in `openchuck-viewport`; the panels in `openchuck-ui` (`run_panel`, `playback_panel`) with no CAM logic. No new dependency.

## Alternatives considered

- **Drawing the machine view by moving the camera:** the guides (rotary axis, A arrow, work axes) would turn with the part and the tool would not stay upright, so the picture would not be what the machine does.
- **Re-uploading the path layer for each frame of playback:** the tool and the part's turn are transforms instead.
- **Colouring by deviation with a vertex colour and a shader change:** bands are separate items over a shared edge item, so the shader and the vertex format stay as they were (record 0029 item 5).
- **Ramer-Douglas-Peucker for the levels:** better compression, but unbounded time on a spiral (item 9).
- **Checkpoints in the pipeline's simulation, so no second run:** every run would hold copies of the stock for nothing (OI-174).
- **A stock mesh updated every frame:** the stock changes at samples a cell apart and a mesh of a million triangles takes a job to make, so it follows the cursor as fast as the jobs allow.

- `openchuck-viewport/tests/render.rs`: slots, shading in the item's frame, translucency, and the matrix helpers.
- `openchuck-ui`: the path layer is drawn in class colours in the workpiece slot; the tool follows the cursor and, in the machine view, the part's transform is the rotation by `sign * A` and the tool's is the turned tip with the axis up; playing follows the frame time and stops at the end; the stock layer and the bands come from jobs; the part is drawn in one item for each band; **the whole shell draws a run without a window** (generate and simulate, results, add-operation dialog, selection panel, edit then "out of date", generate again, cancel).

## Open items

- **OI-174:** stock playback simulates again with checkpoints (twice the simulation time), and holds a copy of the stock for each checkpoint. Keep the checkpoints in the pipeline's run when playback is wanted, or store them compactly (changed columns only).
- **OI-175:** playback shows the position (X, Y, Z, A) the G-code line leaves the machine at, but not the line number. The mapping is tested; showing the line needs the post to say which IR move each line writes.
- **OI-176:** the 1,000,000-point budget and the 17 ms and 2 s limits are measured in one cloud container on the CPU side. Run the NFR-03 frame-time benchmark with a million-point path layer and the tool on the reference machines (verification plan 4.2).
- **OI-177:** the level of detail does not follow the zoom: it is one level for the whole path by tolerance in millimetres. Choose the level from the pixel size and draw full detail only near the cursor.
- **OI-178:** the path is drawn as the tool tip's polyline. A tool axis that tilts (simultaneous finishing, lane I) is shown only by the tool at the cursor, and the part of the path already done is not drawn differently from what is to come.
- **OI-179:** the machine view assumes the rotary axis is X; the tool and stock are drawn without a tool holder, and the stock mesh is blocky at the cell size (OI-115: colouring is done, smoothing is not).
- **Progressed:** OI-115 (the stock mesh is drawn and the part coloured by deviation; smoothing is not), OI-116 (the cut and the comparison watch the cancel flag; not yet measured on a large job), OI-132 (playback re-simulates for its checkpoints, OI-174).


## Issue 333 correction (25 Oct 2026)

The owner's instruction to fix issue 333 supersedes item 11's deliberate
lag and whole-move-only display. SIM-02/03/04 playback now includes the
machine-linear swept prefix of the current move. Completed moves still replay
from checkpoints; the prefix is cut on a temporary stock and never changes
pipeline simulation results, checkpoints or posted output.

The viewport publishes a completed stock surface together with the tool pose,
A rotation and tool readout for that exact cursor. While the next surface job
runs, it retains the previous matching pair. Playback time can continue advancing,
so expensive stock preparation limits visual update frequency without placing
the tool ahead of the displayed material removal. With Cut part hidden, tool
animation follows the clock directly as before.
