## Context

The owner's trial of the nightly build (F-36, F-37, F-38) found the tool library list flat: the library's tools are grouped by type only, whichever machine they belong to; the groups cannot be folded; the list cannot be filtered by size; and a default tool opens in the same editable form as the owner's own tools, with no way to see its dimensions as a drawing. TL-11 gives each machine a default tool set kept with the library; TL-12 ships the Makera Z1 reference tools and common standard tools, and says the user can edit, add and delete tools and that an update never overwrites a tool the user has changed.

## Decision

1. **Sections (owner's answer, issue 192).** The library's tools are listed in a section for each machine whose tool set (TL-11) holds them, in machine-name order, then a section **"Standard tools"** for the tools no machine's set holds. Inside a section the tools are in type groups in the order of the existing list (ball end, flat end, bull-nose and tapered, V-bit, chamfer and drill, custom profile), each group's tools by name with numbers in order (2 mm before 10 mm). A tool that two machines' sets hold is listed in each. An empty group or section is not shown. The section's title is the machine name as its tool set file gives it (OI-770). "This project" stays first and is not a section.
2. **Folding (owner's answer, issue 192).** Every section and every type group has a heading that folds and unfolds on a click, drawn with an arrow and the number of tools inside, "⏷ MAKERA Z1 (3)". Everything is unfolded at first.
3. **Remembered (owner's answers, issues 192 and 193).** Which sections and groups are folded, and the size filter, are kept between runs, per user on the computer, in the `settings.toml` of specification section 13: a new `tool_library` table of the `[interface]` table, with `folded` (a list of keys) and `filter`. The table is additive and the file has no version number, so a file written before it reads as unfolded with no filter, and **no project or library file changes and no schema number is taken** (the issue asked for a schema claim only if a file changed). A section's key is `standard` or `machine:<name in lower case>`; a group's key is its section's key, a slash and the group's short name (`machine:makera z1/ball-end`). The window folds and filters with the state it was given when it opened, and the shell writes the settings when the state changes.
4. **The size filter (owner's answers, issue 193).** Under the search box, "Diameter (mm)" and "Flute length (mm)", each with three small boxes: exact, min and max. An exact value shows tools of that size (within 0.0005 mm) and, when given, the range beside it is not used; a minimum and a maximum show the tools between them, both ends included; either end alone is a one-sided range. The two filters and the search all apply together, and a filter hides the tools it excludes and the groups and sections it leaves empty. A box that cannot be read (not a number, negative, or a minimum above the maximum) is not used, and a line under the filter says which and why, so a typing slip never hides every tool. **No reset:** the filter keeps its state when the window is closed and opened again, and when the program is restarted. **"Clear filter"** empties the boxes by hand; it is disabled while they are empty.
5. **Default tools are read-only (owner's answers, issue 194).** A library tool that is a default tool exactly as the application ships it (the same ID and the same content as the embedded default, TL-12) opens in a read-only view: its name, type, the dimensions that make it up (diameter, flute length, overall length and shank diameter, and corner radius, tip radius and taper angle, included angle and tip diameter, or point angle, where the shape has them), flute count and tool material; the tool's profile drawn as the profile editor draws a custom profile's revolved silhouette, with nothing to edit; and the cutting data by material as a table with no "Add material" and no editing. The view says "A default tool: it cannot be edited". **"Copy to edit"** (the primary button of the view) makes an editable library draft of the tool, named "<name> copy" with a new ID, exactly as Duplicate does (decision 0127 item 4); the default tool is not changed (TL-12). A default tool the user changed in an earlier run is the user's tool (it no longer equals the shipped one) and stays editable, so no edit already made is hidden. Deleting a default tool is unchanged (decision 0127 item 5).
6. **What stays editable in a default tool's view (a lane choice, OI-771).** The machine tool set numbers (TL-11) in the right column stay editable, with Save and Cancel as for any library tool, because the number is the machine's property and "tool numbers belong to the project, not to the library tool" (TL-11); editing one does not change the tool's own content.
7. **Wording.** Plain words, as decision 0114 asks; nothing in the new text says that a value is safe to run (NFR-12).
8. **Esc in a text field (OI-536).** Esc in a text field of the tool library window ends the edit and does nothing else; Esc a second time, with no field editing, closes the window (OI-526). The first version asked egui whether a field had the keyboard at the start of the frame, but egui takes the keyboard from a field as an Esc frame begins, so that Esc also closed the window (a CodeRabbit finding on pull request 173, never registered; the coordinator numbered it OI-536 on 20 Oct 2026). The window now keeps whether a field had the keyboard when the last frame ended and closes on Esc only when none had.
9. **The shared material list (the owner's relayed decision).** The tool library's cutting data material is picked from a list shared with the operation's material, or typed as a new name. That is already built by lane BUG-SPINDLE on `claude/lane-bug-spindle` (`openchuck-app::materials::known_materials` and `canonical_material`, "Pick…" in the cutting data editor; its decision 0196). This lane builds no second list and does not touch it; it reads "material" as the stock material that cutting data is keyed by, not the tool's own carbide or HSS field (confirmed by the coordinator). The tool's own material list (carbide, HSS, cobalt HSS) is unchanged. Whichever lane merges second rebases on the other (`tool_library_window.rs`, `tool_library.rs`).

## Alternatives considered

- **Keep the fold and filter in the library folder.** They are about one user's view, not the tools, and a library can be shared (import and export, TL-01); a library file change also needs a schema claim. Rejected: the per-user settings of section 13.
- **Fold with egui's collapsing header.** It keeps its own state in egui memory, which is not saved with the settings and is hard to test; the heading is drawn by the window so the state is in one place.
- **List a tool once, under its first machine.** A tool two machines hold would then be missing from the second's section; listing it under each is what a section of "the machine's tools" says.
- **Make every default tool editable in place and mark it.** The owner asked for a read-only view with a copy; an edit in place also risks the TL-12 rule that an update never overwrites a changed tool.

## Consequences

The library list is longer by the section and group headings; folding and the filter shorten it. A default tool cannot be changed without making a copy; the copy is a new library tool, so a machine tool set that names the default keeps naming it until the user changes the set (OI-772). The board `ToolLibrary.dc.html` (image 10) shows the earlier flat list (OI-773).
