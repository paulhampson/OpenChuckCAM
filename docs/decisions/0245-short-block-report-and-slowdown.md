## Evidence and need

Owner [results in #284](https://github.com/paulhampson/OpenChuckCAM/pull/284#issuecomment-6399134358): OpenChuckCAM 0.20.0, Windows, Z1 firmware 1.1.2, WiFi upload, ESP32 version not supplied. Parts A and B both passed 20/10/7 ms and stuttered at 5/3/2/1 ms. The 7 ms sections measured 6.1 and 5.9 seconds against 6.0 predicted. This is the shortest tested smooth value, not an exact universal boundary or a proof of which supply stage is responsible.

The accepted investigation found the owner's pencil path demanded a 5.6 ms average over 32 blocks. Reporting and mitigation are justified. The reference jobs mostly have much longer blocks. Do not impose a universal minimum or relax the geometric tolerance to hide command demand.

## Implementation

1. Machine profile: `min_block_ms` (finite, >=0), `block_window` (1..4096), `short_block_mode` (Off, Report, Slow down), with per-field provenance. Optional post overrides independently replace each field. Zero or Off disables analysis. The window cap bounds work and allocation; default window is 1.
2. New built-in Z1: Report, 7 ms, 32 blocks. The 7 ms value records the owner's hardware evidence; 32 is source-based planner depth, not a new measurement. Copies predating the timing fields load as Off; published 19/5 Off/Report copies retain their saved mode. Editing the profile preserves its library ID and marks edited fields as user-provided/unconfirmed. Mode is a policy choice, not a physical measurement.
3. Analyse actual emitted fed blocks using rounded positions, controller feed rule, feed-word rounding and post feed clamp. Consecutive groups and rapid moves split runs. A short run uses `min(N, run length)` so boundaries do not suppress all checks. An isolated short block can otherwise be absorbed by a compliant window.
4. Report changes no G-code or original duration estimate. Per operation it shows individual short moves and their longest run, deficient windows, worst mean, effective contact feed, and the predicted slowdown time including feed rounding.
5. Slow down processes windows in order. It raises the shortest durations first, sharing increases among equally short blocks with stable input-order ties. Increasing durations cannot invalidate a previously repaired window. Feed rounding is conservative: the selected written feed is at or below the calculated cap. No feed is increased, coordinate or move kind changed, merge introduced, or tolerance consumed. This is a deterministic feasible adjustment, not a claim of globally minimum added time or acceleration-optimal feed scheduling.
6. Post results return adjusted verification durations. Gate 2 checks them, and setup sheets/export use the same run's reports and time. Active command management rejects the legacy Contact feed rule because its rotary timing does not identify a controller interpretation; Off retains legacy compatibility. Makera, LinuxCNC and G93 rules retain their respective controller interpretation.
7. Public profile/post/report API additions initially used 0.22.0. Released integration now uses **0.24.0**, the next free library-family version after main's 0.23.0 and an audit of all live remote refs. GATES' `PostJob.block_time`/`BlockTimeSettings` API and standalone complete-window original-IR `block_time_reports` semantics are retained. Managed actual-post-duration reports retain the distinct metrics and short-run rule above; application flows use only these to avoid duplicate or inconsistent warnings. Legacy output reports are omitted in Slow down so they cannot claim its G-code is unchanged. Genuine pre-field projects retain Off, premature fields are refused, and GATES' implemented 19/5 schema steps remain intact before 20/6. Existing 19/5 Off/Report files migrate without changing their setting; a `slow_down` value in a 19/5 file is refused as premature and requires the 20/6 format rather than silently broadening the older schema. Unrelated gate evidence and waivers are preserved.

### Configuring a machine (user-facing, kept with the record pending the owner's answer on where machine guidance lives)

The machine inspector exposes Minimum block time (ms), Block window and mode; `machine.toml` has `min_block_ms = 7.0`, `block_window = 32`, `short_block_mode = "report"`. A post definition can override any field independently under `[options]` (an omitted `block_window` keeps the project's machine value). Report changes no G-code and estimates demand and slowdown cost; Slow down lowers affected feeds and keeps coordinates and geometry (a larger target trades time and cutting feed for processing margin and does not change the geometric tolerance); Off or zero disables analysis; merge stays deferred because it would consume geometric accuracy budget. The built-in Z1 starts at Report / 7 ms / 32 (firmware 1.1.2 over WiFi); copies predating the fields stay Off until the user edits or updates them, and saved Off/Report settings keep their mode. Unknown machines need their own measurements; do not copy the Z1 threshold. The Files area and setup sheet show the effective settings and their source (machine or post override, including overrides that disable analysis). Calibrate with sustained sections that exceed the controller's buffering and with representative line lengths and rotary commands; record firmware and delivery path; use the shortest setting that repeatedly passes the agreed smoothness criteria; repeat when firmware, delivery or configuration changes; feed override above the calibrated setting can invalidate the target.

### First-cut far-end tab: underflow-like motion at 100% override (OI-993; owner report, 25 Oct 2026)

The exact file, operation, line and location were not available. Examined `testdata/golden/first_cut/first_cut_makera-z1.nc` from #284's head `9573685001117c4e71a236c555f34138fb21cbad` (blob `2130bf92f782bc7fa79587d41e361ce138d2ca07`; may differ from the program run). Setup: stock X0..100, head-held region X0..68, tab X68..73, part offset 73, tail-held section X98..100 (10 mm diameter), both tools 3.175 mm. For blocks touching X >= 90, roughing has 4,058 fed blocks and finishing 940, none below 7 ms (shortest 83.327 ms, lowest 32-block mean 83.328 and 83.327 ms). The only block below 7 ms in the whole program is line 12957 (X71.413, nominal 2.279 ms) near the head-side region, so the 7 ms / 32 mitigation would not change this program. At the end of roughing, line 12663 is the last mixed X/Z/A motion (ends X95.912), lines 12664 to 12735 are **72 A-only blocks of 5 degrees** (one extra turn at fixed XYZ, nominal 6.606 s under the Z1 rule; intentional end turn where a held region truncates a continuous pass, decision 0161), line 12736 a fed retract to Z18.509 at F300 (2.555 s), then rapid to Z50, non-moving counter reset, spindle stop and tool change. **Hypothesis (inference from firmware source, not measured):** at the known revision `b3a2e26`, `Robot.cpp:1724` passes `nullptr` instead of a direction vector to the planner for auxiliary A-only motion and `Planner.cpp:172` initialises junction speed to the minimum planner speed (default zero), with junction blending only for a non-null vector; the documented build has `PAXIS=3`. The ring may therefore stop and start at each 5 degree boundary with a full buffer, which would resemble underflow with a different cause: at the published A acceleration of 360 degrees/s^2 a 5 degree rest-to-rest move takes about 236 ms instead of 92 ms (about 17 s for the ring instead of 6.6 s). Command demand there is about 12 commands/s against roughly 143/s at the tested 7 ms setting, so sustained supply starvation is unlikely for this file. The #284 test used X-only and mixed X/A motion, both with primary-axis vectors, so it does not validate A-only junction blending. Next verification: establish whether the symptom occurs in roughing's stationary-X ring, in finishing or in the retract and tool change; compare, at identical safe fixed XYZ, feed and total A travel, repeated small A-only blocks against one monotone A-only block, after the static, replay and simulator gates, in the attended no-tool air-cut procedure. Do not merge the ring or change firmware under GC-17 automatically; merge stays deferred by 0222; if confirmed, assess exact constant-XYZ rotary-span coalescing separately with independent swept-path verification. Raising block time alone cannot restore missing junction blending.
