## Decision

1. Checkpoint only the committed project. Exclude unconfirmed field text, library/workholding drafts not yet Saved/Applied, generated data, and running generation state. Reuse `openchuck-project::file::render` and `load_files` to preserve complete persisted state, stable IDs, order and model references. In-app version control is not built; introducing Git machinery adds complexity and cannot improve this project-only recovery contract.
2. Keep three periodic checkpoints and one independent interim checkpoint inside `.openchuck-recovery/` in the project folder. Its generated `.gitignore` ignores the directory contents, including itself. Do not edit the user's ignore files or enumerate recovery files as normal project files.
3. The periodic interval defaults to three minutes and is configurable per user in whole minutes from one to fifteen. Confirmed changes also request an interim checkpoint after fifteen seconds without another confirmed change. Interim writes replace only the interim slot and never postpone the periodic deadline. Skip unchanged states within each series; schedule periodic capture even when an interim already holds that revision. Continue observing edits during writes; serialize publication jobs and reject stale completions. Failed writes preserve prior data and retry after a short delay with a visible error.
4. The independent recovery format starts at version one. A container holds metadata, the complete map of project-file texts, and a checksum covering metadata and contents. Validate it before publication and recovery. Bound a container to 64 MiB of encoded text; larger states give a clear error and retain the last good checkpoint. This changes neither project schema 18 nor model files.
5. Flush a complete container to a unique staging name, then publish its immutable final name. Only afterward rotate validated checkpoints in the same series. Reserve ordering independently of wall-clock timestamps and preserve interrupted or corrupt files with a clear diagnostic. Process interruption cannot make a partial multi-file snapshot appear valid. File contents are flushed on all platforms; directory flushing is used where supported. Full power-loss durability on every filesystem is not promised.
6. One process owns recovery writing for a project through an OS file lock, released by the OS after termination. Recovery identity and session/revision metadata live only in recovery storage. Save retirement uses captured session/revision boundaries, never asynchronous completion time. A stale job cannot replace a newer checkpoint or retire newer state.
7. A per-user index remembers canonical project folders containing recovery data; equivalent paths are deduplicated. Startup discovery runs in the application layer. A live writer is not a crash. Moved or inaccessible folders retain their index entries and offer Locate; opening a moved folder also rediscovers its snapshots. An arbitrary moved folder cannot be found without opening or locating it. Identity checks prevent a reused path from silently being treated as the original project.
8. Recovery presents all retained valid choices, labelled with project, folder, capture time and periodic/interim type. The user chooses; do not silently restore the newest. Decode into unsaved memory and require ordinary explicit Save to change saved project files. Missing or changed referenced models produce warnings: model bytes are not backed up, selections may no longer match, and generated output must be regenerated and verified.
9. A successful Save retires only recovery states it covers; newer state remains eligible. Retired snapshots remain until normal retention replaces them. Clean exit retires the session only after pending edits and Save/discard are resolved. Cancel leaves it active. Wait asynchronously for close processing before closing the window. Keeping the saved project dismisses existing recovery prompts without deleting snapshots; deleting recovery data requires explicit Discard. Corrupt/partial data remains preserved and cannot prevent choosing another valid checkpoint.
10. Persistence belongs in `openchuck-project`; timing, worker jobs, discovery and retirement orchestration belong in `openchuck-app`; the UI presents settings, choices and errors. No new third-party dependency or `git2` use is needed. Preserve decision 0233's pending-edit guard and the existing explicit Save/Apply boundaries.

## Verification and limitations

Requirement-first tests cover timing, retention, deterministic contents, identities, malformed/incompatible/truncated input, referenced models, OS ownership, stale jobs, Save/close races, recovery without saved-file writes, and Git/enumeration exclusion. Kill subprocesses at publication/rotation boundaries; exercise write/cleanup failures on disposable projects. Add the reader to malformed-input fuzzing. Measure uninstrumented latency, memory and UI frame gaps on representative synthetic projects. Run changed-crate coverage, inspect uncovered lines, remove instrumentation artifacts, and follow the repository's long-test and ten-minute-stop rules. Native Windows/macOS interaction, filesystem durability and reference-hardware responsiveness require evidence distinct from headless Linux tests. Report incomplete checks and remaining gaps without claiming success.

OI-989 tracks native/reference-hardware verification. It is selected under the owner's numbering authorisation after the remote-ref audit found no open-item number above 988. Record acceptance and local automated results do not close that verification item.
