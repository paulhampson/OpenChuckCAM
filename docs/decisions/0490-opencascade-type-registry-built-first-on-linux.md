## Context

The nightly job "AddressSanitizer on the STEP wrapper" failed six nights in a row, for two different reasons:

1. **27 to 30 Oct (jobs 122073506885, 122711993493, 123341882072, 123970250056): the build failed.** The asan OpenCASCADE cache missed, and `occt-sys`'s CMake configure failed on the `ubuntu-latest` image (now Ubuntu 26.04, CMake 4): "Compatibility with CMake < 3.5 has been removed". This is the cause of issue #451; `nightly.yml` did not set `CMAKE_POLICY_VERSION_MINIMUM`. Pull request #452 sets it for the whole workflow, so this record does not repeat it.
2. **31 Oct and 1 Nov (jobs 124488754905, 124806195221): a real memory error.** Once `occt-cache.yml` had seeded the `ubuntu26` asan install, the job built and AddressSanitizer reported a heap-use-after-free (READ of size 8) in `openchuck-step-worker`. The block was 8872 bytes, allocated with `operator new` during `main` and freed by an exit handler, and the bad read was in a later exit handler. Three tests failed both nights: `req_nfr_13_the_worker_exits_cleanly`, `req_nfr_13_the_worker_reports_a_bad_file_with_exit_code_two` and `req_nfr_06_the_answer_is_byte_identical_between_runs`. These are the same three tests whose SIGSEGV on 26.04 was OI-1003 (decision 0251, cause not established).

No commit caused it. The last green sanitizer night was 26 Oct (run 40288012911, `e2189f07`); between it and the first red one (`008e38f9`) only #357 (documentation) and #363 (a CI path filter) landed. The trigger is the runner image.

## Findings

- **The shipped Linux worker crashes at every exit.** `openchuck-step-worker` from the nightly pre-release archive `openchuckcam-nightly-20261101-0b3978885-x86_64-unknown-linux-gnu.tar.gz` (sha256 `d626a6a1…`, as the release lists), run alone: `testdata/step/valid/cylinder.step` exit 139 (SIGSEGV) with its answer written (17348 bytes); `valid/filleted_box.step` exit 139 (123614 bytes written); `broken/garbage.step` exit 139 instead of 2 (its error written). The same holds in an Ubuntu 26.04 chroot and on an Ubuntu 24.04 host, so the fault is in the build, not in the system it runs on. The application still imports, because `step.rs` accepts a non-zero exit when `out.json` was written; NFR-13's clean exit was broken.
- **Stack** (gdb on the shipped binary, which is not stripped): `strcmp`, then `std::_Hashtable<const char*, pair<const char* const, Standard_Type*>, …, Standard_CStringHasher>` (erasing from the registry), then `Standard_Type::~Standard_Type()`, then `opencascade::handle<Standard_Transient>::EndScope()`, then `NCollection_DataMap<handle<Standard_Transient>, int>::DataMapNode::delNode`, then `NCollection_BaseMap::Destroy`, then `NCollection_DataMap<…>::~NCollection_DataMap()`, then `__run_exit_handlers`. The 8872-byte block of the AddressSanitizer report is the bucket array of the registry's `std::unordered_map`.
- **Cause.** OpenCASCADE 7.8.1 keeps its type registry in a function-local static (`GetRegistry()` in `src/Standard/Standard_Type.cxx`). Its own comment says the namespace-scope `theType = STANDARD_TYPE(Standard_Transient)` in the same file is there "to initialize theRegistry map as soon as possible to be destroyed the latest". `src/StepAP214/StepAP214_Protocol.cxx:754` (TKDESTEP) has `static Interface_DataMapOfTransientInteger types(819);` at namespace scope, and the STEP read fills it with `Handle(Standard_Type)` keys. C++ destroys statics in the reverse order of their construction. In the shipped binary's `.init_array` (88 entries), `_GLOBAL__sub_I_StepAP214_Protocol.cxx` is entry 2 and `_GLOBAL__sub_I_Standard_Type.cxx` entry 87, the last, because `build.rs` links Linux in dependency order (TKDESTEP first, TKernel last). So the registry is destroyed first, and the map's destructor then drops the last handles to type descriptors, whose destructors erase themselves from the freed registry. This is decision 0003's exit crash; decision 0003 recorded Linux as unaffected.
- **Reproduced and fixed in an Ubuntu 26.04 environment** (Ubuntu 26.04 base image in a chroot: GCC 15.2.0, GNU ld 2.46, CMake 4.2.3, rustc 1.97.0; OpenCASCADE built by `occt-sys` with `CMAKE_POLICY_VERSION_MINIMUM=3.5` in 21 min). Before the change, `cargo test -p openchuck-import --features kernel --test step`: 15 passed, 3 failed (the same three). The `openchuck-app --features kernel-tests --test step_exact` binary, which reads STEP in-process through the kernel oracle, passed its 2 tests and then ended with SIGSEGV, so it failed too. After the change: 18 passed; the import crate's unit and integration tests all pass (14 + 18 + 14); `step_exact` 2 passed and exits cleanly; the worker exits 0 on `cylinder.step` and `filleted_box.step` and 2 on `garbage.step`. In the new binary the priority initialiser is `.init_array` entry 1, before StepAP214_Protocol's (entry 3).
- **Not established: why builds on the Ubuntu 24.04 image did not crash** with the same link order (the sanitizer job up to 26 Oct and the pinned STEP kernel leg pass). GCC 13 and GNU ld 2.42 there, against GCC 15 and ld 2.46 on 26.04, may place the registry's first construction differently. A comparison build was started here but not finished, for lack of disk space in the container. The fix does not depend on the answer: it fixes the order whatever the linker does (OI-1700).

## Decision

1. **The registry is built before every other OpenCASCADE static on Linux** (owner's option A). `cpp/occ_step.cpp` has a namespace-scope object with `__attribute__((init_priority(101)))`, compiled on ELF with GCC or Clang, whose constructor calls `STANDARD_TYPE(Standard_Transient)`. GCC and Clang run initialisers with a priority before all default-priority ones (the linker sorts `.init_array.<priority>` sections first), whatever the link order, so the registry is constructed first and destroyed last. This keeps decision 0003's rule that the worker ends by returning from `main` with every destructor run, and that the tests check a clean exit on every platform. macOS and Windows keep linking TKernel first (decision 0003). OpenCASCADE's memory manager is itself a function-local static (`Standard.cxx`, `Standard_MMgrFactory`), so calling into TKernel this early is safe. The object file is always linked, because it is the one that defines the C ABI the Rust side calls.
   - Rejected: B, the worker ends with `_exit` and skips static destruction. It fixes only the worker (the in-process oracle above crashes too), hides teardown faults from AddressSanitizer, and reverses decision 0003's clean-exit rule. C, TKernel first on Linux inside `--start-group`: it depends on the archive member pull order and `.init_array` placement, which is what changed between images. D, A and B together: more change for no gain.
2. **The STEP kernel job's Linux leg runs on `ubuntu-latest` again** (owner's option A, proof (i)). `ci.yml` `step-kernel` and the `occt` job of `occt-cache.yml` lose their `runner: ubuntu-24.04` field (decision 0251 items 1 and 3 end). The cache key keeps the image (decision 0251 item 2), so the 26.04 build gets its own `ubuntu26` plain install: the first run after this change (this pull request) rebuilds OpenCASCADE once on Linux, about 21 minutes. This leg is now the pull request guard against shipping a Linux worker that crashes at exit, since `build-archives.yml` and `release.yml` build the shipped worker on `ubuntu-latest`. The `ui-smoke` pin (decision 0250, OI-1002) is a different crash (Mesa llvmpipe in `openchuck-viewport --test render`) and is not changed here; OI-1002 notes that it should be re-checked.
3. **A nightly job can be run alone** (owner's option A, proof (ii)). `nightly.yml`'s manual trigger gains the input `only`: empty runs every job, as before; `fuzz`, `step-mutations`, `sanitizer`, `long-tests` or `beta` runs that job alone. Each of those jobs has `if: (!inputs.only) || inputs.only == '<id>'`, which is true on the schedule (no inputs). The issues job is unchanged; it runs on `main` only and treats a skipped job as "no issue action", so a narrowed run on `main` neither closes nor opens an issue for the jobs it skipped (decision 0102 amended to say so).
4. **AddressSanitizer reports are symbolised.** The sanitizer job finds `llvm-symbolizer` (on the `PATH`, or the newest `/usr/bin/llvm-symbolizer-*`, or installs the `llvm` package) and sets `ASAN_SYMBOLIZER_PATH`. Issue #369's reports gave addresses only.

## Verification

- Test first: the three requirement tests named above, and `step_exact`, failed on the 26.04 build before the change and pass after it (Findings).
- In CI: `STEP kernel (ubuntu-latest)` on this pull request runs on Ubuntu 26.04 after a cold OpenCASCADE build, uninstrumented.
- AddressSanitizer: one manual run of `nightly.yml` on `claude/lane-sanitizer` with `only: sanitizer`, authorised by the owner for this decision: run 41305677193 (job 124845447902, 1 Nov 2026, commit `b10f9768`) passed in 4 min 27 s from warm caches. `--test step` 18 passed (the three tests above included), `--test stl` 14 passed, `step_exact` 2 passed; `ASAN_SYMBOLIZER_PATH` was `/usr/bin/llvm-symbolizer-22`; the other nightly jobs and the issues job were skipped.
- **After merge:** the owner checks a new nightly pre-release Linux archive: `openchuck-step-worker` alone on a valid `.step` file exits 0, and on `testdata/step/broken/garbage.step` exits 2 (OI-1700). Issue #369 closes itself on the first green nightly (decision 0102).

## Consequences and limits

- The fix depends on GCC/Clang `init_priority` on ELF. A Linux build with another compiler would lose it; the STEP kernel job on `ubuntu-latest` would show it.
- The pin of decision 0251 is gone, so the Linux STEP kernel job again tests the toolchain Ubuntu 26.04 users get.
- `occt-cache.yml`'s daily seed now writes the `ubuntu26` plain key; the `ubuntu24` key it wrote is no longer read and ages out of the cache.
