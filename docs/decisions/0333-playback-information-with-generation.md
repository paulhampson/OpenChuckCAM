## Context

Since [decision 0025](0025-slice-7-simulation.md) the pipeline's simulation keeps no checkpoints, and playback ("prepare playback") runs the whole simulation again with them ([decision 0322](0322-simulate-playback-frame-cost.md)). After [decision 0332](0332-simulator-skips-sure-misses.md) made the simulator about four times faster, the owner was asked again (D2) whether the pipeline should keep the checkpoints itself: playback would open at once, but every run would hold up to the playback memory (about 1.2 GB on the carving test piece) and take a little longer. The owner chose both, as a setting.

## Decision

1. **The pipeline keeps playback's checkpoints when the setting is on.** Only a run that simulates every operation it makes (the Simulate step's run, `Application::start_simulate`, and generating with the simulation) keeps them; a run that does not simulate never does. Each setup's simulator keeps a checkpoint at the start and after each operation, and inside each operation every so many moves. The number of operations is known before the first is simulated, but not their moves (an operation is generated against the stock the ones before it left), so each operation, as it comes, gets an equal share of what is left of the memory after the copies still to be kept (one after each remaining operation, and the two a replay holds): its checkpoints are spaced to fill that share, never closer than 1,000 moves. A short roughing at the floor uses little, so nearly all is left to the long finishing after it. The checkpoints of every setup together never pass the memory: a checkpoint that would is not kept (it never stops the run). The stock, the toolpaths and the G-code are the same either way: checkpoints only end a batch of poses, and a column takes its poses in the same order.
2. **Playback takes them.** `Application::start_stock_playback` uses a setup's checkpoints from the run when the run kept them for every operation of that setup, and simulates the others again as before; a playback made wholly from the run says so (`StockPlayback::from_the_run`). The stock at every move is the same as playback prepared by simulating again. A run made with the setting off, or a setup whose stocks came from the cache of such a run, is prepared as before.
3. **Shared, not copied.** A checkpoint holds its packed stock behind a shared pointer (`Checkpoint::stock` is an `Arc<PackedStock>`), so the pipeline's cache, which keeps a copy of a setup's simulation after each operation (decision 0190), the run's report and playback hold the same bytes. Changing the setting drops the stocks the cache keeps (the toolpaths stay), so the next run simulates again and keeps the checkpoints, or not.
4. **The removed volume is reported from the stock.** Each operation's removed volume is now the stock's volume before it less after it, instead of the sum of each batch's removal: checkpoints end a batch, and a sum grouped by batch would differ in the last digits between the setting on and off. The figure is the same either way; it may differ from the one reported before this change in the last digits (it is shown rounded).
5. **The setting.** "Generate playback information with toolpath generation" in Settings, under "Memory for playback checkpoints", kept in the user's settings (`[interface.simulate] playback_with_generation`, unset by default; a file written before it reads it unset). Unset, the computer's default applies: on with 16 GB of memory or more, off below and when the memory cannot be read. A computer sold as 16 GB reports a little less (memory the system keeps for itself), so 15 GB or more counts. Settings names the default this computer gives ("On by default on this computer (32 GB)", "Off by default on this computer (8 GB)", or that the memory could not be read), offers "Use this computer's default" once the user has chosen, and explains the trade-off in plain words. When on, the memory is "Memory for playback checkpoints", capped at a quarter of the computer's memory as before ([decision 0322](0322-simulate-playback-frame-cost.md) item 5). A change applies from the next generation.

## Results

Carving test piece of [decision 0332](0332-simulator-skips-sure-misses.md) (`CarvedRelief::STANDARD`, 538,433 moves in 2 groups), 4 threads, the default 1,536 MB, `playback_times` with and without `on`:

| Setting | Generate and simulate | Prepare playback | Checkpoints | Peak while generating | Peak after preparing playback |
| --- | --- | --- | --- | --- | --- |
| Off | 44.4 s | 26.2 s (simulated again) | 541, 1,194 MB | 626 MB | 2,214 MB |
| On | 44.1 s | 1.3 s (from the run) | 541, 1,194 MB | 1,718 MB | 2,244 MB |

With the setting on, the run keeps the same checkpoints as playback prepared separately keeps (the finishing gets nearly all of the memory), the generation takes no measurably longer (keeping the checkpoints costs about 2 s of the simulation's 19 s, within the run-to-run spread here), and the cut part plays after about 1 s instead of 26 s. The cost is memory: the run holds the 1,194 MB of checkpoints for as long as its result is shown, whether or not playback is used. On the owner's project (a stock of about 7 MB, 1,536 MB) the same is expected: preparing playback from 97 s (25 to 35 s after decision 0332) to about 1 s; not measured (OI-1320).

A first version sized each copy by the stock as held, not packed; it kept 301 checkpoints in 664 MB, so jumps replayed further than needed. Each operation's share is now counted in copies of the size of the last checkpoint kept.

## Tests

- `req_sim_04_req_nfr_06_checkpoints_kept_while_simulating_replay_any_move` (`openchuck-sim/tests/simulation.rs`): checkpoint spacing set for each group as it comes gives the same stock as none; a simulator rebuilt from those checkpoints gives the stock at any move as running up to it does; a clone shares the copies; checkpoints that do not start at the start are refused.
- `req_sim_04_req_nfr_07_each_operation_shares_the_checkpoint_memory` (`openchuck-app` `pipeline.rs`): on the owner's project's numbers, a roughing of 12,217 moves keeps a checkpoint every 1,000 moves and the finishing after it every 1,300 to 1,450; the copies, the one after each operation and the replay's fit the memory; a second setup counts what the first holds; no room gives none, and no count wraps.
- `req_sim_04_req_nfr_06_playback_from_the_runs_checkpoints_shows_the_same_stock` (`openchuck-app/tests/playback.rs`): a project of two operations in one setup gives the same G-code, toolpaths, stock and removed volumes with the setting on and off; the removed volumes add up to what the stock lost; playback with the setting on is made from the run and shows the same stock at about 40 points along the run, at each move and half way through it, as playback prepared by simulating again.
- `req_nfr_07_req_sim_04_the_runs_checkpoints_keep_to_their_memory` (`openchuck-app/tests/playback.rs`): with memory for about eight copies, the run's checkpoints hold no more than that, the stock is the same, and playback from the run shows the same stock as one prepared with the default memory; turned off, the next run keeps none.
- `req_ui_15_req_sim_04_playback_with_generation_is_personal_and_defaults_to_the_computer` (`openchuck-app/tests/settings.rs`): unset by default, unset when read from an older file, and kept on, off and unset.
- `req_sim_04_req_nfr_07_playback_with_generation_is_on_by_default_from_16_gb` (`openchuck-ui` `memory.rs`): on at 32 GB, at 16 GB and at a 16 GB computer's reported 15.5 GiB, off at 12 and 8 GB and when unknown; the GB named in Settings.
- `req_ui_15_req_sim_04_settings_sets_playback_information_with_generation` (`openchuck-ui` frame tests): the line and the default note in Settings at 32 GB, 8 GB and unknown memory; the user's choice and "Use this computer's default"; the application given the memory when on (capped at a quarter of the computer) and none when off; the choice kept in the settings file.
- The existing simulation, playback, pipeline, cache, reference-job and golden tests pass unchanged.

### From the review of pull request 417

CodeRabbit found that `surely_misses` ([decision 0332](0332-simulator-skips-sure-misses.md)) could reach `f64::clamp` with a NaN interval end and panic, for a line whose direction and range end are both not numbers; the coordinator triaged it to ride this pull request. The extended test `req_nfr_07_req_nfr_06_a_line_that_is_not_finite_is_no_crash_either_way` (one or two bad values at once, also on a level line inside the flutes) reproduced it, and found a second case: a NaN origin made the bound report a sure miss while the search gives a span. Such lines are now left to the search. A project cannot reach either (segments and poses are validated finite before the simulator).

## Consequences

- `openchuck-sim`: `Checkpoint::stock` is an `Arc<PackedStock>`; `Simulator::set_checkpoint_every`, `set_checkpoint_budget` and `from_checkpoints` (new, public). Not in the library family; no version bump.
- `openchuck-app`: `Application::set_playback_with_generation` and `playback_with_generation`; `SetupSimulation::checkpoints`; `StockPlayback::from_the_run`; `SimulateSettings::playback_with_generation`; the pipeline keeps the checkpoints and reports the removed volume from the stock; the cache can drop its stocks alone. The example `playback_times` takes `on` after the memory.
- `openchuck-ui`: the Settings line, the default by the computer's memory (`memory.rs`), the shell gives the application the memory when on.
- UI specification section 13: the setting.
- OI-174 closed. Decisions 0025, 0040 and 0322 are amended as above until edited.
