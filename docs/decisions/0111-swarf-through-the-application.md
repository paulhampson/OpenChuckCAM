## Context

Lane Q built swarf as a library strategy ([decision 0061](0061-slice-17-swarf.md)). Its item 1 says the strategy cuts every face it is given, so a user's selection of faces through `BrepSurface::with_faces` is what is cut, as for drilling. Its item 10 says the application wiring arrived with decision 0056, so the registry's `swarf` strategy runs on a STEP part unchanged, and leaves OI-238: a reference job with a ruled wall so gate 3 replays a swarf program, and the interface's "B-rep only" wording for a mesh selection (decision 0021, OI-96).

Reading the application showed one more gap. Decision 0056 item 3 honours a `Faces` set only for radial drilling, and refuses one for every other strategy ("cannot yet be limited to faces of a STEP model"). With no set, swarf cuts every face of the part, and the operation is refused at the first face swarf cannot cut. Every real part has such a face: the ends of a bar, a face that is not ruled, or a cylinder coaxial with the rotary axis (OI-94). So, as `main` stood, swarf could not run on any real STEP part through the application, and decision 0061 item 10's "runs unchanged" held only for a part made of nothing but cuttable walls. The first proposal closed that gap the way decision 0061 item 1 describes: a face set chooses the walls, and with no set every face is cut. The owner asked instead that swarf require a face set compatible with the operation, so an operation is never sent to cut a whole part, and a set swarf cannot use is refused before it runs.

Records read: 0021 (SP-11, swarf B-rep only), 0051 and 0056 (drilling and the B-rep path through the pipeline, the `drilling` reference job), 0061 (swarf), 0066 (B-rep face picking and stored face sets), 0055 (draft pull requests), 0048 (API changes before 1.0). Open items checked: OI-233, OI-237 to OI-241, OI-96, OI-219.

## Decision

1. **Swarf requires a face set, which chooses the walls it cuts (OP-02, OP-07; the owner's change, amending decision 0061 item 1 for the application).** `brep_selection` in `openchuck-app` accepts a face set for swarf as it does for radial drilling, and the strategy is given `BrepSurface::with_faces` of the chosen faces. A swarf operation on a STEP part with no face set is refused before anything is generated: "swarf needs a face set: select the ruled walls to cut with the side of the tool, save them as a set and put it in the operation". The parameter form says the same as its first note until the operation has a face set. An empty set is refused with swarf's own advice ("select the ruled walls to cut with the side of the tool"), where drilling's says to select the hole walls. Face sets for the other strategies, and boundaries, avoid and check surfaces on a STEP part, are still refused (OI-233). **The library is unchanged:** another host that gives the `swarf` strategy a whole `BrepSurface` still has every face cut, as decision 0061 item 1 says, and is refused at the first face swarf cannot cut. Only the application requires the set.
2. **The set must be compatible with swarf, checked before it runs (the owner's change).** A set swarf cannot use is refused naming the operation, the set and every problem, before the strategy is called. These are the cases covered:
   - *The set itself* (decision 0056 item 3, unchanged): a `Faces` set (an `Edges` set is refused, as only edge following uses edges; triangle and mesh edge sets cannot be made on a STEP model); on the setup's part; made on the current version of the file; not empty; naming faces the model has; no stock to leave of its own (OP-11); and no boundary, avoid or check set in the operation (OI-233).
   - *Each face* (new): ruled within the operation's tolerance, by the library's own `detect_rulings` (decision 0061 item 2), and with its rulings not along the rotary axis (within 0.01 degrees, decision 0061 item 4, OI-94). Every face that fails is named in one message, with the reason ("face 1: it is not a ruled surface within the tolerance: ..."; "face 2: its rulings run along the rotary axis, ..."), and the message says to take them out of the set. Before, the strategy stopped at the first such face.
   - *Not checked before it runs*, because they depend on the tool and the placement of each ruling: a ruling longer than the tool's flank (OI-239), a face with no ruling on its trimmed area, the A range, the gouge and material-left gate (decision 0061 items 3 to 7). The strategy still refuses these, naming the face, as before.
3. **The B-rep-only message (decision 0021, OI-96).** For an operation whose strategy is swarf on a setup whose part is a mesh, the parameter form's first note says "Swarf is B-rep only: it cuts the faces of a STEP model, and the setup's part '...' is a mesh, which has no rulings to follow; add the part as a STEP file.", and generating the operation fails with the same reason, naming the operation and the part, before any selection on the mesh is judged. The strategy's own refusal of a mesh stays for other hosts of the library. The interface already draws a form's notes under its parameters (`form_panel`), so no interface code changes.
4. **The `swarf` reference job runs through the application from a STEP file.** A new OpenCASCADE fixture, `testdata/step/valid/hex_bar.step` (written by `testdata/step/generate/make_fixtures.cpp`): a hexagonal bar along X, 20 mm across the flats, from X 0 to 40, with a flat on top. Each flat is a plane ruled across the rotary axis, 11.55 mm wide. `crates/openchuck-app/tests/step_pipeline.rs` (`kernel-tests`) adds it to a project as it is in the file, picks the six flats in the scene with rays from outside (as a user does in the viewport, decision 0066), saves them as one face set, and cuts them with swarf on the Makera Z1 in oak: a 6 mm two-flute flat end mill with 15 mm of flute (12000 rpm, 0.02 mm per tooth, plunge 150 mm/min), the strategy's defaults otherwise, in cylinder stock 24 mm across and 42 mm long from X -1. Both posts pass gates 1 and 2, the program is the same at 1, 2 and 4 threads, the simulated stock is cut nowhere into the part and is left within a cell on the flats, and it matches `testdata/golden/reference/swarf_makera-z1.nc` and `swarf_linuxcnc.ngc`. `cargo xtask replay` picks the LinuxCNC program up from the folder, so gate 3 replays it with the others; its expected time is added to the shard list.
5. **Why a hexagonal bar.** It is a common four-axis job (a hexagon from round bar) and it stays inside what swarf does today: each flat is one pass at one A, its ruling is shorter than the flank (OI-239), the tool tip and the flank above the far end of each ruling meet only convex edges, so no neighbouring face is in the tool's way (OI-237 is not reached), the bar's ends are planes the tool runs past in air, and the entry is the shared one at the first pose (OI-241). The existing corpus has no part like it: the box's walls are 30 and 40 mm high, longer than any flank in the tool library, and the other fixtures are coaxial or not ruled.
6. **No command-line or interface change.** The command-line tool has no command that adds operations or selection sets, for any strategy; swarf already appears in the add-operation list and its parameter form comes from the uniform schema (OP-16). The command-line end-to-end suite leaves out the STEP jobs (`drilling` and `swarf`), which need the kernel; the reference-jobs document says so.

## Alternatives considered

- **With no face set, cut every face (decision 0061 item 1, the first proposal):** on a real part this is always refused at the first face swarf cannot cut (a bar's end, a face that is not ruled), so the default is never useful. The owner chose to require a compatible set.
- **Check compatibility only in the strategy:** the strategy stops at the first face it cannot cut, so a user with several bad faces finds them one run at a time. The application's check names them all; the strategy's own checks stay for other hosts and for what needs the tool.
- **Leave face sets for swarf to OI-233 (B-rep regions for every strategy):** OI-233 is about containment to faces, which the drop-based strategies would honour by a region. Swarf needs no containment: the faces are its input, as the holes are drilling's. Decision 0061 item 1 already says so.
- **A reference job built from the testkit's closed-form boss without the kernel:** it would run in every CI run, but it would not go through a STEP file, the importer, the placement or the face picking; the closed-form path is covered by the unit test in `operation.rs` (below).
- **The box fixture, scaled down by the placement:** its walls are taller than the flank at full size; a scaled box is a contrived part and still reaches only four A positions.
- **Refuse swarf on a mesh only in the add-operation dialog:** the dialog chooses a strategy before the setup's part is known to it; the form and the generation error cover every route, the command line included.

## Measured

Measured in the lane Q2 session on 18 Oct 2026 (a 4-vCPU container; OpenCASCADE 7.8.1 built by `occt-sys`, 45 min cold).

- **The program.** Opposite flats have parallel rulings, so they are cut at the same A, as the walls either side of the upright tool: three A positions (30, 90 and 150 degrees), two flats each, each flat one pass from X 40 to 0 with the tool's axis 13 mm from the bar's axis (the 10 mm flat plus the 3 mm tool radius) and its tip at the flat's lower corner (Z -5.774, half the 11.547 mm flat), entered by the shared plunge along the tool axis beside the wall (OI-241). The LinuxCNC program is 64 lines, the Z1 program 65. The first test as written expected six A positions; that was the test's mistake, not the strategy's, and it now checks one A per flat, the same A for opposite flats, and the three 60 degrees apart.
- **Gates 1 and 2** pass with both posts; the same G-code at 1, 2 and 4 threads.
- **Simulation** (0.1 mm cells): no rapid cuts, nothing cut into the part (the bar's ends included), and every flat left within a cell away from the ends.
- **Gate 3, run locally:** `cargo xtask replay --docker <image> testdata/golden/reference/swarf_linuxcnc.ngc`, LinuxCNC 2.9.10 in an image built from `docker/linuxcnc` with one local change (the session's HTTPS proxy certificate installed before the `git clone`, which the proxy otherwise refused; the repository's Dockerfile is unchanged): all 54 moves reached, largest difference 0.0039, 105.6 s of motion, no fault. Its shard time is set to 110 s. CI's Gate 3 job has not run it yet (it runs when the pull request leaves draft).
- **Times uninstrumented** (`cargo nextest run`, debug): the swarf reference job tests 0.19 s (gates and golden files), 0.32 s (threads) and 3.6 s (simulation); the face-set unit test 0.11 s; the mesh test 0.02 s. None is near a minute, so `.config/nextest.toml` is unchanged.
- **Coverage** (`openchuck-app`, the new tests only, read on the first proposal and again on the revision): every changed product line is reached except the early return of `brep_only` for a swarf operation whose setup has no part, which falls through to the existing "its setup has no part" error, and the early return of `swarf_needs_faces` for another strategy, which the run of the new tests alone does not reach (every other operation's parameter form does).
- **The revision** (items 1 and 2) changes no program: the reference job already had a compatible face set, so its golden files are unchanged and its tests pass as before.
- `hex_bar` is also in the importer's every-face check (`req_imp_02_every_face_has_uv_bounds_trims_and_a_tessellation`) and the exact-surfaces-against-the-kernel check (`req_imp_02_exact_faces_agree_with_the_kernel`); both pass.
