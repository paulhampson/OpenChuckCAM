## Decision (accepted)

1. **The kernel is behind a feature, the importer is not.** `openchuck-import` has a `kernel` feature (off by default) that compiles `cpp/occ_step.cpp` (a C ABI, about 610 lines) with `cc` against OpenCASCADE 7.8.1 from `occt-sys`, or from `OCCT_ROOT`. Without it the crate, and every other crate, builds with no C++ toolchain (architecture section 12). `StepImporter` is always compiled and always registered for `.step` and `.stp`; it needs only the *worker program* at run time, found through `with_worker`, `OPENCHUCK_STEP_WORKER`, or next to the running program. A missing worker is an `ImportError::Worker` with the fix in words. `openchuck-import` is the only crate that names the kernel, so `cargo xtask deps` is unchanged.
2. **The worker is a child process (decision 0003 item 1).** `openchuck-step-worker <in> <out> <linear> <angular> <unit mm>` runs in a private scratch directory with relative file names (so a non-ASCII temporary path never reaches the kernel), is polled every 5 ms against a timeout (default 120 s) and the job's cancel flag, and is killed on either. It writes one JSON answer; a worker that reports a failure writes `{"error": ...}` and exits with 2; a crash writes nothing and the parent reports a damaged or unsupported file. The importer then runs `BrepModel::validate` on the answer, so a damaged answer is an error and no downstream code sees an out-of-range index. The worker ends by returning from `main` (the static destructors run), so the clean-exit test is the test of the link order.
3. **One document crosses the boundary.** The C++ side returns the whole model as JSON in the shape of `openchuck_types::brep::BrepModel`; doubles are written with 17 significant digits and no negative zero. No kernel type, handle or pointer is exposed. The only `unsafe` code in the workspace is `kernel.rs` (`#![allow(unsafe_code)]`, a recorded exception to the workspace `unsafe_code = "deny"`; 6 foreign functions, each call documented); OI-19 stays open for sanitizer coverage.
4. **Face record (decision 0017 item 2, now built).** `openchuck_types::brep` gains `Surface` (plane, cylinder, cone, sphere, torus with a `Frame` and size, or a `BSplinePatch`), `reversed`, `uv_bounds`, `trims` (UV polylines, even-odd), `body`, vertices (`VertexId`, edge end vertices) and `TessellationSettings`. Frames are exactly as the kernel states them: it allows mirrored frames, so evaluators use `y` as given. `BrepModel::validate` and `joined_tessellation` (the face of each triangle, IMP-06) are added. IDs are positions in the kernel's `TopExp` first-visit order of faces, edges and vertices, identical on Linux, macOS and Windows (decision 0003); bodies are numbered solids first, then free shells, then free faces.
5. **Every non-analytic face becomes a clamped patch over its own parameter box.** A B-spline face is copied and, if periodic, cut open at the face's range (`Segment`), which can move parameters by whole periods; the shift is applied to the bounds and trims. A face of any other kind (revolution, extrusion, offset) is converted over its UV box, and its parameters are **not** preserved (a revolved surface's angle becomes the rational circle's parameter), so the bounds and every trim point are mapped to the patch by projecting the point the original surface gives. The kind the file states stays in `BrepFace::surface` (`other`), so the user is still told what the face was. This was found by the comparison test (item 8): the first version kept the original parameters, and the patch and its trims disagreed by up to 0.55 mm.
6. **Units (IMP-03).** The reader converts to millimetres from the unit the file states. The importer reports that unit (`Units::file`, when it is one of the five we offer) and applies it (`UnitSource::File`, new); no `UnitQuestion` is raised, because the file says. The user's unit overrides it by reading the file's numbers in that unit: the worker scales the shape about the origin before tessellating, so the tessellation tolerance is in true millimetres. A file unit we do not offer (a foot) is converted by the reader and said in a note; an override needs a known file unit. `ImportOptions` gains `tessellation: Option<TessellationSettings>` and loses `Eq`.
7. **Tessellation (IMP-06).** Default 0.01 mm linear and 0.1 rad angular, the finest setting SP-9 measured, single-threaded (so the same file gives the same answer; a test compares two runs byte for byte). Triangles are wound outward (flipped for reversed faces) and kept per face; the kernel's tolerance is not a bound on deviation (decision 0003). Measured here: a 10 mm cylinder at 0.5, 0.1 and 0.01 mm gives strictly more triangles and a smaller worst deviation each time, under 0.02 mm at 0.01; a 15 mm sphere at the default is up to 9.2e-3 mm from the exact surface, still over the 0.005 mm budget of verification plan 4.1, so toolpaths use the exact faces and the tessellation is for display and mesh checks (decision 0017 item 1; OI-76).
8. **Exact `SurfaceSource` (IMP-02; item 6).** `openchuck_path::BrepSurface` (`SurfaceSource`) and `ExactFace` (`ParametricFace`), pure Rust, deterministic, built from a `BrepModel` or a chosen set of face IDs. Analytic faces are closed form; B-spline faces use rational evaluation, a damped Newton ray hit, and a closest-point solver that seeds from a grid and from the nearest tessellation vertex, handles the poles, and polishes (this closes OI-72). `drop_tool` falls back to the tessellation (OI-81 stays open). Verification is a **regression test against the kernel** (`openchuck-app/tests/step_exact.rs`, feature `kernel-tests`; the kernel is reached through `kernel::Oracle`, which numbers faces as the import does): 4,102 samples and 4,102 rays over the 11 fixtures agree to 2.6e-12 mm (point), 2.1e-8 rad (normal), 8.3e-14 mm (closest-point distance) and 1.6e-13 mm (ray distance), and the trim test disagrees with the kernel's classifier on 2 of 4,293 samples. Against the tessellation the exact sphere is 7e-15 mm and the mesh 9.2e-3 mm. The oracle sits behind a feature so the default build never links the kernel.
9. **Corpus, mutation run and CI (items 8 and 9).** `testdata/step` holds the SP-1 fixtures (8 valid, 6 malformed, 12 files that crashed the reader) and five more written by `generate/make_fixtures.cpp` (inches, three bodies, two surfaces of revolution, an extrusion), all written by OpenCASCADE (OI-25 stays open). `examples/step_mutations.rs` damages the corpus at random and imports each file through the importer (150 mutants: 62 read, 42 clean errors, 46 worker crashes caught; the application never crashed), run for 150 files in CI and 3,000 nightly (this closes OI-27). CI gains a `step-kernel` job on Linux, Windows and macOS (build, clippy, the import tests, the kernel comparison, the mutation run), path-filtered and cached with `cache-on-failure` so a failed test does not lose a 30 to 70 minute kernel build (this closes OI-20). `cargo deny` is unchanged because the default feature graph has no kernel.

10. **Follow-ups settled with acceptance (14 Oct 2026).** (a) **Version 0.5.0 (OI-123):** the library family moves from 0.4.0 to 0.5.0 for the new fields on `BrepFace`, `BrepEdge` and `BrepModel`, as decision 0004's lockstep scheme and the 0.2.0 to 0.4.0 precedents do; `cargo-semver-checks` against `main` then reports no update required for the four crates. (b) **The worker ships (OI-118):** `nightly-build.yml` builds `openchuck-step-worker` with the kernel on each platform (cached, saved on failure) and puts it in the archive beside the application with the OpenCASCADE licence texts taken from the `occt-sys` source and `LICENSES/OpenCASCADE-NOTICE.txt`, which carries the source offer (this also does what OI-29 asks for the nightly archives; the release route is slice 20). (c) **Sanitizer (OI-19):** a `sanitizer` job in `nightly.yml` runs AddressSanitizer over the import tests and the comparison with the kernel, with leak detection off because OpenCASCADE leaves small registry objects on its error paths (verified on the garbage file: 80 bytes). Miri is not used: it cannot run C++ and the unsafe Rust is a thin layer over it.

## Alternatives considered

- **Kernel always on:** every workspace build would take 8 to 70 minutes of C++ and the library family could no longer be built without a C++ toolchain. Rejected.
- **A kernel-backed `SurfaceSource`:** decision 0017 item 5.
- **Preserving the original parameters of converted faces** by using the kernel's own evaluation at run time: puts the kernel behind the library port. Rejected; projecting once at import costs one projection per trim sample.
- **One FFI call per fact (the SP-9 shim's 20 functions):** a bigger unsafe surface and a chatty protocol across a process boundary. One JSON document needs four functions and is easy to inspect.
- **`_exit` in the worker** to skip static destruction: hides the link-order fault instead of testing it. The clean-exit test stays; `_exit` remains the fallback if a platform shows the crash.
